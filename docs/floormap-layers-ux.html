1Why layers#

A floor map gets crowded fast, and today there is only one way to organise it.

The editor draws everything on the map as a fact — the background floor plan, gates, desks, cameras, and the moving events (people) that stream over the top. A real site map ends up holding hundreds of facts across a dozen types, plus multiple background images, all layered in time. Three problems show up as soon as it fills:

  • You can't focus. There is no way to say "just show me the cameras and the floor plan" while I check coverage, or to hide the swarm of live events so I can tidy the desks.
  • Editing is risky. Because the background image is itself a fact, it is easy to grab it, an already-placed camera, or someone else's furniture by accident and nudge it. Nothing can be pinned down.
  • Everything competes for attention. Backgrounds, fixed assets and live events all render at full strength. There is no way to push the plan into the background as a faint reference while the thing you care about pops.

Today the only organising axis is the fact's type. The Settings tab already keeps types as an ordered list whose order is the paint order (z-order), with a default shape and colour per type. That is genuinely a proto-layer system — it just has no way to hide, lock, dim, or isolate anything, and no surface on the canvas itself. Layers are the natural next step, and most of the plumbing is a rename-and-grow of something we already have.

Already in the model

An ordered, per-type list drives z-order today (FloorMapDoc.typeStyles → FloorMapZOrder). "Reorder the list to restack the map" is a shipped behaviour we can expose more richly — not something we have to invent.

2What we mean by "a layer"#

Borrowing a mental model people already carry from Photoshop, Figma, AutoCAD and QGIS.

Across design and CAD tools a "layer" is the same handful of ideas. If we adopt the metaphor, users arrive already knowing what the controls do. A layer gives you:

🗂️

Stacking

Layers sit in an order; higher layers paint in front. Drag to restack.

👁️

Visibility

An eye toggle shows or hides everything on the layer at once. Solo isolates one.

🔒

Lock

A locked layer still shows but can't be selected or edited — it can't be nudged by accident.

◐

Opacity

Dim a layer to a faint reference without hiding it, so the active work stands out.

🧷

Grouping

Related things travel together — name them, reorder them, toggle them as one.

🎯

Scope

Selection, "select all", and nudges act within the layers you can currently touch.

Every tool frames the same primitives slightly differently. Worth stealing the best of each:

ToolWhat they nailedWorth borrowing
Photoshop / FigmaEye + lock per row, drag to reorder, opacity slider, alt/opt-click the eye to solo.The row anatomy and the muscle memory.
AutoCADLayer is the primary organising unit; a "current" layer new objects land on; freeze vs. hide (freeze also skips redraw).A default target layer for new facts; hide that truly stops drawing (matters for our redraw cost).
QGIS / mappingLayers driven by data/queries, not manual filing; a layer panel that doubles as a legend.Query-driven "smart" layers — see §7 — and legend-as-panel.

3How this fits the FloorMap model#

Being honest about what exists so we grow it rather than bolt something on the side.

The renderer already composites in passes — grid, then facts (in type z-order), then events on top. User-facing layers should sit on top of that fact model, mapping cleanly onto it:

Layer ideaFloorMap todayProposed
Stacking orderOrder of the typeStyles list = paint order The layer panel is that ordering, made draggable and visible on the canvas
What's on a layerFacts grouped implicitly by type A layer = one type (start), later a group of types or a saved query (§6–§7)
AppearancePer-type default shape + colour Same fields, shown as the layer's swatch/legend row
Show / hide— (nothing)Per-layer eye; hidden layers are skipped in draw()
Lock— (nothing)Per-layer lock excludes its facts from hit-testing & the selection set
Opacity— (nothing)Per-layer group opacity applied at the fact-group level
The shape of the idea

Layers are largely a control surface over the ordered type list we already persist, plus three new per-layer flags (visible, locked, opacity). The debate that actually matters is whether a layer stays 1:1 with a type or becomes a richer grouping — that's §6.

4The Layers panel#

The centrepiece. A dockable panel beside the canvas — try it below.

Give the Editor a Layers panel, sitting alongside the existing Fact List / Time List tabs. Top row = front of the map (the Figma/Photoshop convention). Each row carries the whole vocabulary from §2 in a scannable strip. Below is a live, throwaway mock-up — the map on the left reacts to the panel on the right. It's illustrative, not the real widget.

Layers top = front · drag-equivalent ▲▼

    Toggle the eye to hide a layer, solo (◎) to isolate one, slide opacity to dim, lock (🔒) to protect it, and ▲▼ to restack — watch the paint order change on the map. The map is schematic; real facts carry images and live positions.

    Anatomy of a row

    Left to right, each row is a fixed grammar so the eye can scan a column at a time:

    • Reorder ▲▼ / drag handle — stacking. Dragging is the primary gesture; the arrows are the keyboard/accessible equivalent (and what the mock-up uses).
    • Eye — visibility. Alt/Opt-click to solo (hide all others); alt-click again to restore.
    • Lock — protect from selection and edits.
    • Swatch + name — the layer's colour/shape doubles as a legend; the name is the type (or a group name). Double-click to rename a group.
    • Count — how many facts are on the layer at the current time (see §8).
    • Opacity — a compact slider; also lives in the overflow menu.

    5Per-layer controls in depth#

    The four superpowers, and how each behaves against our renderer.

    Visibility & isolation

    The eye hides the layer's facts entirely — they are skipped when the canvas rebuilds, so hiding a heavy layer is also a performance win (the redraw loop rebuilds the whole SVG each frame today, so "not drawn" genuinely means "not built"). Solo / isolate is the fast path everyone reaches for: show only this layer, remember what was on, restore on toggle-off. A visible Isolate chip while soloing avoids the "why is half my map gone?" trap.

    Lock

    A locked layer still draws but is inert: its facts are removed from hit-testing and can never enter the selection set, so clicks fall through to whatever is behind, and rubber-band selection skips them. This is the single biggest safety win — lock the Background and you stop dragging the floor plan when you meant to grab a desk. Locking also disables the layer's move/scale/rotate handles.

    Reuses the selection set

    Selection is already a set of keys (from the coordinate redesign, §7). "Locked layers can't be selected" is a filter on what may enter that set and on hit-testing — no new selection model.

    Opacity & dimming

    Per-layer opacity applied to the fact group. The high-value pattern is reference dimming: drop the background plan to ~30% so it reads as a faint tracing sheet while your working layer stays at full strength. Consider a one-click "dim others" (a softer solo) that fades every layer except the active one rather than hiding them.

    Stacking

    Drag a row to restack; the map repaints in the new order. This is exactly today's "reorder the type list = change z-order", now direct-manipulation and visible on the canvas. Unconfigured facts (a type seen in the data but not yet placed) already paint on top today — in the panel they surface as a highlighted "Unassigned" layer at the very top, a standing nudge to file them.

    6The design decision: are layers the same as types?#

    This is the fork in the road. Everything else is comparatively mechanical.

    We already group facts by type and order those types. The question is whether a layer is just a nicer face on a type, or a new grouping that sits above types. Three options, cheapest first:

    Option A

    A layer is a type

    Promote the Type Styles list

    The existing ordered type list becomes the Layers panel verbatim. Each discovered type is one layer; we add visible, locked, opacity to TypeStyle. No membership concept — a fact's layer is its type.

    For

    • Almost no new model; ships fastest.
    • Ordering, discovery, shape/colour already done.
    • Zero ambiguity about "which layer is this fact on".

    Against

    • Can't group several types into one layer (e.g. "Security" = cameras + gates).
    • Can't split one type across layers (e.g. by floor).
    • Many types ⇒ a very long panel.
    Option B

    A layer groups types / facts

    New layer entity + membership

    Introduce a first-class Layer that owns an ordered set of types (or explicit facts). Types nest under layers; layers carry the flags. Full graphics-editor power.

    For

    • Arbitrary, meaningful grouping ("Security", "Furniture", "Live").
    • Collapse/expand groups; nested stacking.
    • Closest to what CAD users expect.

    Against

    • New persisted model + membership rules on the doc.
    • Manual per-fact filing fights our data-driven facts.
    • More UI: two-level tree, drag between groups, precedence.
    Option C

    Smart layers (saved rules)

    Layer = a rule over facts

    A layer is a named, ordered rule: "all facts of type X", or "facts matching this query", or "these pinned keys". Membership is computed, not filed. This is how GIS tools think, and our facts already arrive from queries.

    For

    • Membership stays correct as data changes — no re-filing.
    • Native to Stroom: reuses the query the map already runs.
    • "Type = X" is just the simplest rule, so A is a strict subset.

    Against

    • Rule-authoring UI to design.
    • Overlap: a fact matching two layers needs precedence (top wins).
    • More concept to teach than a plain list.
    Recommendation

    Ship A, design toward C. Turn the Type Styles list into a real Layers panel now (eye · lock · opacity · drag-to-restack) — high value, tiny model change, reuses everything. Then let a layer optionally be a rule (type, query, or pinned keys), which makes "one layer = one type" the default case and unlocks grouping without per-fact filing. Treat Option B's manual filing as a last resort, only if users genuinely need to hand-place individual facts.

    See also · Domain Types

    This "is a layer a type?" fork is the same modelling question the companion Domain Types proposal raises from the other side — whether a map object's identity stays a free-typed string or gains a semantic domain type. If it does, "layer = type" becomes "layer = domain type", and Option C's rule-based membership lines up with that doc's query- and meaning-driven grouping. Worth deciding once, across both docs.

    7Smart layers — membership from data#

    Where FloorMap can beat a generic graphics editor.

    Facts already come from a query against the Facts Store, and events from the Events Store. So the most powerful "grouping" isn't manual — it's a saved filter. Three membership modes, in one panel:

    • By type — the default; equals Option A. "Cameras", "Desks".
    • By query / filter — "desks where status = free", "events for badge in (VIP list)", "anything on floor = 2". The layer is a live view.
    • Pinned — a hand-picked set of fact keys, for the odd "these three, specifically" case, without a general filing system.

    Smart layers double as a legend and give us natural switches for common asks: a "Live people" layer you flick off to declutter, a "Coverage" layer that shows only cameras and their fields of view, a "Vacant desks" layer for facilities. Because membership is computed, it stays correct as the timeline moves and as data updates.

    Open question

    When a fact matches two smart layers, which wins for visibility, lock and paint order? Simplest rule: the topmost matching layer owns it (its flags apply; it paints there). Needs a sanity check against real data before we commit.

    See also · Domain Types

    A smart layer that toggles or spotlights everything of a kind is the same capability the companion Domain Types doc calls a semantic legend & filter (C11), and its query-driven membership is the flip side of that doc's bind-by-meaning (E15). Build the legend/filter surface once and let both framings share it.

    8Layers & the timeline#

    FloorMap is temporal; layers have to play nicely with time.

    The map already shows facts as they were at the selected time, and playback animates through time like a video. Layers are a spatial/organisational axis and should stay orthogonal to that:

    • Counts are time-aware. A layer's count reflects facts present at the current time, matching the Fact List's default. (The Fact List's "Show all" clock toggle has a natural per-layer echo.)
    • Visibility is not animated. Hiding a layer hides it across all time; it isn't a keyframe. Time controls what exists; layers control what you're looking at.
    • Onion-skinning, per layer (later). A tempting extra: let a layer show faint "ghosts" of an event's recent past positions — a per-layer trail toggle — without cluttering the rest.
    • Play only what's visible. If the "Live events" layer is hidden, playback needn't animate it — again, a redraw saving.

    9Layers on the read-only Map tab#

    The editor authors; the viewer consumes. Layers matter on both.

    There are two faces: the editable Editor tab and the read-only Map tab that shares the same canvas. Locking and reordering are authoring concerns, but visibility is exactly what a viewer wants — "show me just coverage", "hide the furniture". Proposal:

    • Saved layer presets ("views"). The author defines named visibility sets — Security review, Facilities, Live ops — stored on the doc. The Map tab offers them as one-click switches. This is the layer feature most likely to be used daily.
    • Default state on open. Each layer carries a default visibility/opacity used when the map first loads, so a shared map opens sensibly rather than showing everything at once.
    • Viewer can toggle, not restructure. On the Map tab, eyes and presets are live but lock/reorder/membership are hidden — the viewer explores without changing the authored map.

    10Interaction details & edge cases#

    The small stuff that decides whether it feels good.

    • Clicking into a hidden layer. You can't — hidden facts aren't hit-tested. Selecting a fact from the Fact List whose layer is hidden should offer to reveal it (or flash it), not silently do nothing.
    • Selecting into a locked layer. Blocked, with a subtle cue (cursor/toast). "Select all" and rubber-band act only on unlocked, visible layers.
    • New facts need a home. Borrow AutoCAD's current layer: Add Object Here lands the fact on the active layer (or its type's layer). Facts of an unknown type land on the top "Unassigned" layer until filed.
    • Empty & loading states. Before Discover runs, the panel shows a friendly empty state with a Discover types button (the action already exists). A layer with zero facts now but some in other time ranges shows a muted count, not disappearance.
    • Keyboard. Arrow keys move focus between rows; Space toggles visibility; L toggles lock; [/] restack; Esc clears selection (as today).
    • Performance. Each frame rebuilds the SVG DOM, so visibility must short-circuit before building a layer's facts, not just set display:none. Hidden and locked-but-off layers are the cheap escape hatch for heavy maps.
    • Don't overload "type". If we keep A (layer = type), make sure Settings' shape/colour and the panel's swatch are the same setting shown twice, never two places to edit the same thing that can drift. And if the companion Domain Types styling (Theme C) lands, that single source of truth should be the domain type's shared style — the swatch then reflects the semantic style rather than a free-typed one.

    11Suggested phasing#

    Each step ships something useful on its own.

    1. Panel + visibilityMVP

      Render the existing ordered type list as a Layers panel with an eye per row and solo. Hidden layers are skipped in draw(). Pure win, tiny surface.

    2. Lock + opacityNext

      Add locked and opacity to TypeStyle; lock filters hit-testing/selection, opacity applies to the fact group. The safety + focus story lands here.

    3. Drag-to-restackNext

      Direct-manipulation reorder in the panel, replacing "edit the list order in Settings". Surfaces the "Unassigned" layer at the top.

    4. Presets & viewerThen

      Named visibility presets + per-layer default state, exposed as switches on the read-only Map tab.

    5. Smart / grouped layersLater

      Let a layer be a rule (type / query / pinned) so several types can share a layer and membership stays data-driven. Only add manual per-fact filing if the need is proven.

    12Open questions for the team#

    Layer = type, or more?

    Do real maps need to group several types into one layer (§6), or is one-layer-per-type enough for v1?

    Events as a layer

    Are moving events (people) just another layer, or special enough to deserve dedicated treatment (density, clustering, trails)?

    Where does the panel live?

    A new tab beside Fact List / Time List, a collapsible rail, or folded into the existing Settings type grid?

    Freeze vs. hide

    Is "hidden but still counted" enough, or do we also want AutoCAD-style freeze (excluded from queries/redraw entirely) for very heavy maps?

    Overlap precedence

    If we go to smart layers, is "topmost matching layer wins" the rule everyone expects (§7)?
