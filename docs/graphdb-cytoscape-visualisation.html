Rendering the Graph DB with Cytoscape.js

One element-row contract, two surfaces: a built-in graph view on the Graph DB Data tab, and a reusable graph visualisation in a dashboard.
Status: Design note
Audience: Stroom engineering (graph DB, query UI, dashboard visualisations)
Scope: The data shape Cytoscape.js needs, whether the Graph DB can produce it, and how to surface a Cytoscape renderer in two places — the Graph DB document's Data tab and a dashboard visualisation component — from a single shared output contract.
Two outputs: value table & element table One adapter, two surfaces Bundled, air-gap friendly
The through-line. A graph query has two output modes, both now implemented: a scalar RETURN yields an ordinary value table (for tables, other visualisations, and joins to other datasources), and RETURN GRAPH yields an element table (one row per node/edge) that Cytoscape.js renders as a graph. Both travel the same single-Val[] result pipeline; the graph "format" is a client-side reshape of the element table, not a separate transport — so it feeds both the Data-tab view and a dashboard visualisation through one row→elements adapter.

1. Executive summary

The Graph DB emits results the same way every Stroom query does — a single Val[] table into coprocessors — so a scalar RETURN is already a normal table you can feed to any visualisation or join to other datasources. To draw the graph, the RETURN GRAPH mode returns an element table (one row per node/edge) that maps almost 1:1 to Cytoscape.js's element list. Both modes are implemented (§4).

Given the element table, a Cytoscape renderer can appear in two places:

  • Built into the Graph DB Data tab — a "Graph" view mode next to the existing results table, fed directly by the tab's own query result store. Zero-configuration; the natural place to look at a graph you're building.
  • As a dashboard visualisation — a reusable Visualisation document (Cytoscape bundled as an asset) driven by a Table→Query component, so a graph view can sit alongside other dashboard panes and participate in selection/linking.

Both consume the element table through the same adapter. The dashboard surface additionally needs Cypher to run from a generic dashboard query — the from "GraphDb" routing, also now implemented.

2. What Cytoscape.js needs

Cytoscape consumes a collection of elements — nodes and edges — as JSON:

elements: {
  nodes: [
    { data: { id: 'acct-118', label: 'Account', owner: 'Alice' } },  // id mandatory; rest for styling
    { data: { id: 'd-42',     label: 'Device' } }
  ],
  edges: [
    { data: { id: 'e1', source: 'd-42', target: 'acct-118', type: 'CONNECTED_TO' } }
  ]
}

The firm requirements:

  • every node carries a unique data.id;
  • every edge carries data.source and data.target referencing node ids (and, for stable updates, its own data.id);
  • nodes are de-duplicated — one entry each, even when on many edges;
  • all other fields (label, properties, type, a changeKind) are optional data used for style mapping;
  • positions are optional — a client-side layout (fcose / cola / dagre) computes them, so the database supplies no coordinates.

A flat array of elements each tagged group: 'nodes' | 'edges' is equally acceptable — which is what lets a single flat table feed Cytoscape directly.

3. The enabling contract: one element-row table

The output mode that produces this is RETURN GRAPH — the "annotated subgraph" described in the diff-operator design: the de-duplicated union of every node and edge in the matched subgraph, each row an element carrying its identity and properties (and, in a diff, a changeKind). Kept as a single table (one row = one element, nodes and edges together), it maps directly onto Cytoscape:

Why the single table matters here. A single element-row table serves three things at once: Stroom's existing single-result-set visualisations, the diff operator's annotated-subgraph mode, and Cytoscape's flat group-tagged element array. The adapter is a trivial row→element map: split by kind, dedupe node rows by id, build edges from source/target.

4. Two output modes — and how other graph clients compare

This is the crux of the "we need a table, but the graph is a different format" question. A graph query can produce two result shapes. Both travel the same pipeline — a single Val[] table into coprocessors / a ResultStore — and differ only in schema:

ModeResult schemaFeeds
Scalar RETURN a.id, b.name, …a value table — columns are the projected propertiesa Table component; any Stroom visualisation; joins to other datasources (StroomQL join / Cypher-as-a-join-side)
RETURN GRAPHan element table — one row per node/edge (kind, id, labels, source, target, props[, changeKind])the Cytoscape graph view (via the row→elements adapter, §3)

Both are implemented. The "table for other visualisations and joins" is the scalar path — a Cypher query is just another source of ordinary rows. The "graph format" is RETURN GRAPH, which is still a single flat table on the wire; the nodes-and-edges structure is a client-side reshape, not a separate transport. So there is no second data path to build — only a second RETURN mode (which exists) and one client adapter for the graph case.

How other graph clients handle this

Your instinct is right that mature graph clients give you both a table and a graph view — but the mechanism matters, because it drives our options. Neo4j Browser / Bloom (and Bolt clients generally) do not have two separate return values. They have one result set whose column values can be whole graph entities — a cell can hold a Node, Relationship or Path object carrying identity + labels/type + properties. The client renders that one result either as a Table (show the cell values) or as a Graph (pull the node/relationship entities out of the rows and draw them). Return only scalars and the graph view is empty; return n, r, m and both views work off the same rows.

Stroom's row model is different by design: a Val[] cell is a flat scalar — there is no "node value" type carrying identity + properties inside a result cell, and bare RETURN n / RETURN path is rejected. That flat model is exactly what lets Stroom tables, joins and every other visualisation consume graph results uniformly. So rather than Neo4j's "return an entity, render either way", Stroom makes the graph shape an explicit, dedicated result (RETURN GRAPH → element table). Same destination — a table or a graph from one engine — reached by a different means.

Recommendation. A is the right base and is what shipped — it respects the flat row model and the existing visualisation framework. C is the most attractive addition: because the dashboard vis already binds element roles by column name (§6), the same field-mapping could let the Cytoscape view render any id/source/target-shaped table — including a joined result — with no new engine mode, and it is the natural route to "style the graph by joined data" (§10). B is the full Neo4j experience but costs the flat-Val[] invariant — pursue only if that UX becomes a priority. E is B done right for Stroom (an explicit, honest flatten rather than pretending a Table can render an entity cell) and the principled path to the full "one result → table or graph, and joinable" experience — but it is the biggest change (an entity Val type across the whole stack). D only if a strong "one query, both panes, always in sync" need emerges.

Table and graph together, today

Because a query returns one shape, to analyse tabularly and visualise the graph you use two components over the same MATCH: a scalar RETURN feeding a Table (and joins / other vis), plus a RETURN GRAPH feeding the Cytoscape pane. Each stays semantically clean — you never join on, or bar-chart, an interleaved node/edge list. Option C would later collapse this to one query, where the field-mapping decides whether a given table is also renderable as a graph.

Where the reshape runs: server or client (JS)

Both directions — entities→table (Option E's flatten) and table→graph (Option C's element reshape) — are reshapes, and either can run on the server or in the browser. Which home is right depends on who consumes the result:

  • Server-side (a StroomQL function / the query pipeline) is required whenever the reshaped result must be used server-side — a join to another datasource, further query processing, or a dashboard Table component that feeds other components. Joins and processing run before results leave the server, so a client-side reshape can't feed them.
  • Client-side (JavaScript in the UI) is feasible and cheap for display only — a table view rendered next to the graph view from the same result, with no second query. This is exactly symmetric to the Cytoscape row→elements adapter, which is already client-side JS: the UI receives the result (entities serialised as JSON), and flattens property columns for a grid just as it splits element rows into nodes/edges for the canvas.

So yes — the flatten can live in JavaScript in the UI as well as on the server; they serve different consumers. The server flatten is the canonical one (it alone unlocks joins and downstream processing, and it can equally produce the UI table); a client flatten is a UI convenience for the display-only case. The one caution is duplication: an entities→columns reshape written in both Java and JavaScript can drift apart — the same class of risk as the duplicated assembleRow the review flagged. Mitigate by keeping the client version strictly display-only, or by driving both from one shared column-mapping spec (the vis field-mapping is a natural home).

5. Surface A — built-in on the Data tab

The Graph DB document already has a Data tab that runs an editable Cypher query and shows results. It is built on the shared query UI: GraphDbDataPresenter extends AbstractQueryDataPresenter and renders through a QueryResultTablePresenter — i.e. today it is a table.

The built-in graph view is an additive view mode on that tab:

  • A Table / Graph toggle (or auto-select the Graph view when the query is a RETURN GRAPH). The Table view is unchanged; the Graph view is a new presenter that renders the same result store with Cytoscape.
  • Fed by the tab's existing result store. No new query path — the element-row rows the tab already fetches are handed to the row→elements adapter and into a Cytoscape instance mounted on a client-side element. The tab resolves its target graph from its own doc-ref (ownerDocRef), so no FROM-equivalent is needed here.
  • Cytoscape bundled with the client (a local asset, no external CDN) — Stroom deployments are frequently air-gapped, so the library must be self-hosted.
  • Interaction hooks — node/edge tap can select a row / open the element's properties; a layout picker and a node cap keep large results manageable.

This is the "look at the graph I'm building" surface described as the visualisation stretch in the parent design (temporal-cypher-graph §6.5 / P6.3). It is the lower-effort of the two surfaces because it reuses the tab's own query plumbing and needs no dashboard wiring.

6. Surface B — a dashboard visualisation

Stroom already has a general visualisation framework; a Cytoscape graph is a new instance of it rather than new infrastructure. The moving parts:

  • A Visualisation document (VisualisationDoc) carrying a functionName, a scriptRef, and a settings JSON that declares the config controls and how table columns feed the vis.
  • The code — either a ScriptDoc (with a library like Cytoscape as a dependency ScriptDoc), or — the modern path — an asset bundle: if the Visualisation doc has an index.html asset, the runtime loads /assets/{uuid}/index.html directly (served by DocumentAssetServlet). This is the natural home for a bundled cytoscape.min.js + a small index.html adapter.
  • The runtime — a same-origin iframe (ui/vis.html + vis.js) that talks to the dashboard over postMessage. The vis object must expose element, setData(context, settings, data), and start/end/resize.
  • The data — always table-shaped. The vis is linked to a Table component (itself fed by a Query); the server transforms that table into a nested Store tree (VisJson → VisResult) per the Visualisation's data.structure. Controls bind by column name.

So the Cytoscape dashboard vis is:

  1. A Visualisation doc whose settings exposes field controls mapping element-row columns to graph roles — id, source, target, label, plus style/limit controls — and a data.structure that projects the table as a mostly-flat element list (little nesting; one row per element).
  2. An asset bundle (index.html + cytoscape.min.js + layout extension) that implements the setData contract: walk the Store leaf rows, map columns → Cytoscape elements, cy.add(...), run a layout, and call cy.resize()/cy.fit() on resize().
  3. Selection wiring — a node tap calls the framework's stroom.select(...) to drive dashboard selection/linking, so the graph pane cooperates with tables and other panes.
Dashboard-specific prerequisite. A dashboard Query component is a generic surface, so running Cypher there needs the portable from "GraphDb" routing (today Cypher routes only via ownerDocRef). The Data-tab surface does not need this — it already has the graph's doc-ref.

Fit with the framework's grain, and where it fights it: the vis framework is built for aggregated, nested tabular data; a graph is a flat element list, which is the framework's simplest case (a single values level, no nest). The friction points are (a) per-level limit truncation — a graph needs node/edge caps exposed as controls so a big subgraph degrades predictably; (b) the ~2s refresh throttle and resize lifecycle — Cytoscape must re-layout/fit on those callbacks; and (c) the same-origin, eval-dispatch iframe — the library must be bundled locally, not pulled from a CDN.

7. One adapter, two surfaces

The valuable design point: the row→elements mapping is identical on both surfaces. The only difference is delivery.

Practically, the adapter and a thin Cytoscape wrapper can be authored once and hosted twice: as the client widget behind the Data tab's Graph view, and inside the dashboard vis's index.html bundle. Both receive the same columns; both emit the same elements.

10. Non-goals & open questions

  • Non-goal: a bespoke graph renderer. Cytoscape.js is the renderer; this note is about feeding and hosting it, not reimplementing layout.
  • Non-goal: time-scrubbed animation. A temporal "scrubber" over AS OF instants is a later enhancement; v1 renders one result (including a diff's annotated snapshot).
  • Open: node identity source. Is the Cytoscape id the internal element UID, or a chosen identity property? (Affects stable edge ids and cross-refresh position retention.)
  • Open: Data-tab default view. Should the Graph view auto-activate for a RETURN GRAPH query and the Table view for scalar returns, or always offer a manual toggle?
  • Open: shared code packaging. How is the one adapter shared between an in-app client widget and a sandboxed iframe bundle without divergence — a common JS module built into both?
  • Open: selection semantics. What should tapping a node/edge do on each surface (open properties, filter the table, drive a linked dashboard pane)?
  • Open: graph styled by joined data. A join produces a value table and RETURN GRAPH an element table — today they don't meet, so "colour/size nodes by an attribute joined from another dataset" isn't possible. Option C (§4 — render any id/source/target-shaped table as a graph via the vis field-mapping) is the natural path to it, and is the one place the table and graph outputs would need to converge.

This document is a design note. The query-side output modes — the scalar value table and the RETURN GRAPH element table — are implemented; the remaining work is the Cytoscape renderer, a single row→elements adapter hosted both as a built-in Data-tab view and as a reusable dashboard visualisation.
