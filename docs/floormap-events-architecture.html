Stroom Floor Map · events backend

Two questions,
one store

A proposal for how the Floor Map should read its events. One event stream, two derived structures, and the expensive query moved off the read path — so that drawing the map costs the same whether the store holds a day of history or a year.

01

The architecture

Events arrive as they do today. A periodic builder folds them into a checkpoint — the state of every entity at an hourly boundary — and aggregates them into bucket counts. A query surface we own serves the client from those two, falling back to the log only for the minutes since the last boundary.

BlockWhat it isStatus
AThe event log, keyed by entity then time — append-only, partitioned, retained for a dayexists
BCheckpoints: every entity's state at an hourly boundary, keyed boundary firstnew
CCounts per histogram bucketdeferred
DThe builder — runs the expensive query once an hour instead of 3× a secondnew
EThe query surface, with semantics we define rather than infernew
FThe client — scrubber, variable-speed playback, unchangedunchanged

Three new pieces in total — the checkpoint store, the job that fills it, and the query surface in front. The event log and the client are what exist today.

02

How the map gets drawn

A snapshot at the scrubber position is a checkpoint read plus a short fold forward.

Folding here means overlaying. The checkpoint is a complete answer as at the boundary — every entity, with its position. The events since that boundary are laid on top of it: an entity that moved takes its newest position, and one that did not keeps the checkpoint's. It is the same reduction the client already performs on every result set, except that it starts from a known-good baseline instead of from nothing.

That is exactly why the cost is bounded. Nothing ever searches for an entity's latest row — the unbounded-lookback problem in §03 — because the checkpoint already holds it. Both halves are bounded, and neither grows with how much history the store holds.

The histogram is served the same way in spirit: counts per bucket rather than events, so the bars cost roughly a hundred rows regardless of how many events they summarise. Until the count store earns its place, a GROUP BY over the log with a time index does it in 147 ms for a day.

Playback needs nothing further. It is sampling, not replay — the timeline advances with wall clock, and at ×10000 a single tick covers 35 days — so speed costs nothing as long as each sample is independently cheap. That is exactly what the checkpoint buys.

03

Why it has to be this shape

The client needs two things from the events store and nothing else: where every entity was at the scrubber's position, and how much happened across the visible range. They are plainly different questions. What is not plain is that their access patterns are in direct conflict.

QuestionShapePrunes by time?
State at T
where is everyone, at this scrubber position		 a point lookup per entity, with unbounded lookback No
Activity over a range
the density bars under the timeline		 a bounded range scan Yes

An entity that has not moved for three months still has to appear on the map. Its most recent row may sit in any earlier partition, so a query bounded at T cannot rule any partition out — while a range query rules out nearly all of them.

This is not a property of any particular storage engine. It follows from the key layout, and every temporal store worth considering shares it.

A snapshot cannot be made cheap by narrowing the read. So it has to be made cheap by not doing the work at read time at all — which is what the checkpoint is.

04

What the measurements settled

Four facts, measured on 99,999,000 rows — 3,000 entities emitting 100 events a day for a year — rather than reasoned about.

The decisive one

Pruning cannot help a snapshot

Cost rises with how much history precedes the scrubber — 172 ms at the start of the year, 366 ms at the end, on the same data. So the common case, scrubbing near now, is the slowest.

And seeking is not enough on its own

Hundreds of milliseconds, against a 300 ms tick

Even seeking once per entity rather than scanning, a snapshot over a year of events costs 232 ms warm and 2,408 ms cold. Viable; nowhere near comfortable.

Structural

The key order cuts both ways

Events keyed (entity, time) are exactly right for one entity's history and useless for a time range. Adding one time index took the histogram from 6,780 ms to 147 ms.

Storage

Cardinality beats volume

Repeated event values cost 162 bytes a row; unique ones 1,350. A 10 GiB store lasts seven months or four weeks at the same event rate — the difference is whether payloads repeat, not how many arrive.

05

The one subtlety: late events

A checkpoint is only correct if every event before its boundary has already arrived. Events are pipeline-ingested, so late arrival is ordinary rather than exceptional — and nothing in the checkpoint reveals that one was missed. Hence the grace period: a checkpoint is built at boundary + grace, never at the boundary.

The checkpoint is a performance optimisation, not a source of truth. Correctness lives in the event log.

That is what makes a cheap answer defensible. A grace period is self-healing: an event that misses one checkpoint is still in the log, so the next one picks it up.

ExposureWhat a viewer sees
one boundary intervala single entity at a stale position, for scrubber positions inside that window
afterwardscorrects itself permanently, with no intervention

A very different severity on a monitoring view than in an audit report. If a deployment turns out to have genuinely long lateness, the escape hatch is to fold from an older checkpoint — a read-time knob, with no rebuild and nothing to migrate.

06

What this replaces

Each of these was tried or costed first. None was rejected on taste.

Re-reading the store every tick

What happens today: a whole-store scan three times a second, and a histogram that reads every event and truncates silently at ten thousand rows.

Holding the history in the browser

A year is 18–79 GB depending on payload cardinality. The transfer constraint rules it out before the memory one does.

Replaying events forward during playback

At ×10000 a 300 ms tick covers 35 days of timeline. Replay makes speed expensive; sampling keeps it free.

Delta reads between ticks

A bounded time range is not expressible on either store: an upper bound switches both to snapshot mode, and the caller's lower bound is then discarded.

07

Decisions

All nine are taken. None of them blocks starting.

#DecisionReason in one line
D1Plan B for the event logValue deduplication is worth ~5× on storage, ingest is built for bursts, and merge, retention and snapshots come already written.
D2Hourly boundaries24 builds a day; worst-case fold 15,600 events. Recent times are the ordinary case, not an edge case.
D3Grace period for late eventsSelf-healing, bounded to one interval. What Traces already chose for the same problem.
D4A dedicated store document typeKey and value schema, state type and condense become properties of the type, not fields a user can break.
D5Keep the user-authored events queryThe flexibility is worth the machinery, and it keeps the Events Query tab.
D6Expiry and retention default to 1 dayA user who raises it too far owns the consequence — but expiry above retention must be rejected, not silently under-reported.
D7Checkpoints in their own documentOne document carries one state type, so A and B are two — both ours by type rather than by convention.
D8GROUP BY before a counts store147 ms measured for a day. Build C when wide ranges become an actual complaint.
D9Route the query tab through EFixes a real bug: the accessible summary counts whichever producer pushed last, and that tab publishes unreduced rows.
08

Order of work

  1. Seek-based snapshotThe biggest single win, no new stores and no format change — and it becomes the checkpoint builder's implementation.
  2. Bounded histogramA GROUP BY plus a time index. Removes the last read that touches all history.
  3. Store type and query surfaceOne piece of work: a floor-map-owned document type is not served by the generic search provider, so E is its prerequisite.
  4. CheckpointsThe bounded snapshot. Worth deriving in memory first, to prove the fold and the grace logic before committing to storage.
  5. Counts storeOnly if wide-range histograms become a complaint.

Steps 1 and 2 are independently shippable and each fixes a defect that exists in the code today.

Every figure here is measured — a 99,999,000-row query benchmark and a store-capacity probe — not estimated. Full reasoning, the assumptions it rests on, and the alternatives considered and rejected are in docs/floormap-events-backend-design.md.
