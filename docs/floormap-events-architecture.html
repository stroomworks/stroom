Stroom Floor Map · events backend

Two questions,
one store

The Floor Map needs two things from its events store, and their access patterns conflict. Resolving that turned out to need far less machinery than first proposed — one change to how the store is read, and one to how the histogram is counted.

01

The architecture

Events arrive as they do today. The map reads the store directly, seeking to each entity's position rather than scanning for it. The histogram counts server-side. A query surface we own sits in front so the semantics are ours to define.

02

How the map gets drawn

Entries are stored under prefix + time, so one entity's history is already contiguous and in time order. That means its position at any instant can be found by seeking to that instant and stepping back one — rather than by reading the entity's whole history and keeping the newest row that qualifies.

Measured at floor-map scale: 3 000 entities, snapshot taken with the whole history behind it. 5–8 ms, and unchanged when the store grows twentyfold.

A year of events adds about four more B-tree levels over the six million measured here, so call it six milliseconds — against a 300 ms playback tick.

03

How the data drives the UI

Playback samples; it does not stream. No query delivers a window of time that the client then plays through, and nothing is carried between ticks.

WhenQuerySize
every 300 ms while playing, and on every scrub, step or loopsnapshot at the scrubber's position~3,000 rows · ~6 ms
when the visible range changesbucket counts for the density bars~100 rows

Why sampling rather than a window. The timeline advances by wall clock × speed, not by event count — so at ×10000 a single 300 ms tick covers 35 days of timeline. A prefetched window would need to hold 35 days of events to serve one tick, and what it must hold grows without bound with speed. Sampling costs the same at every speed, which is why speed is free today and must stay so.

Each tick is independent

The answer at T does not depend on the answer before it, so a dropped or late tick costs nothing and needs no catching up.

One read at a time

A tick arriving while a read is in flight is skipped. The next one asks about a position at most 300 ms further on.

A scrub is not a special case

The same query at a different position. No window to refill, and no events to replay in order to arrive there.

Nothing accumulates

The client holds one row per entity — the last answer — and replaces it wholesale. The only thing kept is where each entity was drawn, so movement interpolates instead of teleporting.

04

Why it has to be this shape

The client needs two things from the events store and nothing else: where every entity was at the scrubber's position, and how much happened across the visible range. They are plainly different questions. What is not plain is that their access patterns are in direct conflict.

QuestionShapePrunes by time?
State at T
where is everyone, at this scrubber position		 a point lookup per entity, with unbounded lookback No
Activity over a range
the density bars under the timeline		 a bounded range scan Yes

An entity that has not moved for three months still has to appear on the map, and its most recent row may sit anywhere in the store. So the map is served by seeking per entity, and the histogram by a grouped count — two different reads, because they are two different questions.

05

Storage

Only one schema matters, because only one store holds the data.

PartStructureWhy
Keyprefix ‖ big-endian timePuts one entity's history together and in order, which is what makes the seek possible at all
ValueVARIABLEDeduplicates repeated values through a lookup table — worth about five times on storage

Repeated event values cost 162 bytes a row; unique ones 1,350. A 10 GiB store lasts seven months or four weeks at the same event rate.

That is the decision to get right early, because a Plan B key or value schema is immutable once data is written. Anything per-event and unique in the payload — an embedded timestamp, a sequence number — defeats deduplication and costs roughly five times the store. It is a larger lever than event rate, and it is fixed a long way from where the symptom appears.

06

What this replaces

Scanning the store every tick

What happened before: every row read and discarded to find one per entity, three times a second, with cost growing as the store filled.

A histogram that read every event

Counted on the client, and truncated in silence at ten thousand rows — hours of coverage at the finest bucket width.

Checkpoints, and the machinery around them

A store of hourly keyframes, a job to build it, a grace period for late data and a rebuild to repair it. All of it existed to bound a read that is now six milliseconds.

Holding the history in the browser

A year is 18–79 GB depending on payload cardinality. Ruled out by transfer before memory even comes into it.

07

When checkpoints come back

Not never — just not yet. The trigger is entity count, not history, because that is what the cost is proportional to.

EntitiesSnapshot
3,000~6 ms  measured
100,000~200 ms  projected

At tens of thousands of entities, or if a cold-cache snapshot on a large store proves slow in practice, the checkpoint design is the answer and is written up in full. It would return with one change from the version proposed here: late data handled by periodically rebuilding the last few hours rather than by delaying each keyframe behind a grace period — repair on a schedule beats waiting and hoping.

08

State of the work

  1. Seek-based snapshot — built47× faster at 200,000 rows and flat in history depth. Verified against 4,071 store tests and a nine-case parity suite running both temporal stores live.
  2. Server-side histogram — builtCounts per bucket instead of events. Bucket width follows the visible range, from five minutes up to thirty days.
  3. Query surface — nextA dedicated store type, so key schema, value schema and condense become properties of the type rather than fields anyone can edit into an unusable state.
  4. Counts store — only if neededThe grouped query is bounded below but not above; a store of counts closes that if wide ranges become a complaint.
