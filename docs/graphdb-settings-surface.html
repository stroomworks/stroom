The Graph DB configuration surface

Do we need a settings tab in the Graph DB UI to tune Plan B — and what settings should a graph expose?
Status: Design note / recommendation
Audience: Stroom engineering, and product owners deciding the Graph DB editor's shape
Scope: What "tuning Plan B" means for a graph, why a raw Plan B settings tab is the wrong shape, and the tiered per-graph configuration surface we should build instead — including the settings a graph will legitimately need to vary per document.
Verdict: no raw Plan B tab Per-graph settings: yes, eventually Principle: graph-altitude, mapped down
Short answer. No — we should not add a tab that exposes Plan B's raw tuning knobs, because a graph is not one Plan B store but several, and those knobs are per-store physical/operational settings. But per-graph settings are coming and are the right idea — the question is altitude. A graph should expose a small set of graph-level choices (retention, temporal precision, mapping today; a storage budget and condense policy later) that the graph then maps down onto its internal stores. That "one graph-level setting, fanned out to the sub-stores" pattern already exists in the code for retention; this note proposes generalising it, not exposing Plan B directly.

1. Executive summary

The trigger question was narrow: "do we need a settings tab in the Graph DB UI to allow tuning Plan B?" The answer splits in two.

  • Exposing Plan B's raw knobs — no. Those settings (store size, merge/overwrite behaviour, snapshotting, condense, physical key/value schema) are defined per Plan B store, and a single graph owns several stores. There is no one "Plan B" for a graph to tune, and surfacing the per-store internals would be a large misconfiguration surface for no user benefit.
  • Per-graph settings in general — yes, and we will need them. Different graphs will legitimately want different retention windows, different time granularity, different size budgets and condense policies. The right design expresses these as graph-level settings on the GraphDbDoc and translates them, inside the graph, into the concrete per-store Plan B settings. The graph is the abstraction boundary; Plan B stays an implementation detail.

This note inventories the actual Plan B knobs, explains why the graph must sit a level above them, and proposes a three-tier configuration surface: what to expose now, what to expose later (behind an Advanced section, with good defaults), and what to keep entirely automatic.

2. What "tuning Plan B" actually means

Every Plan B store carries the settings below — the common ones on AbstractPlanBSettings, plus per-type extras (e.g. condense, keySchema, valueSchema on TemporalStateSettings). This is the concrete meaning of "tuning Plan B":

KnobWhat it controlsDefault
maxStoreSizeThe LMDB map-size cap for the store10 GiB
retentionWhether/how long to keep old data (enabled, duration, use-state-time)disabled; 1 year
condenseCollapse versions older than a duration (reduce history granularity)off
snapshotSettingsUse cluster snapshots for lookup / get / query (distribution behaviour)all false
synchroniseMergeWhether merges run synchronouslyfalse
overwriteOn a duplicate key, overwrite vs keep-firsttrue
keySchema / valueSchemaPhysical key/value serde layout (hash lengths, value types, tiering)type defaults

Two things stand out. First, these are a mix of capacity (maxStoreSize), lifecycle (retention, condense), cluster/operational (snapshotSettings, synchroniseMerge), and physical layout (keySchema/valueSchema) concerns — very different altitudes. Second, they are attached to a single store. That is the crux of the next section.

3. Why "tune Plan B" is a category error for a graph

A graph is not backed by one Plan B store. A single GraphDbDoc owns one LMDB environment containing several sub-stores (GraphStores):

  • four interning stores (node / label / edge-type / property-key UID lookups),
  • the node store, the out-edge adjacency, the in-edge adjacency,
  • and the property-value anchor index.

Plan B's settings are per store. So "let the user tune Plan B" has no single referent for a graph — it would mean exposing (say) a maxStoreSize and keySchema for each of the sub-stores, most of which the user has never heard of and should never have to reason about. Worse, several are physical-layout choices the graph deliberately freezes for itself (the order-preserving key layout that makes adjacency prefix-scans and as-of lookups work) — a user-facing keySchema knob there is not a tuning option, it's a way to break the graph.

The tell. If a proposed setting only makes sense once you know a graph is secretly N Plan B stores with a frozen key layout, it is an implementation detail, not a user setting. The graph exists precisely to hide that.

4. What the graph exposes today (and the tab we removed)

The document model already draws the line in roughly the right place. GraphDbDoc models exactly four things beyond standard doc metadata:

FieldMeaningBorrowed from Plan B?
descriptionFree textno (standard doc metadata)
temporalPrecisionGranularity of the time axis — DAY…NANOSECONDyes (TemporalPrecision)
nodeTypeMappingsWhich fields become which nodes / labels / edgesno (graph-specific)
retentionKeep-history policyyes (RetentionSettings)

Note what is absent: no maxStoreSize, no condense, no snapshotSettings, no keySchema. The graph currently opens its environment with a default size (the env is constructed with a null size, i.e. the Plan B default) and hard-codes its physical layout. That is the intended shape — the doc carries graph-level choices only.

There is also a concrete piece of history worth carrying forward. A Settings tab used to exist in the editor and was deliberately removed (GraphDbPresenter): it exposed only a description field, which the Documentation tab also binds, and because the editor folds every visited tab's write over the document with no per-field conflict detection, having two tabs bind the same field caused a last-write-wins clash. The lesson is not "never have a settings tab" — it is "a settings tab must own distinct fields."

5. The principle: settings at the graph's altitude, mapped down

The design that makes per-graph settings safe is already demonstrated in the codebase for retention. Retention is a single policy on the document; when it runs, GraphStores.deleteOldData reads doc.getRetention() once and applies it across all three temporally-versioned sub-stores. One graph-level choice, fanned out to the internal stores. The user never sees the fan-out.

This is the whole design rule: the user configures the graph; the graph configures Plan B. A per-graph "size budget", for example, is one number the user understands ("this graph may grow to ~X"), which the graph apportions across its sub-stores — not five separate maxStoreSize fields.

6. A tiered configuration surface

Sorting every candidate setting by altitude gives three tiers. Tier 1 is a genuine near-term settings tab; Tier 2 is the "different settings per graph" future, exposed carefully; Tier 3 stays automatic forever.

SettingTierRationale
Retention (keep-history window)Expose nowAlready on the doc; a clear operator choice; already mapped down by deleteOldData. Has no editor yet.
Temporal precision (DAY…NANOSECOND)Expose nowAlready on the doc; determines the meaning of "as of"; a real per-graph choice. No editor yet.
Node / edge mappingExpose nowAlready on the doc; the graph's schema. Often derivable from the domain-type catalogue, but needs a review/edit surface.
Storage size budget (graph-level, apportioned to sub-stores)Advanced (later)Legitimately varies per graph (scale differs), but should default well; expose as one graph budget, not per-store maxStoreSize. Currently a fixed default.
Condense policy (collapse old versions)Advanced (later)A real lifecycle lever that differs by graph; pairs naturally with retention. Default off; expose once retention editing lands.
Snapshot / distribution behaviourAdvanced (later)Per-graph in principle, but a cluster-operational concern; better as a sensible default (or system policy) than an everyday knob.
Key / value schema & serdesAutomaticPhysical layout the graph freezes for correctness (adjacency scans, as-of lookups). A user knob here breaks the graph.
Interning, adjacency layout, sub-store composition, shardingAutomaticThe graph's internal machinery. The whole point of the GraphDbDoc wrapper is to own these.
synchroniseMerge, overwriteAutomaticCorrectness/consistency behaviour the graph should set for itself, not per document.
Where "different settings per graph" lands. It is real, and it lives in Tiers 1 and 2 — retention, precision, mapping now; a size budget and condense policy later. What it is not is Tier 3: exposing Plan B's physical/per-store internals. Per-graph variation is expressed at the graph's altitude and mapped down.

7. Design constraints for the settings tab

Whoever builds the tab should hold to a few rules the code history and architecture already imply:

  • Own distinct fields. Do not re-bind description — the Documentation tab owns it. Binding the same field from two tabs is exactly what got the previous Settings tab removed.
  • Edit graph-altitude fields only. The tab writes GraphDbDoc fields; GraphStores maps them onto the sub-stores. The tab never addresses a sub-store directly.
  • Default everything. Each new field must have a sensible default so an untouched graph behaves exactly as today; advanced fields live behind an Advanced disclosure, collapsed by default.
  • Flag rebuild-implying changes. Some settings (e.g. temporal precision, or any future physical choice) only take full effect on rebuild. Because a graph is a materialised, rebuildable projection, this is supported — but the UI must say so rather than imply an in-place change.
  • Leave room for the config surface already anticipated. GraphStoreManagerImpl notes it runs "without yet introducing a dedicated config surface (P5 hardening)" — this tab is that surface; build it where that hardening expects it.

8. Recommendation & phasing

  1. Near term — a minimal Settings tab for Tier 1. Add an editor for the three graph-level fields that already exist on the model but have no UI: retention, temporal precision, and node/edge mapping. This fills a real gap (those fields are currently only settable at creation / via import), and it re-establishes a Settings tab correctly — owning its own fields, not description.
  2. Medium term — Tier 2 behind Advanced. Introduce a per-graph storage budget (one number, apportioned by GraphStores to the sub-stores; today the env uses a fixed default) and a condense policy alongside retention. Snapshot/distribution behaviour can follow if a real need appears, but is a candidate for system-level policy instead.
  3. Never — Tier 3. Keep physical schema, interning, adjacency layout, sharding and merge/overwrite behaviour owned and defaulted by the graph. These are not user settings.

Net: we do not add a tab to tune Plan B, and we should resist requests to. We do add a graph-settings tab — starting with the fields that already exist and are genuinely user-facing — and we grow it along the graph's own altitude as per-graph needs (size, condense) become concrete.

9. Open questions

  • Size budget mapping. How should one graph-level budget be apportioned across node / adjacency / index / interning sub-stores — fixed ratios, or measured-and-rebalanced? What is the sensible default that replaces today's single fixed env size?
  • Precision changes on a populated graph. Is changing temporalPrecision after ingest a rebuild-only operation, and how is that surfaced?
  • Snapshot behaviour altitude. Is distribution/snapshotting ever a per-graph choice in practice, or should it always be system policy?
  • Mapping editor scope. How much of the node/edge mapping is derived from the domain-type catalogue (§ of the temporal-graph design) versus hand-edited here, and how do the two reconcile in the UI?

This document is a design note, not a commitment. It argues for a graph-altitude configuration surface that maps down onto Plan B, rather than a tab that exposes Plan B's per-store internals; the near-term Tier 1 tab simply gives the three settings already in the model an editor.
