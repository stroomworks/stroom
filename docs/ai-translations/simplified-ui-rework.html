Shapeshifter AI UI Rework, simplified

This is a version of the Shapeshifter AI UI Rework that assumes the server-side simplifications are adopted. The aim is the same: organise the screens around what a person does (set a document up, watch its feeds learn, step in when one needs them). What changes is how much there is to show. There's one fixed way of learning, so the flow editor goes. New translations wait for approval by default, and the Supervisor has fewer actions.

Superseded, 18 November 2026: not to be built. The agreed UI is described in ui-design.md. Unlike this proposal, it keeps editable flows and every Supervisor action.

Editing the flow Removed: one fixed approach

The server learns every feed the same, tested way. Settings shows it as a short read-only explanation. There's no Approach tab and no step editor. See section 7.

New translations Wait for approval by default

Using them automatically is a per-document choice that needs a permission. Every promotion goes through the same Approve screen. See section 6.

Monitoring screen Stays, as the administrator's view

An overview across every document: what's stuck, overdue, costly or running unattended. Actions move to the Feeds tab. See section 8.

What's wrong today

These are the workbench screenshots from the design docs (design/images), with the problem areas marked. Most of the problems come from one cause: the screens mirror the engine's own model (learners, sessions, turns, a flow graph), when a person thinks in feeds and in what needs doing.

Two problems don't show in the screenshots:

  • Setup is spread over four places. A Shapeshifter AI document, a template pipeline whose element points at it, a Pipeline Factory document pointing at the template (with a run-as user and a stream filter, then enabled), and the Monitoring screen to watch it all. Nothing tells you whether you've done all of it.
  • A new document judges nothing. It has no scorers, so every candidate passes, and nothing says so (ISSUES 22).

7

How a feed is learned

In the full rework, sections 6 and 7 described the Approach tab and its step editor in detail: starting-point cards, step cards, rules, menus, a route map and a text view. With the server's fixed recipe there's nothing to edit, so all of that is replaced by the short read-only panel at the bottom of Settings (section 6), and by the progress strip on the Feeds tab, which uses the same step names.

StepWhat happensIf it runs out of tries
1 Choose the elementsThe AI picks the parser and transform, e.g. DSParser → XSLTFilter.Paused for a person
2 Write the parserThe AI writes the parser configuration. It's run on the stream and judged on reading all the input and giving the right number of records.Learning stops for the feed (its streams error with the reason)
3 Write the transformThe AI writes the XSLT. It's run on every record and judged by the Quality checks.Goes on to step 4
4 Unknowns, if neededThe AI writes the XSLT once more, now allowed to mark kinds of record it can't translate as Unknown events.Paused: couldn't finish

Why fixed rather than editable. On a document that uses new translations straight away, nobody reads a run before its result goes live. Every document should therefore learn in a way that's been tested, rather than one edited on a screen. Fixing it also removes a kind of failure the full rework had to design around: "this approach is invalid, so learning stops".

What goes: the Learn tab with its FlowChart, FlowStepEditor and TransitionEditor; the starting-point cards and step cards the full rework would have built; moving the kinds' default checks into the shared model (ISSUES 8); and the "edit lost on clicking another step" problem (ISSUES 7), since there's nothing to edit.

Existing documents: a document saved with a flow loses it when the server stops reading the field. Every document then learns the fixed way. The feature hasn't been released, so this only affects demo and test content.

Delivery plan

Each phase can ship on its own and leaves the Monitoring screen working. Each comes with workbench stories (default, read-only, dialog OK and Cancel) run with the leak check, as stroom-gwt/UI-GUIDE.md asks. The phases are timed against the server work: the client stops using a feature before the server removes it.

Phase 1Words, wiring and hiding
  • New Settings tab built from the Learn tab's Start section, with the promotion mode and held-out fraction moved over from Score, tries per step, and the read-only "How a feed is learned".
  • Readiness line with the document checks, replacing ProcessHeader.
  • Labelled buttons and the state sentence in the existing Supervisor, from a client-side FeedSituation worked out from SupervisorLearner and SupervisorAttempt.
  • Hide the actions being removed: Accept, Improve, Exhaust, Answer instead, Guidance. Hide the Learn tab's flow editing. Once this ships, the server can remove the endpoints and the flow field.
  • Turns and Conversation merged into one read-only expanding list in TurnTranscript.
  • The new on-screen wording.
Phase 2Feeds tab
  • Feeds tab in ShapeshifterAiEditor: LearnerList on the left, a new FeedDetail component on the right, with progress strip, conversation, waiting streams and earlier runs. There's no note box.
  • Approval evidence, who approved, and the spending-limit state: the three server additions in section 12.
  • Monitoring keeps working as today, with the hidden actions gone. Each action that the Feeds tab now offers stays in Monitoring until phase 4.
Phase 3Quality, and removal
  • Quality presets.
  • Delete the Learn tab, FlowChart, FlowStepEditor, TransitionEditor, TurnAnswerEditor, and the guidance, improve and exhaust dialogs, in step with the server removing the shared flow types.
  • This replaces the full rework's largest phase, building the Approach tab, with deletion.
Phase 4Administrator's overview
  • Rebuild Monitoring as the overview in section 8: tiles, spending meter, feeds grouped by document with their mode, recent automatic approvals, and Open into the Feeds tab.
  • Remove the Supervisor's own actions and its three stacked grids, now that the Feeds tab has every action.
  • The server additions for system-wide spending and the approval filters (section 12).
Phase 5Setup, if needed
  • Connected readiness checks, information only.
  • Setup wizard.
14

Open questions

  1. Per-feed notes. A document serves many feeds, and a note like "the %ASA-6-302013 code is the event type" belongs to one of them. Putting it in the document's instructions sends it to every feed. Should the server keep a simple per-feed note (add and withdraw, no history) after all? If so, the note box from the full rework comes back, without the history.
  2. Fewer ways to unstick a run. With no Answer it myself and no Finish with Unknowns, a paused feed's remedies are: more budget, better instructions, or Learn again. Is that enough for v1, or is Answer it myself the one deferred action worth bringing back early?
  3. Quality presets. Which checks and pass marks go into Lenient, Standard and Strict? Should Standard be what a new document starts with (which would close ISSUES 22)?
  4. Approval evidence. Is one record next to its event enough, or should approval also show the lowest-scoring records by default? This matters more here, since approval is the everyday path.
  5. Who sees Monitoring. Which application permission gates it: the one that gates Monitoring today, or a new one for AI translation? Rows are already limited to documents the person can view.
  6. Acting from Monitoring. Should an administrator be able to do anything directly from the overview, such as stopping all learning for a document in an emergency, or is Open into the Feeds tab enough? Switching learning off in the document's Settings already does the former.
  7. Connected readiness checks. Build them in phase 5, or wait and see whether phase 1 and the wizard make them unnecessary?
