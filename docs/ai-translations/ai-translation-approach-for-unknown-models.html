Fixed steps or a model in charge? Designing AI Translations for a model we don't control

Branch ai_translations_server · 17 November 2026 · Looks at whether Shapeshifter AI should keep breaking translation into small, checked steps, or hand a capable model the whole pipeline, given that some installations run a self-hosted model of unknown strength. Some Stroom knowledge assumed; the Shapeshifter terms used are explained as they come up.

The short answer. Keep the step-by-step design as the floor that every installation gets, because it is the only approach that works with any model. Add larger steps, up to "write the whole pipeline", for installations whose model has been measured as able to handle them. Whatever the step size, decide promotion with a small set of objective checks that don't depend on the model, plus reference data and, until trust is earned, a person's approval.

Related tasks. Six raised tasks fix faults this paper relies on: shapeshifter-ai-missing-year-hard-coded.md, shapeshifter-ai-mixed-record-elements.md, shapeshifter-ai-parser-drift-not-detected.md, shapeshifter-ai-preservation-matches-record-markup.md, shapeshifter-ai-single-target-schema.md and shapeshifter-ai-supervisor-visibility.md. Section 5 sets out the proposal, with mock screens. 1. The question

Shapeshifter AI learns how to turn a feed's raw data into event-logging XML. Today it does this as a flow of small steps, each with a defined input, a defined form of answer and its own checks. The Any feed document on the dev instance uses the ESCALATING example flow:

CHAIN                      which elements: e.g. JSONParser -> XSLTFilter
SPLIT                      what one record is
CONFIGURE parser           on yield-short goto split
first: CONFIGURE transform 2 candidates; on passed goto end, else goto target
TARGET kinds 3             write the event one record of each kind should become
again: CONFIGURE parser
CONFIGURE transform        on preservation-short goto again, else goto admit
ADMIT

Each answer is scored by code (it compiles, it is valid against the schema, enough events come out, and so on), and a step that falls short sends feedback back to the model or moves the flow on. This works with small models, such as Haiku, on simple formats, because every question is small and every answer is checked mechanically.

The alternative now being explored gives a much more capable model complete control of the pipeline: it chooses the structure, writes the parser and the XSLT, and runs them. Its checks are that everything compiles, that the feed's processing shows no errors, and the model's own understanding of the input and output.

The constraint. We don't choose the model. At least one installation runs a self-hosted model through an OpenAI-compatible endpoint, and we don't know how capable it is. Any design has to behave sensibly with a model anywhere from small to frontier-class.

2. What the demo feeds show

The evaluation of the ten demo feeds (docs/ai-translations/shapeshifter-ai-demo-evaluation.md) and the OTEL-TRACES attempt diagnosed this week point to two separate limits of the step-by-step design.

Limit 1: the system can't improve what the scorers can't see

Every feed that learned was promoted with a score of 1.0 (WINDOWS-SECURITY 0.966). That includes NETFILTER, which reviewers rated Poor. Its learned XSLT contains this:

<!-- the feed's logs are from 2023 -->
<xsl:variable name="year" select="2023"/>

The year is invented: the source lines (Oct 19 09:00:03 …) don't state one. The translation also dropped line 25 (FRAG:185) and decided the outcome from the rule name (contains($prefix, 'DROP')), so FW-SCAN-XMAS reads as permitted traffic. It compiles, is valid against the schema and raises no errors, so no scorer objected.

The year is not simply a model mistake. The model isn't shown when the stream was received, and the prompts never mention stroom:format-date, Stroom's function that takes a missing year from the stream's received time. No model, however capable, could have known the right year (shapeshifter-ai-missing-year-hard-coded.md).

The scorers fail in the other direction too. In attempt 147 on OTEL-TRACES, the model's targets were correct, but the preservation check wrongly reported the value SpanId as missing. That word was a label the model chose for a Data element, and the check found it inside the JSON key parentSpanId. The attempt parked with "JSONParser failed on its input" (see shapeshifter-ai-preservation-matches-record-markup.md). Every check written by hand is also code that can be wrong.

And once a translation is serving, nothing judges the input side at all. NETFILTER's ISO-timestamp drift sample produced no events and 20 parser errors, yet the learner stayed Serving with a score of 1.0, and nothing was deferred or relearned (shapeshifter-ai-parser-drift-not-detected.md).

Limit 2: the system can only express what its steps can express

The SPLIT step names one element or array as "the record". Two feeds need more than that:

  • GATEWAY-AUDIT never learned. Its records are the children of <batch>, under nine different element names (authentication, transfer, share, policyChange, …). The split only accepts "every element named X", covering at least 90% of the text, so every answer naming a real record was rejected and the attempt stopped with No record boundary after 5 candidates. The model's last reply was "No single element name fits. The records are the mixed children of batch …": a correct diagnosis, refused because it wasn't an element name (shapeshifter-ai-mixed-record-elements.md).
  • OTEL-TRACES learned at the wrong grain. The split chose resourceSpans, so a block holding four spans became one event, with three of them squashed into <Data Name="ChildSpan" Value="…"/> strings.

Tellingly, the model's own first XSLT for OTEL-TRACES (turn 3) got the structure right: one event per span, with the enclosing resource and scope available to each:

<xsl:for-each select="//array[@key='resourceSpans']/map">
  <xsl:variable name="res" select="map[@key='resource']/array[@key='attributes']/map"/>
  <xsl:for-each select="array[@key='scopeSpans']/map">
    <xsl:variable name="scope" select="map[@key='scope']"/>
    <xsl:for-each select="array[@key='spans']/map">
      <Event> … span fields, plus host and service from $res, generator from $scope … </Event>

That candidate failed for an unrelated schema reason (TimeCompleted isn't allowed in EventTime), but the structural judgement was better than the framework's split, which then overrode it.

Example: what "compiles and no errors" lets through

The full-control approach removes the second limit, but its scoring is weaker than it looks. Both of these pass "compiles" and "no errors in the feed":

An invented constant

<xsl:variable name="isoTime"
  select="concat($year, '-',
                 format-number($month, '00'), '-',
                 format-number(xs:integer($ts[2]), '00'), 'T',
                 $ts[3], '.000Z')"/>

NETFILTER's real code, with $year fixed at 2023 and .000Z appended to a time the source doesn't give a zone for: valid, error-free and wrong. See shapeshifter-ai-missing-year-hard-coded.md.

A catch-all that hides failure

<xsl:choose>
  <xsl:when test="$id = '4634'"><Logoff/></xsl:when>
  <xsl:otherwise><Logon/></xsl:otherwise>
</xsl:choose>

Illustrative, after WINDOWS-SECURITY's catch-all: a 4625 failed logon becomes a logon. The evaluation found catch-alls like this on six feeds.

"No errors" is easy to satisfy by swallowing everything. A capable model told to reach zero errors will, sooner or later, do exactly that. Using the model's own understanding as the remaining check means the model marks its own work; the faults that need a second look are precisely the ones it is confident about.

The scoring problem doesn't go away with a stronger model. It moves into the model's head, where it can't be inspected, tested or regression-checked.

4. What an unknown model changes

If every installation had a frontier model, the obvious design would put that model in charge and keep strong checks around it. Not knowing the model rules several things out:

Model review as a check
A weak model reviewing its own output, or another copy of itself reviewing it, tells you nothing. In the evaluation, the reviewers were a strong model (Claude Fable 5.2) given raw records beside output events, and they found every fault. An installation can't count on having that.
Tool calling
Full control usually means an agent loop: run the pipeline, read the errors, change the XSLT, run again. Self-hosted models behind OpenAI-compatible endpoints vary widely in whether function calling works at all, and how reliably.
Context
The whole-pipeline approach needs room for samples, schema extracts, tool output and history. The Any feed document already caps samples at 8,192 bytes (sampleSizeLimit) for this reason.
Speed
Self-hosted models can be slow. The 60-second read timeout (now fixed) cost AUDITD-AUSEARCH 15 failed attempts and 1.74 million tokens. Small steps that can each be retried are more forgiving than one long session.
Format of replies
Small steps check each reply against a fixed form, so a model that answers off-format is refused and asked again. A free-form session has no such guard rail.

So the step-by-step design isn't a crutch to retire once models get better. It is the one approach that works whatever the installation runs. What should change is how big the steps are, and that should depend on evidence about the model, not on assumptions.

5. Proposal: steps sized to the model

One system, with four parts:

  1. a small set of objective gates that decide promotion at every step size;
  2. calibration: measure each model against the scenario suite when it is set up;
  3. a step size chosen from that measurement;
  4. escalation and fall-back between step sizes within an attempt.

5A. Objective gates for every step size

These don't depend on the model at all, and they matter most when the model is weak. They are where effort on scoring should go.

The literal check and the time plausibility check overlap on purpose. The literal check reads the stylesheet, so it catches the constant before anything runs; the time check reads the output, so it also catches a year computed wrongly. The time check alone can't catch a time-zone error of a few hours, which is why the missing-year task also proposes a document- or feed-level time zone.

Gates run while serving, not only at promotion

Completeness and time plausibility must also judge every served stream, so that drift defers the stream and relearns rather than going unnoticed. That is fix 1 of shapeshifter-ai-parser-drift-not-detected.md, which the missing-year task's time check depends on to trigger relearning. When serving, the threshold should come from the document's existing yield or coverage setting rather than zero tolerance, so that one bad line in a noisy feed doesn't force a relearn.

The existing heuristic scorers (extraction quality, business rules, event classification) try to measure meaning with rules. That is where both the false confidence and the false failures come from. They should become advice shown to the model and to the reviewer, not gates that decide promotion.

Context, as well as checks

Some faults can't be fixed by any model, only prevented by giving it what it needs. Whatever the step size, the model should be shown the stream's received and effective times, be told about stroom:format-date, and know the time zone of zone-less timestamps where the feed states one (fixes 1, 2 and 4 of shapeshifter-ai-missing-year-hard-coded.md). It should also be told the target schema from the same single setting the schema gate uses (shapeshifter-ai-single-target-schema.md).

5B. Calibrate each model

The only honest measure of an unknown model is to run it against known inputs with known answers. Most of the pieces exist:

  • The scenario folder (stroom-shapeshifter-ai/src/testFixtures/resources/stroom/shapeshifter/ai/scenario) has inputs with hand-written reference events: syslog.log and syslog.events.xml, fixed-width.log and fixed-width.events.xml, windows-security.xml and windows-security.events.xml, auditd.log, CSV and JSON.
  • TestLiveScenarios already runs these scenarios against a real model endpoint, under the DIRECT, TARGET_FIRST or ESCALATING flow, and reports outcomes and cost. Its own description: "to learn what no script can say — whether the questions as put draw replies the grammar accepts, whether the feedback steers a second candidate to a passing one…".

The scenario references are written in event-logging. Once the target schema is a single setting (shapeshifter-ai-single-target-schema.md), calibration for another schema needs references written in it, or reports only the gates that don't need references.

Calibration makes this a feature of the model document. It runs when a model is set up or changed, probes the endpoint's capabilities, runs the suite at each step size, scores the results against the references, and records a recommended step size.

5D. Escalate and fall back

Within one attempt, the step size can move:

  • Fall back. If a larger step fails its gates after its candidates are spent, the attempt continues at the next smaller size, carrying the gate report as feedback. Example: a coarse candidate for csv-multiline parks because the parser cuts quoted newlines; the fine flow's SPLIT and on yield-short goto split are built for exactly that.
  • Hand on. If an installation has more than one model, a fine-step attempt that parks can be handed to a stronger model at a larger size. Example: GATEWAY-AUDIT parks on the split; a calibrated strong model writes a stylesheet that handles all nine record kinds under batch. (The "children of element" boundary proposed in shapeshifter-ai-mixed-record-elements.md would let fine steps learn it too.)

The existing ESCALATING flow already escalates within fine steps (direct first, then targets when the transform stays short). This extends the same idea across step sizes.

5E. Promotion and review

With an unknown model, meaning has to be checked by something other than the model. Two things do that:

  • Reference corpora. Approved events become references. Every relearn is run against them, so a fault found once stays found. The scenario *.events.xml files seed this; feeds without references (APACHE-ACCESS, NETFILTER, AUDITD-AUSEARCH) get them as people approve output.
  • A person approves, by default, until the model is calibrated and the feed has references. The review screen puts the gate results first and raw records beside their events, which is how the evaluation's reviewers found what the scorers missed.

The review evidence belongs on the pipeline's Learning Status tab, beside Approve and use it, and the advice could also sit on its Quality Assurance tab (see ui-design.md); neither should duplicate the other's parts (shapeshifter-ai-supervisor-visibility.md): the gate strip and the advice column come from the same server-side rule set as the findings proposed for the Learning Status tab (proposal 6, which already lists "dropped more than X% of records" and "events dated far from the stream's receipt time"), and the records-in and events-out counts are those of the proposed Streams tab (proposal 2).

Model review stays possible, as one more piece of advice, for installations whose model is calibrated as strong. It should run in a separate context and see raw records beside events, not the author's reasoning. It is never a gate.
