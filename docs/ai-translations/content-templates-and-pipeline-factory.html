Content Templates and the Pipeline Factory: one feature or two?

Branch ai_translations · 10 November 2026 · Compares Stroom's existing Content Templates with the Pipeline Factory added for AI translations, and sets out options for merging them. Some Stroom knowledge assumed; no Shapeshifter knowledge needed.

The short answer. They overlap heavily. At their core, both see a new feed and make a pipeline that inherits from a template pipeline, plus a processor filter for that feed. They differ in when they fire, what else they create, and how much can be configured. Neither knows the other exists: the Pipeline Factory's design document never mentions Content Templates.

Section 4 sets out four ways to end up with one feature, each with advantages, disadvantages and a worked example. Section 5 sets out the security implications, including with Shapeshifter AI. Section 6 recommends an option, section 7 sets out how to make it usable and visible, and section 8 lists the decisions needed.

1. The two features

Content Templates (core Stroom, in production)

Content Templates are part of data receipt (stroom-core, stroom.core.receive.ContentAutoCreationServiceImpl). When data arrives for a feed name that doesn't exist yet, Stroom matches the receipt's headers against an ordered list of templates. The first match decides what's created. Stroom then creates:

  • the feed itself, in a folder built from the headers (default Feeds/${accountid});
  • user groups and permissions (default grp-${accountid} under "Data Feed Reader", and grp-${accountid}-dev under "Data Feed Developer");
  • processing content, depending on the template's type:
    • INHERIT_PIPELINE: a new pipeline named after the feed that inherits from the template pipeline, plus a processor filter. It can also copy and re-map the template's XSLTs and text converters into a sub-folder.
    • PROCESSOR_FILTER: just a processor filter for the feed on an existing, shared pipeline.

The filter is always Feed = <feed> AND Type = <type>, with the template's priority and maximum concurrent tasks. Once the feed exists, the templates are never consulted for it again. The feature is configured as one global list on the Content Templates screen (it needs the Manage Content Templates permission), with the run-as user and folder patterns in the autoContentCreation application config. It's off by default.

The Pipeline Factory (this branch, new)

The Pipeline Factory is a new document type (PipelineFactoryDoc, module stroom-pipeline-factory). It's described in stroom-shapeshifter-ai/design/02-pipeline-factory.md as a general-purpose feature that "knows nothing of AI". A job runs every minute and scans the stream store. The first time it meets a new combination of key values (by default feed and type), it makes:

  • a folder, from a pattern (default Feeds/${feed});
  • a pipeline that inherits from the template, named from a pattern (default ${feed} ${type}), with per-pipeline property values written onto its elements;
  • a processor filter with the factory's full set of filter settings and its run-as user.

It remembers every combination it has met (PENDING, MADE or FAILED) and retries failures after 10 minutes. A new factory reads every stream already held, so it also covers feeds that already exist. It doesn't create feeds, groups or permissions.

For AI translations, the template's head is the Shapeshifter AI element. The factory writes the element's learnedFolder and learnedName properties so each feed's learned content sits beside its pipeline.

Two things called "pipeline factory". Stroom has long had stroom.pipeline.factory.PipelineFactory, which builds a running pipeline from its elements. It's unrelated. This note means the new document type, stroom.pipelinefactory, which has no dot between the words.

Different triggers and different extras, but the same core result. While both are on, a new feed that both match gets the core result twice.

3. Double processing

While both features are on, a new feed that matches a Content Template and a factory gets two pipelines and two filters, so its streams are processed twice. Neither checks for the other. Merging the features, or removing one, removes the problem, so this paper doesn't consider it further.

4. Options for one feature

Every option uses the same example. A Stroom installation has 300 existing feeds and wants AI translations on all of them. It also takes on a new customer, account 1234, whose first data arrives for an unknown feed, ACME-FIREWALL-EVENTS. That feed must be created with the account's usual groups and given an AI pipeline.

A. Content Templates absorb the Pipeline Factory

medium work no new feature for users

Keep Content Templates as the single feature, and give it what only the factory can do today:

  • a second trigger: a job that scans the stream store, so a template can also apply to existing feeds;
  • per-pipeline element property values from patterns;
  • a Pipeline key, for processed streams;
  • the full set of filter settings;
  • state and retries, through the factory's combination table, moved into stroom-core.

The scan uses the same first-match rule as receipt. Each stream the scan reads is matched against the whole ordered list of templates, and only the first template that matches can make anything for it. The scan doesn't run each template separately. The record of what's been made is kept per feed and type, not per template, so the same combination is only ever made once. Moving or changing a template later can't make a second pipeline for something already made. This removes a problem the Pipeline Factory has: each factory selects and remembers on its own, so two factories whose filters overlap each make a pipeline for the same feed.

The PipelineFactoryDoc type, its editor and its module are removed.

Example

Content Templates screen, one new row
#3  Expression:  Type = Raw Events
    Applies to:  new feeds at receipt  +  existing streams (scan)   ← new
    Type:        INHERIT_PIPELINE
    Pipeline:    AI supervised template
    Properties:  Shapeshifter AI.learnedFolder = Feeds/${feed}      ← new
                 Shapeshifter AI.learnedName   = ${feed} ${type} learned

ACME-FIREWALL-EVENTS arrives: the feed, the grp-1234 groups and its pipeline are created at receipt, as today. The new scan meets the 300 existing feeds. It matches each one against the list in order, so a feed that an earlier template matches is left to that template, and the rest get a pipeline from #3. A row in the combination table stops the scan making a second pipeline for ACME-FIREWALL-EVENTS.

Advantages

  • One feature, in the place administrators already look for it.
  • Builds on code that's in production, as AGENTS.md asks ("reuse existing project utilities first").
  • Feed creation, groups and processing content are set up in one place, so double processing can't happen.
  • One ordered list decides, for receipt and scan alike, so no two rules can both claim a feed.
  • No new document type to explain, export or migrate.

Disadvantages

  • Content Templates is a single global list: no per-template permissions, export or version history, and one global run-as user. The factory's document model is more flexible.
  • Two different triggers behind one row: "this template also scans history" is easy to switch on by accident, and on a large store it makes hundreds of pipelines.
  • Changes a production feature. Existing templates must keep working exactly as before, so every new field needs a safe default.
  • The factory's Made tab, tests and editor are rewritten, not reused.

B. The Pipeline Factory absorbs Content Templates

most work migrates production config

Make the factory document the single feature, and give it what only Content Templates can do today:

  • a receipt trigger that creates the feed, groups and permissions when unknown data arrives;
  • a filter-only mode on a shared pipeline;
  • copying the template's XSLTs and text converters.

Existing Content Templates are migrated into factory documents on upgrade, and the Content Templates screen is removed.

Example

Pipeline Factory document "Account feeds"
Trigger:          on receipt of an unknown feed        ← new
Create feed in:   Feeds/${accountid}                   ← new
Groups:           grp-${accountid}, grp-${accountid}-dev  ← new
Stream filter:    Type = Raw Events
Template:         AI supervised template
Name pattern:     ${feed} ${type}

Pipeline Factory document "Existing feeds"
Trigger:          scan the stream store
Stream filter:    Type = Raw Events AND Create Time < 2026-11-10

ACME-FIREWALL-EVENTS is created by "Account feeds" at receipt. "Existing feeds" covers the 300 feeds already held. Both are documents, so they can be exported to another environment, and each can be given its own permissions and run-as user.

Advantages

  • One modern design: documents, per-factory run-as users and permissions, state, retries and a Made tab.
  • Factories can be exported and imported between environments, which a global list can't.
  • The richest model for everyone, not just AI translations.

Disadvantages

  • The most work, and the most risk. A production feature is removed and its configuration migrated, which every installation using it must test.
  • Feed creation has to happen at receipt, before any stream exists. The factory would need a hook into the receipt path, which mixes a receive-time concern into a background job's design.
  • Adds new database tables to every installation, including ones that only used Content Templates.
  • Users must learn a new screen to do what they did before.

C. One maker, two triggers

medium work removes the duplication

Split along the line where the two already differ:

  • Content Templates keep feed onboarding, the receipt-time part: creating the feed, its folder, groups and permissions.
  • The Pipeline Factory owns making processing content: pipelines, property values, filters, state and retries.

A Content Template gains a third type, PIPELINE_FACTORY, which names a factory. When the template creates a feed, it hands the feed straight to that factory's maker, so its pipeline appears at receipt rather than a minute later. The factory's combination table records it, so the scan never makes a second one. INHERIT_PIPELINE and PROCESSOR_FILTER keep working unchanged and can be retired later.

Example

Content Templates screen
#3  Expression:  AccountId = 1234
    Type:        PIPELINE_FACTORY                     ← new
    Factory:     AI feeds

Pipeline Factory document "AI feeds"
Stream filter:   Type = Raw Events
Template:        AI supervised template
Properties:      Shapeshifter AI.learnedFolder = Feeds/${feed}

ACME-FIREWALL-EVENTS arrives: template #3 creates the feed and the grp-1234 groups, then asks "AI feeds" to make its pipeline at once. The factory's scan covers the 300 existing feeds and skips ACME-FIREWALL-EVENTS, because it has already met it.

Advantages

  • Each part does one job. "Who creates the feed" and "who makes its processing" have one answer each.
  • Only one piece of code makes pipelines and filters, so double processing can't happen by construction.
  • Existing Content Templates keep working with no migration, and installations that don't use factories see no change.
  • The factory's state, retries and Made tab cover feeds whichever way they arrived.

Disadvantages

  • Two screens remain, and people have to understand how they connect.
  • Until INHERIT_PIPELINE is retired, there are still two ways to make a pipeline from a template, and the guard from option D is still needed for them.
  • stroom-core (receipt) gains a dependency on the factory's maker. It needs a small API in stroom-pipeline-factory to keep the layering clean.

D. Keep both, with a guard and documentation

ruled out

Keep both features, with a guard so neither makes a pipeline for a feed the other has covered, and documentation saying when to use each. It's the least work, but two features doing the same core job would remain, so it doesn't meet the aim of ending with one.

5. Security implications

This section looks at the security of each feature, alone and with Shapeshifter AI, and then at what that means for options A, B and C. Option D is left out because the features are to be merged, or one removed. Everything here comes from reading the code and the design documents in stroom-shapeshifter-ai/design/. Unless it says otherwise, nothing has been reproduced on a running Stroom.

The short answer. Two problems come with whichever route is chosen. They come from the AI, not from either feature. Three more depend on the route, and they make B the riskiest, C acceptable once one gap is closed, and A the safest.

What was found

  1. Pipeline Factory Anyone who can edit a factory can choose any run-as user. PipelineMaker.make switches to the factory's run-as user before anything else happens (PipelineMaker.java:112). ProcessorFilterServiceImpl.checkRunAs normally checks that the person creating a filter may choose its run-as user (ProcessorFilterServiceImpl.java:270). Here it runs as the run-as user, so it always passes. Saving and importing a factory check only problems() (PipelineFactoryStoreImpl.writeDocument, importDocument).

    So anyone who can create, edit or import a factory can name an administrator. Within a minute the factory makes folders and pipelines as that administrator, and processor filters that run as them for good. CombinationScanner also reads the stream store as that user, so the factory meets feeds its author can't see. Content Templates don't have this problem: their run-as user is createAsSubjectId in the application config, which only an administrator can set.

  2. Content Templates with AI Anyone who can send data can start the AI on it. A Content Template fires on data for a feed name Stroom doesn't know. The sender chooses the feed name and the headers that templates match. If a template makes an AI pipeline, anyone who can send data can, without any person approving it:

    • send data to the model. Samples aren't redacted (ruling A146). A146 relies on "a feed is pointed at a model only where its data may go to that model", but an automatic template makes that choice for a feed nobody has looked at yet;
    • run up model costs. Each new feed name starts learning. The spend breaker across sessions is designed but not built (10-status-and-future.md §10.3), so sending lots of feed names is a cheap way to burn tokens;
    • get model-written XSLT run on the node. The sender writes exactly the text the model reads, so prompt injection can steer the stylesheet it writes. The static check on model-written stylesheets (A147, ISSUES 21) isn't built. On a node, candidates run in the real XSLTFilter, which isn't sandboxed:
      • stroom:http-call, fetch-json and document() over http make requests from the node (server-side request forgery);
      • unparsed-text() and uri-collection() read the host's filesystem;
      • xsl:result-document writes files on the host. This was confirmed on a development machine.
      So the chain runs from a network sender, through crafted data and a model-written stylesheet, to reading and writing files on the Stroom host.

    Stroom's own documentation already warns about the first step. guides/sending-data/choosing-a-feed.md says feed cardinality is uncapped: with auto-creation on, a sender that derives Feed from a pod name or hostname makes one feed per distinct value, "an estate that nobody can administer". With AI, each of those feeds is also a learner spending on the model.

  3. Pipeline Factory with AI A new factory sends existing data to the model. A new factory reads every stream from id 0. In section 4's example, one factory with Type = Raw Events puts the data of 300 existing feeds, history included, through the model at once. None of those feeds was approved for AI under A146. Content Templates can't do this because they only fire for new feeds.

  4. Pipeline Factory with AI Factory names and folders aren't cleaned. Content Templates clean every value they substitute (cleanTemplateVariable, cleanGroupString, ContentAutoCreationServiceImpl.java:208-231). PipelineFactoryKey.substitute cleans nothing, and PipelineMaker.folderOf splits on /. Feed and type values are limited by the feed name pattern and the list of stream types. A ${pipeline} value, though, is a pipeline's name, which can contain anything. The learnedFolder and learnedName values the factory writes are used later by learning. Learning runs as the internal processing user (DeferredLearning, PipelinePlaces), so learned XSLTs and text converters can be written to any folder, without the permission checks the run-as user would face.

  5. Pipeline Factory Customer data can be seen across accounts. Content Templates set up access per account: grp-${accountid} gets View on the folder, the feed and the pipeline. The factory creates no groups, and what it makes takes its folder's permissions. With the default Feeds/${feed}, every customer's AI pipeline and learned content takes whatever permissions apply at Feeds. Learned XSLTs can contain literal values copied from customer samples.

Needed whichever route is chosen

Every route ends with both triggers, receipt and scan, so findings 2 and 3 come with all of them. They come from the AI, not from either feature. They need:

  • A147 built before any AI pipeline is made automatically. It is the only thing between an outside sender and model-written code running on the host.
  • AI switched on by a person, per feed. A feed made automatically gets its pipeline with learning disabled, or in review mode, until a person who has decided the data may go to the model switches it on. This is what A146 already assumes.
  • No scan from stream 0 for AI: a template or factory whose template has the AI element at its head must have a minimum stream creation time.
  • The spend breaker (A24, A44) built before receipt can start learning, so a flood of new feed names is limited across sessions, not just within each one.
  • Learned content kept in the pipeline's own folder: learnedFolder limited to the made pipeline's folder or below, whatever pattern produced it.

Security verdict: A is the safest, C is acceptable once finding 1 is fixed, and B is the riskiest.

  • A keeps the privileged choices with administrators, and its cleaning and per-account permissions are already in production. The price is that access can't be delegated: anyone allowed to manage templates manages all of them.
  • C is safe if the factory's run-as user is checked, as the person saving or importing it, with the same rule processor filters use. Values substituted in the maker must be cleaned the same way Content Templates clean them, and the template must grant its account groups access to what the factory makes. Handing a feed from template to factory must not let the factory act with the template's identity.
  • B puts feed creation, group creation and permission grants behind a document whose run-as user an author chooses, and that can arrive from another environment by import. It needs every control C needs, and more, around the most powerful thing either feature does.

If one feature is to be removed outright, with nothing absorbed, removing the Pipeline Factory removes findings 1, 4 and 5 completely, but then nothing covers existing feeds. Removing Content Templates leaves the factory's findings and removes receipt-time onboarding, which production installations use.

6. Recommendation

The two features are to become one, so the choice is between A and C. B is ruled out: it is the most work, migrates production configuration, and section 5 shows it carries the most security risk. Keeping both (D) is ruled out because two features would remain.

Recommendation: A. Content Templates absorb the Pipeline Factory.

  • It is the only route that gets to one feature directly. C gets there only once INHERIT_PIPELINE and PROCESSOR_FILTER are retired. That is a migration of production configuration, the same cost that rules out B, only later.
  • It is the safest. The identity that makes content stays an administrator's choice. The value cleaning and per-account groups that the factory would have to rebuild are already in production.
  • Nobody's configuration is migrated. The Pipeline Factory hasn't been released, so removing it costs no installation anything. Its migration scripts can be deleted from the branch rather than undone by new ones.
  • It reuses what's there, as AGENTS.md asks.

Why one decider, not several

Several rules are fine. The trouble comes from several independent deciders, each picking its own data and keeping its own record of what it has made. The Pipeline Factory works this way: every factory has its own scan position and its own list of combinations met, and nothing compares one factory's choices with another's. With two or more deciders:

  • Overlap goes unnoticed. A feed two deciders match gets two pipelines. With Shapeshifter AI that also means two learners, twice the model spend, and two sets of AI-written stylesheets.
  • There's no clear owner. "Why does this feed have this pipeline, and what changes it?" has more than one answer, which makes it hard to audit or to switch off cleanly.
  • Changes give different results depending on order. Widening one decider's filter, or adding a new one, can claim feeds another has already handled. The outcome depends on what was scanned when.
  • Security gets wider. Each decider is another way to make content as a privileged user, and another thing to lock down (section 5, finding 1).

One ordered list, where the first match wins, and one record of what's been made, kept per feed and type, avoid all of this by design. A gives exactly that, for receipt and scan alike.

One gap remains: content made by hand. Even with a single decider, the scan could give a pipeline to a feed someone has already set up manually. Checking whether the feed "already has a filter" is too blunt, because a feed with a filter for something else, such as indexing, would wrongly be skipped. The rule needs to be precise, for example skipping only a feed that already has a translation filter for that type (decision 6).

Settings move from system properties to the templates

Today most of the feature is configured in the autoContentCreation system properties (docs/reference/docs/reference/configuration-properties.md), not on the Content Templates screen. That splits one feature across two places with two permissions, Manage Properties and Manage Content Templates. It hides settings that decide what a template does from the person editing it, and it forces every template to share one folder layout, one set of groups and one run-as user. A scan-only template that adds AI to existing feeds has no use for account groups, but today it would get them.

On upgrade, each existing template takes the current property values, so nothing changes until someone edits it, and the properties are then deprecated. The preview, the checks as people type and the "made by" link (section 7) can only cover settings the template holds, which is a further reason for the move.

The run-as user moves with care. A run-as user on each template brings back finding 1 from section 5 unless it's checked. Saving or importing a template must check, as the person saving it, that they may use that run-as user, by the same rule processor filters use.

What A costs, and how to contain it

  • No delegation. Whoever holds Manage Content Templates manages every template. Moving the run-as user onto each template (above) narrows what each template can do, but not who can edit it. That's acceptable while automatic onboarding stays an administrator's job. If teams later need to own their own rules, that is the time to reconsider C.
  • The scan can be switched on by accident. The scan should be a separate, explicit setting on each template, off by default. It should need a minimum stream creation time when the template's pipeline has the AI element at its head, so no template sends history to the model without a person choosing a date.
  • A production feature changes. Every new field defaults to today's behaviour, and the existing tests for ContentAutoCreationServiceImpl must pass unchanged before any new tests are added.
  • The default run-as user is the Administrators group. createAsSubjectId defaults to Administrators, with createAsType = GROUP, so by default everything a template makes, including the scan's pipelines and filters, is made as Administrators and runs as Administrators. Section 5 calls A the safest route because an administrator chooses this identity, but the default choice is the most powerful one there is. The default should become a dedicated group with only the permissions templates need: creating feeds, folders, pipelines and processor filters in the template folders, and reading the template pipelines.
  • The factory's work is rewritten, not reused. Its maker, combination table and Made tab can move across largely as they are. The document editor is what's lost.

Order of work

  1. The controls section 5 needs on any route: the A147 stylesheet check, AI pipelines created with learning disabled until a person switches it on for the feed, and the spend breaker. These come first, because they are what make automatic AI onboarding safe at all.
  2. Settings move to the templates: the autoContentCreation properties move as in the table above, with the run-as check on save and import, and a dedicated group replacing Administrators as the default.
  3. Per-pipeline element property values on templates, substituted with the existing cleaners, with learnedFolder kept inside the made pipeline's folder.
  4. The full set of filter settings on templates.
  5. State and retries: the combination table moves to the receipt module's database, and the Made view moves to the Content Templates screen.
  6. The scan trigger, off by default, with the minimum creation time rule above, as the template's run-as user. It matches each stream against the whole ordered list, first match wins, and records what it makes per feed and type.
  7. Remove PipelineFactoryDoc, its editor, the stroom-pipeline-factory module and its tables, and update the Shapeshifter AI design documents (02-pipeline-factory.md and rulings A122 and A123) to match.
  8. Document it. The reference docs mention Content Templates in only four places, each a line or two: the Administration menu list (concepts/user-interface/_index.md), one bullet in concepts/data-receipt.md, a warning in guides/sending-data/choosing-a-feed.md, and the properties table. There's no page that explains the feature. Once it is central, it needs one: first-match order, the two triggers, run-as users, AI approval, and what each status and problem on the screen means. The properties table also has an out-of-date entry: the enabled description refers to a templatesPath property that doesn't exist.

Choose C instead if the team needs onboarding rules owned by different teams, or moved between environments as documents. In that case, fix finding 1 (the run-as user) and finding 4 (cleaning) before anything else, and plan from the start to retire INHERIT_PIPELINE and PROCESSOR_FILTER, so the product does end with one feature.

7. Making it usable and visible

Option A puts a powerful automatic feature in front of administrators: one rule can make hundreds of pipelines, and with Shapeshifter AI, send data to a model. This section sets out how to make sure the feature is easy to use, that people can see what it's doing, and that they know when something is wrong and how to fix it.

These four aims match root causes already listed in docs/ui-self-explaining-assessment.html: invisible state, silent failure, background work with no progress, and manual recovery. Today the merged feature would hit all of them. A Content Template that fails at receipt, for example, writes the error only to the server log, and the sender gets the error back (ContentAutoCreationServiceImpl.java:267). Nobody looking at Stroom's screens sees it.

If only two things are built, build these. A preview of what a template will do, and a "made by" link on everything it makes. The preview answers "what will this do?" before anything happens, and the link answers "why is this here?" afterwards. Most support questions about automatic features are one of those two.

Easy to use

  • Start from what the user wants to do. "New template" offers two choices: Onboard new feeds for an account and Add a pipeline to feeds already held. Each fills in sensible defaults, with the scan off and AI learning off.
  • Pick tokens from a list instead of typing them. ${feed}, ${accountid} and the rest are chosen from a list, so a mistyped token can't be saved.
  • Check as people type, not on save. Each problem is shown beside its field, with the reason. Examples: an unknown token, an AI template with no minimum creation time, or a run-as user who can't use the template pipeline.
  • Preview before saving or enabling. For example: "This template would match 37 existing feeds; 3 of them are claimed by template #1, which comes first; it would make these folders and names." This makes both the scan and the first-match rule safe and easy to follow.

See exactly what's going on

  • Each template row shows its status: how many feeds it has matched, made, failed or is still waiting on, when the scan last ran, and how far behind the newest stream it is.
  • Each made thing explains itself. The feed and the made pipeline show "Made by template #3 'AI feeds', at receipt, 10 Nov 2026, as user X", with a link to the template. The factory already writes "Made by Pipeline Factory …" into the pipeline's description; this turns that into a link.
  • A "Which template matches?" tester. Pick a feed, or type in some headers, and see each template checked in order, with the reason each one matched or didn't. First-match only feels natural if people can see the order working.
  • Every feed shows its AI state (waiting for approval, learning, serving, raised), with a link to its pipeline's Learning Status tab, as Monitoring > Smart Pipelines lists them.
  • A history of every creation, kept in Stroom. Whether it happened at receipt or in a scan, it's recorded in a list people can view, not only in the log.

Know when something is wrong

  • Failures on the screen. A failed count on the template row and on the Content Templates tab, and a status on the affected feed itself. Receipt-time failures are recorded, not just logged.
  • Problems that aren't errors. Silence is the hardest case. The screen flags:
    • a template that has never matched anything;
    • a template that never gets a feed, because an earlier one always matches first;
    • a deleted template pipeline;
    • a run-as user who has lost permissions;
    • a scan that's falling behind;
    • a feed waiting days for AI approval;
    • feed names that arrived and matched no template.
  • A flood of new feed names. An alert when the number of new feeds created, or of feed names that matched no template, jumps above normal. This is the pattern choosing-a-feed.md warns about: a sender deriving feed names from hostnames or pod names. It should show before it becomes thousands of feeds, and with AI, thousands of learners.
  • Warnings before something breaks. For example, deleting a pipeline that templates use warns "used by templates #3 and #5".

Know how to fix it

  • Each problem says its cause and offers the fix as a button: Retry now, Open template pipeline, Approve AI for this feed, Forget, so the scan makes it again, or Move this template above #1.
  • Show what a fix will do before it runs. For example, Forget says "a new pipeline will be made on the next scan; the old one is not deleted". The same preview used when editing also covers fixes that change templates.
  • Failure reasons in a few plain categories, such as permission, missing template, bad pattern or missing element, each with a link to help. PipelineMaker already words its errors in the user's terms, which is a good base.
  • A workbench story for every state, as stroom-gwt/UI-GUIDE.md asks: an empty list, a template that's never first, failures, waiting for approval and a scan falling behind. The "something's wrong" screens are then designed and tested too, not only the screens for when things work.
