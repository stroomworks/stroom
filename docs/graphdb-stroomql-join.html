Joining Graph DB results into StroomQL

A feasibility & design study: can a StroomQL query join in the results of a Cypher graph traversal — and what would it take?
Status: Design proposal / feasibility study
Audience: Stroom engineering, and analysts who write the queries
Scope: Bringing graph (Cypher) results into a StroomQL join — the syntax, what is already reusable, worked examples, how it compares to other graph databases, and a risk profile. Extends the temporal-graph and query-optimiser design series.
Verdict: not today — a bounded increment Execution plumbing: already source-independent Missing piece: a language/compile surface
One-paragraph answer. Not today — there is no way to name a Cypher/graph query as one side of a StroomQL join, and Cypher has no JOIN to pull StroomQL rows the other way. But this is a missing language surface, not missing machinery: StroomQL and Cypher already compile to the same logical plan, produce the same Val[] row model, and the join executor already fans each side out to a SearchProvider chosen purely by data-source type — and the graph engine is already a registered provider. So the work is concentrated at the grammar/compile layer, and the execution path is largely reuse.

1. Executive summary

Analysts increasingly want to combine two kinds of data that live in different Stroom engines: high-volume event/index data (queried with StroomQL) and relationship data (queried with Cypher against a Graph DB — see the companion temporal-cypher-graph design). The natural ask is: "filter/enrich my events using something I can only compute by traversing the graph."

That query cannot be written today. StroomQL's join can combine two datasources, but each side is compiled as a StroomQL sub-query over a named source — there is no syntax to make a side a Cypher traversal, and a Graph DB advertises no StroomQL-style columns to join on.

The recommended direction is a Cypher sub-query as a join side: let a bracketed sub-query on the right of a join route to the Cypher grammar (reusing the proposed from "GraphDb" routing), and let its RETURN … AS col list declare the columns the join binds on. Everything below that — dispatching the side to the graph engine, reading its rows, hash-joining them to the event stream, spilling, guardrails, coprocessors, the dashboard — is already built and already type-agnostic. The risk is concentrated at the language/compile layer and in one semantic contract (deriving a column schema from a schemaless graph's projection); the execution layer is reuse.

2. The gap today

Here is roughly what an analyst would want to write, and why each part fails on the current build:

from "AuthEvents" as e
inner join ( /* a Cypher traversal */ ) as g on e.user = g.userId
select e.time, e.user, g.riskBand

StroomQL does have a real, shipped join — LEFT/INNER, equi-join only, expressed in the grammar as from <source> [join <source> on a.f = b.f]… (StroomQL.g4, fromClause/joinClause). Three concrete things block a graph side:

  1. No syntax to attach Cypher to a join side. A join source in the grammar is a bare datasource name (nameToken), never a sub-query. And the compiler lowers each side into a synthesised StroomQL sub-query — literally from "<name>" select <fields> — in compileJoinSide (OptimisingQueryCompiler.java). There is nowhere to carry Cypher text. Worse, createJoin currently accepts only a single join, two sources, each a plain (optionally filtered) datasource Scan — "both sides must be plain datasource scans". A Cypher traversal is not a plain Scan.
  2. A Graph DB advertises no StroomQL field schema. The join binder resolves each alias.field against the source's declared fields. But GraphSearchProvider returns an empty field list, getFieldCount → 0, and getIndexField → null (GraphSearchProvider.java) — a node/edge has no fixed columns until a query's RETURN projects them. So there is nothing for g.userId to bind to.
  3. The engines are wired apart at execution. A Graph DB query rides the wire as raw Cypher on a GraphSpec; GraphSearchProvider.createResultStore throws if a request routed to it carries no GraphSpec. A StroomQL-compiled side carries none. And Cypher itself has no JOIN / multi-MATCH / WITH-chaining, so the reverse direction (StroomQL rows into a Cypher query) is absent too.
The shape of the gap. All three blockers sit at the front / compile layer — grammar, binder, and the join compiler's shape checks. None of them is in the execution layer, which (next section) is already agnostic to where a join side's rows come from.

3. Why the plumbing is already source-independent

The query stack was deliberately built so that a new front-end (Cypher) and a new datasource (Graph DB) slot into the same core the relational side uses. Three shipped facts do the heavy lifting:

  • One logical plan. Cypher compiles into the same LogicalPlan IR as StroomQL (CypherToLogicalPlan.java) — "a second front-end onto one IR, not a forked engine." The IR is a single sealed interface permitting both relational nodes (Scan, Filter, Join, Aggregate, …) and graph nodes (NodeScan, Expand, VarLengthExpand).
  • One row model. The graph engine emits ordinary Val[] rows into the same coprocessor / result-store pipeline as every other source — the row-assembly contract is literally shared with the join provider.
  • Type-driven provider dispatch. The join executor opens each side through JoinSearchProvider.openSide, which resolves a provider purely by DocRef.getType() via the SearchProviderRegistry and then reads Val[] (JoinSearchProvider.java). GraphSearchProvider is already registered for type GraphDb. The general streaming hash-join only ever sees Val[].
The consequence. Because openSide already routes by type and reads Val[], a Graph DB side would be "just another provider" to the executor — no new join algorithm, no new result plumbing. This is what turns "join graph results into StroomQL" from a rewrite into a bounded, front-loaded increment.

4. Proposed syntax

The cleanest fit reuses two things already on the table: the proposed portable from "GraphDb" routing prefix (cypher-from-clause-implementation-plan, which lets a chunk of Cypher name its own Graph DB and route to the Cypher grammar), and the join side abstraction. A graph side becomes a bracketed sub-query whose body is Cypher:

from "AuthEvents" as e
inner join (
    from "IdentityGraph"                              -- routes this side to Cypher
    match (u:User)-[:MEMBER_OF]->(g:Group)
    return u.id as userId, g.name as groupName    -- declares the side's columns
) as ident on e.user = ident.userId
select e.time, e.user, ident.groupName

Two design points make this work against the three blockers in §2:

  • The bracketed side carries a GraphSpec. Instead of synthesising a StroomQL select * for the side (blocker 1/3), the compiler emits a sub-SearchRequest targeting the Graph DB with the Cypher text on a GraphSpec — exactly what GraphSearchProvider already expects. Dispatch then works unchanged: the side's DocRef is type GraphDb, so openSide routes it to the graph engine.
  • The RETURN … AS col list is the side's schema. This resolves blocker 2: rather than asking the (schemaless) Graph DB for field metadata, the join binder reads the projected column names — and, where inferable, their types — straight from the sub-query's RETURN list. ident.userId and ident.groupName bind to those projected columns.

v1 shape (kept deliberately narrow): equi-join only (matching today's on a.f = b.f), a single graph side, and the graph side evaluated wholesale then hash-joined — not a per-row correlated lookup (that "broadcast lookup" optimisation is reserved for keyed State/Plan B stores today and is future work for graphs). Both inner and left are natural; left keeps every event row and null-pads the graph columns when there is no match.

Why a sub-query rather than a bare name. A plain join "IdentityGraph" can't say which traversal to run or which columns come back — a graph has no default tabular shape. The bracketed Cypher supplies both the computation and the schema in one place, which is precisely the two things the join needs and the Graph DB can't otherwise provide.

5. Worked examples

5.1 Reachability filter (INNER join, temporal + variable-length)

Question: "Show network events whose destination host was reachable within three hops of the known-compromised host, as the network looked at 09:00 on 1 July."

from "NetworkEvents" as e
inner join (
    from "HostGraph"
    match (seed:Host {id: 'compromised-1'})-[:CONNECTED_TO*1..3]->(h:Host)
    as of datetime('2026-07-01T09:00:00Z')
    return distinct h.id as hostId
) as reach on e.dstHost = reach.hostId
select e.time, e.srcHost, e.dstHost
order by e.time

The graph side runs a temporal, variable-length traversal and returns a one-column set of reachable host ids; the event stream is narrowed (INNER) to just those hosts. What comes back is an ordinary events table:

timesrcHostdstHost
2026-07-01T09:04:12Z10.0.0.710.0.3.19
2026-07-01T09:07:55Z10.0.3.1910.0.4.2
………

The traversal (var-length hops, AS OF floor lookups) happens entirely inside the graph engine; StroomQL only ever sees the projected hostId column as Val[] rows to join on.

5.2 Enrichment (LEFT join, null-padding)

Question: "List all transactions, and where the account is flagged by a fraud rule in the graph, show which rule."

from "Transactions" as t
left join (
    from "FraudGraph"
    match (a:Account)-[:FLAGGED_BY]->(r:Rule)
    return a.number as acct, r.name as rule
) as flag on t.account = flag.acct
select t.time, t.account, t.amount, flag.rule
timeaccountamountrule
2026-07-20T14:01Zacct-118250.00velocity-spike
2026-07-20T14:02Zacct-20419.99(null)
2026-07-20T14:05Zacct-118800.00velocity-spike

The LEFT join keeps every transaction; flag.rule is null where the account isn't flagged — the same SQL null semantics the join executor already implements (a null key never matches; the row is emitted null-padded for LEFT).

6. What's reused vs. built new

Reused (already shipped)Built new (focused surface)
The shared LogicalPlan IR (both front-ends already compile to it). Grammar + binder support for a sub-query as a join side (today a side is a bare nameToken; createJoin demands a plain Scan per side).
The universal Val[] row model + coprocessor / result-store pipeline. Emitting a join side's sub-SearchRequest with a GraphSpec (Cypher text) instead of synthesising a StroomQL select * in compileJoinSide.
SearchProviderRegistry / getSearchProvider — dispatch by DocRef.getType(). Deriving the join side's column schema from the Cypher RETURN … AS projection (so alias.field binds without the Graph DB advertising fields).
JoinSearchProvider — openSide, streaming hash-join, spill-to-disk, guardrails, cross-side where. The from "GraphDb" routing prefix that lets the bracketed side select the Cypher grammar (a proposal today — see cypher-from-clause plan).
GraphSearchProvider + GraphTraversalEngine — Cypher execution over Plan B, already producing Val[]. (Optional) wiring the existing GraphStoreStats port into the join cost model so a graph side has a cardinality signal for build-side / algorithm choice.

The pattern to notice: the right-hand column is almost entirely compile-time work. The one runtime concern — feeding graph rows through the join — is already handled by the left column.

7. How this differs from other graph databases

Most graph databases keep the graph in its own engine and make you leave the query to combine it with anything else. Stroom's angle is different because the combining happens inside one shared query core.

SystemHow you'd combine graph results with other data
Neo4j (Cypher) Cypher's CALL { … } composes graph sub-queries with graph; combining with a relational/search store is an out-of-query step — Fabric (federation across Neo4j databases), APOC procedures (e.g. pulling from JDBC), or ETL. There is no single planner that joins a Cypher result to an external full-text index.
TigerGraph (GSQL) Traversal + accumulators in a dedicated engine; mixing in external tabular/search data means connectors or an export/load step, not one federated query.
SQL/PGQ (SQL:2023) & Oracle PGQL The closest analogue: GRAPH_TABLE(… MATCH …) exposes a graph pattern as a table you can join in SQL. But that graph is a view over relational tables in the same engine — graph-over-tables — not a dedicated adjacency/traversal engine federated with a separate search index.
Stroom (proposed) Two genuinely different physical engines — a Lucene/searchable index, a Plan B state store, and an LMDB-backed adjacency graph — are unified by one logical plan and one row model, with join sides dispatched by datasource type. A cross-engine join is therefore a composition of existing providers, not ETL or a bolt-on federation layer.

Two things fall out of that design that are unusual:

  • "A hop is a join" already. Inside the graph engine, a Cypher hop lowers to a join over adjacency on the same IR. Making a graph result a StroomQL join operand is the same idea one level up — join composition is the native currency, not a special case.
  • The graph side is temporal. Because the Graph DB supports AS OF / AROUND / BETWEEN (see temporal-cypher-features), a StroomQL join can correlate a live event stream against the graph as it existed at a chosen instant — a point-in-time enrichment that graph-over-tables systems don't offer natively.

8. Relationship to the temporal work

This feature sits directly on top of the temporal-graph series. The graph side of a join can carry any of the temporal clauses, so the join answers questions like "score today's events against the ownership graph as it was at the time of each shift change." That raises one genuine design question — temporal alignment:

  • Explicit instant (v1). The AS OF t lives inside the bracketed Cypher, so the graph side is evaluated once at a fixed instant and hash-joined. Simple, predictable, and it fits the wholesale-evaluation model in §4.
  • Aligned to the event's time (future). "As the graph was at each event's timestamp" is a correlated, per-row point-in-time lookup — powerful, but it needs the broadcast-lookup path (today reserved for keyed State/Plan B stores) taught to do a temporal graph lookup. Out of scope for v1; noted so the syntax doesn't foreclose it.

9. Risk profile

The engineering is moderate and front-loaded: the execution path is reuse, so the risk lives at the language/compile boundary and in one semantic contract. Ranked most-significant first.

RiskSeverityWhy it mattersMitigation
Column schema from a schemaless graph Medium-High The join binds alias.field at compile time, but a Graph DB advertises no fields. The whole feature rests on deriving the side's columns (and, ideally, types) from the Cypher RETURN … AS list. Make the RETURN projection the authoritative schema for a graph join side; require explicit AS aliases; infer types where the projection allows and treat unknowns conservatively. Land this as its own testable contract.
Grammar / compile surface Medium Sub-query-as-join-side + embedded Cypher touches the StroomQL grammar, the binder, and createJoin — which today insists each side is a plain Scan. Model the graph side as a first-class sub-query join operand (not a Scan); reuse the from "GraphDb" routing to select the Cypher grammar for the bracketed body; keep v1 to a single graph side.
Unbounded graph side Medium A traversal can emit a large result that becomes a join build/probe input; the graph engine is single-shard and in-memory today. Reuse the existing join guardrails and spill; encourage a bounded/selective RETURN; where the equi-key is a graph property, consider pushing it into the traversal's WHERE.
Cost model blind to the graph Low-Medium The GraphStoreStats port exists but isn't wired into the join cost model, so a graph side has no cardinality signal — build-side / algorithm choice falls back to defaults. Wire the graph stats adapter into the cost model; until then, default the graph side to the build side or rely on the streaming hash-join's runtime side selection.
Semantic edges Low-Medium Temporal alignment (§8), LEFT/null semantics, and the fact that arbitrary StroomQL predicates can't be pushed into a Cypher traversal. Restrict v1 to equi-join on projected columns with an explicit AS OF in the graph side; document the sharp edges; defer correlated/temporal-aligned lookups.
Overall: a moderate, front-loaded feature. The load-bearing piece is the schema-from-projection contract; get that right and the rest is grammar plumbing over an execution path that already exists. There is no new join algorithm, no new result plumbing, and no new storage engine.

10. Non-goals (v1)

  • No reverse direction. Pulling StroomQL rows into a Cypher query (Cypher has no JOIN/multi-MATCH) is a separate feature.
  • No N-way graph joins. The compiler supports a single two-source join today; a graph side inherits that limit.
  • No correlated / per-row graph lookup. The graph side is evaluated wholesale and hash-joined; the broadcast-lookup fast path stays reserved for keyed State/Plan B stores.
  • No predicate push-down from StroomQL into the traversal beyond what the analyst writes in the Cypher WHERE/RETURN themselves.
  • Not the graph visualisation. This is about tabular join results; rendering the joined graph is separate UI work.

11. Open questions

  • Schema inference rules. Exactly how are column names and types derived from RETURN — are AS aliases mandatory, how are expression/aggregate projections typed, and what happens for a bare RETURN n (whole node) that has no scalar shape?
  • Temporal alignment default. If the graph side omits AS OF, does it mean "latest", or should the join default it to the event side's time window? (§8.)
  • Guardrail interaction with the single-shard engine. What is a safe ceiling for a graph side's result as a join input, and how should it degrade — truncate-with-warning, or require a bounded RETURN?
  • Which side may be the graph. Restrict the graph to the build (right) side for v1, or allow either? This interacts with the cost-model wiring above.
  • Name disambiguation. The bracketed side names its own source; how do we surface the existing "multiple data sources found" ambiguity when a Graph DB and an index share a name (the same issue the from "GraphDb" plan raises)?

12. The reverse direction (StroomQL → Cypher)

Everything above is graph-into-StroomQL: a StroomQL query consuming graph rows. The mirror image — feeding StroomQL rows into a Cypher query (say, using a set of event-derived values as the seed/anchors of a traversal, or joining a graph pattern to an external table from inside Cypher) — is a genuinely separate, and larger, feature. Three reasons it does not come for free:

  1. Cypher has no clause to accept external rows. The engine compiles only the narrowest reading shape: a single MATCH. WITH-chaining and multiple MATCH clauses are explicitly rejected at compile time (CypherToLogicalPlan: "not in PoC subset: exactly one MATCH clause is supported"). There is no UNWIND-of-external-rows and no relational-input operator, so there is nowhere for inbound rows to enter the query.
  2. The wire model has no slot for an inbound side. A graph query rides the wire as a GraphSpec that carries only raw Cypher text — no sub-SearchRequests. Contrast JoinSpec, whose two sides are fully-compiled SearchRequests. That asymmetry is exactly why graph-into-StroomQL is easy (the graph side is just another SearchRequest) and the reverse is not (a graph query has no place to attach a StroomQL side).
  3. The execution model is different. Graph-into-StroomQL works because the graph is just another provider emitting Val[] into the existing join executor — provider composition. The reverse would need the bespoke GraphTraversalEngine (anchor-scan → expand over Plan B) to consume rows mid-traversal — a correlated injection of external values into the anchor scan, which is a different kind of integration entirely.

What it would actually take is one of: (a) a Cypher parameter/seed-binding mechanism that feeds a set of StroomQL-derived values into the anchor scan (a correlated drive), or (b) a relational-input node on the shared IR that a graph plan joins against — executed by the join core rather than the traversal engine.

Why it's lower priority than it looks. Much of the reverse direction's value is already reachable from the other side. An inner join of a graph side into StroomQL (§5.1) acts as a semi-join — it filters the event stream down to what the traversal returned — and any selective condition on graph properties can live in the traversal's own WHERE/RETURN. So "start from events, use the graph to narrow them" is expressible today via graph-into-StroomQL; the truly reverse cases (external rows driving a traversal) are the residue that needs (a) or (b).

This document is a design proposal, not a commitment. It describes a feasible increment on top of already-shipped foundations (the shared logical plan, the Val[] row model, type-driven provider dispatch, and the Graph DB engine); the schema-from-projection contract in §9 is the piece to prototype first, before any grammar work.
