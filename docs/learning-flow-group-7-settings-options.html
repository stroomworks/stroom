Shapeshifter AI: where the target schema and the time zone are set

Decisions D1 and N6 · 19 November 2026 · branch ai_translations_server · Companion to the delivery plan, group 7. The mockups are sketches of the final UI (ui-design.md) with each option's fields added; they show layout and wording, not exact styling.

What is being decided. Two settings that don't exist yet. D1: where the one target-schema setting lives, now that every target schema must be usable (D2 option G). N6: where the time zone of timestamps that carry no offset comes from, so local times stop being written as UTC.

Why together. Both are new fields that most naturally sit on the Learning Flow's Setup tab, and the audit asks for them to be decided at the same time so the Setup tab, its route-map summary and its workbench stories change once.

Status: decided, 19 November 2026. D1: option A(i), a Target schema field under AI model and instructions, naming one schema version, not a group (EVENTS holds seven event-logging versions), with one Learning Flow per target schema. N6: option F with option G's pipeline property, in the order the stream's TimeZone header, then the pipeline's timeZone property, then UTC; the stage puts the resolved zone in the stream's metadata, read with stroom:meta, so a change needs no relearning. The options are kept below as the record of what was weighed.

Added after the plan. Section 3 adds a per-pipeline setting for each: N6 option G and D1 option H. Neither is in the delivery plan yet.

1. D1: the target-schema setting

Today

The target schema is set in one place and assumed in several others. The Schema-valid check (the schema conformance scorer) has a free-text Schema group setting, defaulting to EVENTS. The prompts, the wrapper that target checks put round a proposed answer, and the admission, corpus and extraction-quality XPaths all hard-code event-logging:3.

Figure 1. Today's readers of the target schema. Only the Schema-valid check reads the setting.

Whichever option is chosen, the work in Track 1 task 7 makes all of these read one setting, and the prompt's description of the schema is generated from the XSD (D2 option G). D1 only decides where that one setting lives and how it appears on screen.

Option A: a top-level field on the Learning Flow (recommended in the source)

A Target schema field on the Shapeshifter AI document, shown once on the Setup tab. The prompts, the target checks and the Schema-valid check all read it. The check's own Schema group setting is removed, and a non-default value is copied into the new field.

The UI design leaves open which section it goes in. Both placements are shown.

A(i): in AI model and instructions

Figure 2. The field sits with the model and the instructions, and the route map's summary for the section names the target.

A(ii): at the top of Quality checks

Figure 3. The field sits with what answers are judged by, above Start from.

For

  • The schema says what the Learning Flow produces, so it belongs to the document, not to one check.
  • It is still defined when the Schema-valid check is Off, which UM-2 now allows.
  • One obvious place to look, shown in the route map without opening anything.
  • Placement A(i) puts it beside the time zone, if N6 puts a zone on the Learning Flow (C or F), so the section that changes for group 7 is the same one.

Against

  • A new document field, a serialiser change and a Setup tab field, with its route-map summary and workbench stories (default, read-only, dialog OK and Cancel). This is one of the minor UI changes AS18 already allows for.
  • Existing documents with a non-default Schema group need it copied across; under N5 option A, dev and demo documents are reset instead.

Choosing between A(i) and A(ii). A(i) frames the schema as part of what the AI is asked to do, and is where the route map is read first. A(ii) frames it as what answers are judged against, which is how it works today. With every check now switchable to Off, A(i) avoids implying the schema matters only when Schema-valid is on.

Option B: keep it on the Schema-valid check

No new field. The prompts and target checks read the check's Schema group setting.

Figure 4. The target is a setting of one check, inside Advanced options → The checks.

For

  • No new field and no document change.
  • Nothing to migrate.

Against

  • The setting that tells the AI what to write is hidden in Advanced options, under one check.
  • Mixes "what to produce" with "how to judge it". Under UM-2, the check can be Off while its setting still steers every prompt, which is easy to miss.
  • The source document's worry, a document with no such scorer and so no target, is smaller now that every check is always in the list. But the check's settings would have to stay editable while it is Off.

2. N6: where a feed's time zone comes from

Nothing in Shapeshifter knows a time zone. The prompt tells the model to write times "with a trailing Z", so a local time is written as if it were UTC (audit finding S9). Receipt headers reach the learning stage but are never read, and no document has a time zone field.

The example used throughout. A London firewall logs Oct 19 09:06:02, during British Summer Time (UTC+1). The right TimeCreated is 2026-10-19T08:06:02.000Z. Today the model writes 2026-10-19T09:06:02.000Z, an hour out, and no check can tell: time plausibility allows a window of days, not hours.

Whichever option is chosen, the zone is shown to the model and passed to stroom:format-date as its third argument. format-date is on the N1 allow-list, which is already decided.

Option C: a field on the Learning Flow

One zone per Learning Flow, beside the target schema.

Figure 5. A zone field in AI model and instructions, shown here with D1 option A(i).

The difficulty is that one Learning Flow can serve many pipelines, and so many feeds (AS4). The demo's Any feed Learning Flow is used this way.

Figure 6. One zone for every feed: right for the London feed, five hours out for the New York one (EDT is UTC−4, so 09:06 local is 13:06Z).

For

  • One place, next to the target schema, so group 7 is one change to one section.
  • Smallest change: a document field, the serialiser and a Setup tab field.
  • Right whenever a Learning Flow serves feeds in one zone.

Against

  • Wrong, silently, for every feed in another zone. A site would need a Learning Flow per zone to avoid it.
  • The zone is a fact about where data comes from. A Learning Flow describes how feeds are learned, not where they are.

Option D: a property of the feed

A Time Zone field on the feed document's Settings tab. The Learning Status tab shows which zone a pipeline's feed uses, and where it came from.

Figure 7. Above: the feed's Settings tab with the new field after the existing ones. Below: the pipeline's Learning Status tab saying which zone it is using.

For

  • The zone belongs to the data's source, and the feed is where Stroom describes a source (it already has Data Encoding, Data Format and Data Schema).
  • Right for a Learning Flow that serves feeds in many zones.
  • Useful outside AI translation: a hand-written translation could read it too.

Against

  • A change to the feed document in core Stroom, outside Shapeshifter, with the feed screen's own stories and review.
  • No XSLT function reads feed settings today. The zone has to be put in the prompt when learning, or made readable at run time.
  • Needs a default for feeds with nothing set: UTC, as today, or asking the AI (option F).
  • Each feed has to be set by someone who knows its zone.

Option E: a receipt header

The sender adds a header such as TimeZone: Europe/London when it posts data. It is kept with the stream's attributes, where stroom:meta can read it. Nothing is set in Stroom.

Figure 8. Above: a stream's attributes on the feed's Data tab, with the header. Below: the Learning Status tab with a header, and with a stream whose sender left it out.

For

  • The sender knows its own zone best, and can be right for each stream, even across a clock change or a device moved between sites.
  • Headers already reach the learning stage. No new field or screen; only a line on the Learning Status tab.

Against

  • Senders often don't set it, and Stroom has no standard TimeZone header today. It would need agreeing and documenting for senders and proxies.
  • On its own, a stream with no header is as wrong as today.
  • The zone can differ between streams of one feed, so a learned stylesheet must read it at run time (stroom:meta('TimeZone')) rather than having it written in. That needs meta on the allow-list.

Option F: a combination, in order

Take the zone from the first place that has one: the stream's header, then the feed's zone (D), then optionally one zone for the Learning Flow (C). If none has one, the model is asked to state the zone it assumed instead of silently writing UTC. The Setup tab sets the order once for the Learning Flow.

Figure 9. The Setup tab with the list of places to look, and the Otherwise choice open.

Figure 10. The order, and the London example under each case. The Learning Status tab says which step supplied the zone, as in figures 7 and 8.

For

  • Right in the most cases: per stream where senders say, per feed where someone has set it, and never silently UTC.
  • Each level is optional, so a site can use only the levels it needs.
  • The last step turns a hidden error into one a reviewer sees, and review is the default (SIM-1).

Against

  • The most work: it includes C's field, D's core change and E's run-time reading.
  • More for a person to understand when a time is wrong. The Learning Status line saying which step was used is needed, not optional.
  • "The AI states its assumption" needs somewhere to record and show the assumption, and the model may still guess wrongly.

A smaller F. F doesn't need every level. Header then feed then "the AI states it" avoids changing the Learning Flow. Header then Learning Flow then "the AI states it" avoids the core feed change. Either is a subset of figure 9.

3. Per pipeline: N6 option G and D1 option H

Both settings could be properties of the pipeline's AI Translator element, beside the learnedFolder and learnedName properties it already has. A learner is identified by its pipeline and element, so each learner gets exactly one value. A child pipeline inherits a value from its parent, such as the AI template, and can override it.

The server already works this way for learnedFolder and learnedName: PipelinePlaces reads them for a learner from the pipeline with its parents' values merged in. The learning worker could read timeZone and targetSchema the same way.

On the pipeline's Structure tab

Figure 11. The AI Translator selected on a feed's pipeline. targetSchema is inherited from the AI template, and timeZone is set on this pipeline. This is Stroom's existing properties table, so no new screen is needed.

Figure 12. Stroom's existing Edit Property dialog, overriding the inherited zone. The value is a plain text box, so it has to be checked when saved.

Inheritance from the template pipeline

Figure 13. The template sets a default. One feed's pipeline overrides it, and a feed onboarded later inherits the template's zone until someone edits its pipeline.

On the Learning Status tab

Figure 14. The value in use, and where it was set, shown where the pipeline's learning is watched.

N6 option G: a property of the pipeline

The zone is a timeZone property of the AI Translator, inherited from the template pipeline and overridden per feed's pipeline. It can also be one step in option F, in place of the feed's zone: the header, then the pipeline's property, then the AI states its assumption.

For

  • Matches how the UI divides the work: a Learning Flow says how feeds are learned, and a pipeline is where a feed's learning happens. A zone is a fact about where.
  • One value per learner, with a default from the template, so one Learning Flow can serve feeds in many zones.
  • No change to the feed document or to core Stroom screens. The properties table and the Edit Property dialog already exist.
  • Set under the pipeline's permissions, so an account's own groups can set the zones of their feeds.

Against

  • Content Templates can't write a value per pipeline. The Pipeline Factory could, but it is being dropped (SIM-7). Every new feed starts with the template's zone, and per-feed values need editing by hand, as with option D. Adding per-pipeline values to Content Templates is listed as possible work in the Content Templates note, but a pattern there only knows the feed, account and headers.
  • A hand-built pipeline whose filter covers several feeds has option C's problem again, on a smaller scale.
  • Easy to miss in the properties table, and a plain text box with no zone picker. It needs checking when saved and the Learning Status line (figure 14).
  • Changing it must force a relearn if the zone is written into the stylesheet.

D1 option H: a property of the pipeline

The target is a targetSchema property of the AI Translator, inherited from the template pipeline. A variant has no new property: Shapeshifter reads the schemaGroup of the pipeline's own Schema Filter (the note in figure 11).

For

  • The variant fixes audit W1-6. Today the pipeline's Schema Filter and Shapeshifter's target are set separately and can disagree. Reading the filter makes the pipeline state the schema once.
  • Lets one Learning Flow serve pipelines with different targets.

Against

  • A Learning Flow's Instructions to the AI, its question texts and some checks (allowUnknownEventDetail, the EventDetail/Unknown XPaths) are written for one schema. A pipeline that overrides the target still gets them. That only works if the Learning Flow is schema-neutral, or if the pipeline's target is checked against the Learning Flow when either is saved.
  • The variant depends on the pipeline having exactly one Schema Filter after the AI Translator, which nothing enforces.
  • Changing the target makes every learned translation for that pipeline wrong, so it must force a relearn.

On balance, per pipeline suits the time zone better than the target schema. The schema is tied to how the Learning Flow asks and judges; the zone is tied to where the data comes from.

5. What holds whichever is chosen

  • The prompt changes anyway. Track 1 task 3 fix 1 replaces the "trailing Z" sentence and explains partial dates. N6 gives that sentence a zone to name.
  • Written in, or read at run time. A learned stylesheet can have the zone written into it as a literal when it is learned, or read it for each stream with stroom:meta. A literal is fine where the zone is fixed for the learner (C, and D when a pipeline serves one feed), but changing the zone then means learning again. A header (E, and F's first step) can only be read at run time. Reading at run time needs meta on the N1 allow-list, where it is already a candidate.
  • The learning worker needs the stream's metadata. Task 3 already sets it so that format-date gets the stream's year. The same work lets a run-time zone be read while learning.
  • Time plausibility won't catch a zone error. Its window is days wide, and a zone error is only hours. The zone has to be right at source.
  • The downstream pipeline still says EVENTS (audit W1-6). D1 covers Shapeshifter's setting only. A pipeline's own SchemaFilter and stream type are set separately.
  • Stories. Every changed screen gets its workbench stories: default, read-only, and dialog OK and Cancel, run with the leak check. Option D adds the feed Settings tab to that list.

6. Questions to answer

  1. D1: option A, B or H? If A, in AI model and instructions (A(i)) or Quality checks (A(ii))? If H, a new property or the pipeline's Schema Filter?
  2. N6: C, D, E, F or G? If F, which levels (the pipeline's property could replace the feed's zone), and is the last resort "the AI states its assumption" or UTC?
  3. If G or H: should Content Templates gain per-pipeline property values, so a new feed's pipeline can be given its own zone when it is made?
  4. Run time: should a learned stylesheet read the zone for each stream (stroom:meta on the allow-list), or have it written in when it is learned?
  5. If E or F: what is the header called (TimeZone is assumed here)? Does it take IANA zone IDs only, or fixed offsets too (Stroom's user time-zone preference offers both)? Who tells senders and proxies about it?
