1. Why a temporal graph

Most graph databases store the present. Ask them what a relationship looked like last Tuesday and the honest answer is "you should have modelled that yourself." Stroom's graph is different by construction: it is a materialized, rebuildable projection of event data that already lives in the stream store, and the store underneath it — Plan B, an LMDB-backed temporal state store — keeps every version of every fact, addressable by time. History is therefore not a feature bolted on top; it is the substrate.

That makes a family of questions first-class rather than DIY:

  • "What did this network of accounts and devices look like at 09:00 on the day of the incident?" — a snapshot.
  • "Which connections were live at any point in the hour around that alert?" — a window.
  • "What changed in this subgraph between Monday and today — what appeared, what vanished, what was altered?" — a diff.

Cypher has no standard syntax for any of these, so Stroom adds a small, resolved-before-execution temporal extension: one temporal clause attached to a MATCH. This document walks through each clause, what it returns, and — since "temporal graph" means different things in different products — how the approach compares to the rest of the field.

2. The temporal model

Every node and edge is stored as a series of versions, each stamped with the instant it became effective (validFrom). A version is valid over the half-open interval [validFrom, nextValidFrom) — i.e. until the next version of the same element supersedes it. A delete writes a tombstone version, which means "absent from here on" until (if ever) the element is recreated.

Every temporal read reduces to one primitive: the floor lookup — for a given element, the latest version at or before instant T. In an order-preserving key/value store that is a single reverse-cursor seek, which is exactly what Plan B's temporal state already does. Windows are the same idea widened to an interval; a diff is two floor lookups compared. Understanding this one picture explains all four clauses.

One temporal clause per query. The grammar allows exactly one temporal clause on a query, attached after a MATCH pattern and before its WHERE. No clause at all means "latest". This keeps semantics unambiguous — and is why DIFF is a single clause that internally names two instants rather than two clauses you combine.

4. AS OF — a snapshot at an instant

The workhorse. AS OF t applies a floor lookup per element at the same instant t, so a path is returned only if every node and edge on it was valid at t. The result is "the graph as it existed at t" — same shape as any ordinary query, just resolved against history.

MATCH (d:Device {id:'d-42'})-[c:CONNECTED_TO]->(a:Account)
AS OF datetime('2026-07-01T09:00:00Z')
RETURN a.id, c.startTime

Because the lookup is per element at one instant, an edge whose latest version at t is a tombstone is treated as absent, and the path drops out — there is no "half-deleted" state.

5. AROUND / BETWEEN — a window

Both resolve to an inclusive interval — AROUND t ± d expands to [t−d, t+d]; BETWEEN t1 AND t2 is [t1, t2] directly — and return every element whose validity interval intersects that window, collapsed to one row per surviving element. A version intersects [w1, w2] iff validFrom ≤ w2 AND nextValidFrom > w1; if an element's latest intersecting version is a tombstone, it is absent for the rest of the window and omitted.

MATCH (d:Device {id:'d-42'})-[c:CONNECTED_TO]->(a:Account)
AROUND datetime('2026-07-01T09:00:00Z') +/- duration('PT1H')
RETURN a.id, c.startTime
A window is a union, not a change set. BETWEEN t1 AND t2 reads like "what changed between t1 and t2", but it returns everything that existed at any point in the window — one row per surviving element, with no indication of what was added or removed. If you want the delta, that is DIFF, below — this distinction is the single most common misreading of the temporal syntax.

6. DIFF — what changed between two points

DIFF FROM t1 TO t2 compares the graph as of t1 (the baseline) against the graph as of t2 (the comparison) and classifies each element. The four kinds fall straight out of "present or absent at each instant":

presentpresent, properties differMODIFIED
presentpresent, identicalUNCHANGED

Two output modes, chosen by how you write RETURN

DIFF feeds two very different consumers, so it has two output shapes from the same clause:

  • Delta table — RETURN changeKind, a.id, …. One row per matching path; UNCHANGED suppressed by default. For analysis and reporting: list me what changed.
  • Annotated subgraph — RETURN GRAPH. The deduplicated union of every node and edge across both instants — including UNCHANGED — each row an element carrying a changeKind column (plus before/after values). For the graph UI to draw the whole subgraph and style each element by its change kind.

The RETURN GRAPH result is one element-row table — nodes and edges in a single table, distinguished by an elementType column, with changeKind, endpoint ids, labels, properties, and before/after values. A single table (rather than separate node and edge result sets) is the deliberate v1 choice: it matches how current Stroom visualisations consume tabular results. The graph component reads changeKind and styles accordingly — unchanged as neutral context, added/removed/modified highlighted.

Why keep UNCHANGED? Suppressing unchanged elements is right for a delta report, but it would leave a change visualization disjointed — added and removed fragments floating with nothing to anchor them. So the annotated-subgraph mode returns the full union and guarantees that the endpoints of any returned edge are themselves returned, within the matched subgraph. See the companion diff-operator design doc for the full semantics, the two build strategies, and the risk profile.

7. How this differs from other graph databases

"Temporal graph" is claimed by several products, but they mean quite different things. The axes that actually distinguish them are: (a) is point-in-time state a native storage capability or something you model in the schema? (b) is there a first-class way to diff two states? and (c) which time axis — the valid time a fact was true in the world, or the transaction/revision time the system recorded it?

Characterisations reflect native, out-of-the-box behaviour as generally documented; every one of these systems can model time with enough schema and application effort. The point is what the engine gives you for free.

Three things set Stroom's approach apart — not any one feature in isolation, but the combination:

  • Point-in-time state is a storage primitive, not a schema pattern. Among mainstream property-graph databases (Neo4j and friends), historical state is something you engineer into your model with dated relationships or state nodes, and every query has to thread the time logic by hand. Here, AS OF is a reverse-cursor seek the store already performs; the model stays clean and the time logic lives in one clause.
  • A diff is a query clause, not a post-processing chore. The systems that do offer time-travel (TerminusDB, Datomic, XTDB) generally hand you two snapshots — or a low-level stream of changed facts/triples — and leave assembling a human-meaningful, connected, colour-coded delta to you. Stroom's DIFF … RETURN GRAPH emits exactly the annotated subgraph a UI needs, in one query.
  • It diffs valid time, and the graph is event-sourced. The revision-based systems diff commits — "what did version A of the database contain vs version B". Stroom's AS OF/DIFF ask about the modelled world — "what was true at t1 vs t2" — because each element's validFrom is the effective time carried from the source event. And because the graph is a rebuildable projection of the stream store, that history is intrinsic: reprocessing the raw events reconstructs it.

8. Valid time vs transaction time

This is the distinction that most often causes confusion when comparing temporal databases, and it is worth stating plainly.

  • Valid time — when a fact is true in the modelled world. "This device was connected to that account from 09:00 to 10:00." This is the axis Stroom's temporal graph uses.
  • Transaction time — when the system recorded (or corrected) the fact. "We wrote that connection into the database at 09:03, and revised it at 11:00." This is the axis git-like stores (TerminusDB) and immutable logs (Datomic) key on.
The consequence for DIFF: because Stroom uses a single valid-time axis (bitemporal is deferred), a diff reports changes in the world, and cannot distinguish a genuine real-world change from a later data correction — both appear as a change. It also compares two instants, so churn that happened and reverted between t1 and t2 is invisible. Where an audit trail of "when did we learn / record this" is required, that is a transaction-time (bitemporal) question — a documented future extension, not a v1 capability.

9. Status & caveats

  • Implemented (PoC): the temporal model (versioned nodes/edges, tombstones, floor lookup) and the AS OF, AROUND and BETWEEN clauses, with window-intersection execution, are built and tested.
  • Implemented: the DIFF FROM … TO … clause with both output modes — the scalar delta table and the RETURN GRAPH annotated subgraph — is built and tested. It reuses the AS OF path (evaluate at each instant, classify, merge). See the companion design doc for the semantics.
  • Single valid-time axis. Bitemporal (separate transaction time) is deliberately deferred.
  • Subset Cypher. The temporal clauses attach to a defined Cypher subset; a query currently lowers a single reading clause. Anything outside the subset is a parse-time error by design.
  • Query-side, not rendering. RETURN GRAPH defines the element-row contract the UI consumes; the actual force-directed / time-scrubbed rendering is separate UI work.
  • Properties are string-typed (v1). Graph properties are currently stored and compared as strings (a deferred typing decision), so type-sensitive operations use best-effort string coercion: ORDER BY on a numeric property sorts lexically ("10" before "9"), numeric aggregates and WHERE comparisons coerce from the string form, and RETURN GRAPH renders numbers as quoted JSON strings. Model numeric/date values with this in mind (e.g. zero-pad, or normalise on ingest) until typed properties land.
  • Variable-length paths are node-simple. A -[:T*m..n]-> hop's cycle guard forbids revisiting a node within a path, whereas standard Cypher forbids reusing a relationship — so Stroom can return fewer paths than Neo4j for a query that legitimately revisits a node via a different edge.
  • No multigraph. An edge's identity is (source, type, target); there is no per-relationship identity, so multiple distinct same-type edges between the same pair are treated as temporal versions of one edge, not separate edges. Model repeated relationships (e.g. multiple calls between two entities) with a distinguishing property or an intermediate node.
  • DIFF change-detection scope. A scalar DIFF … RETURN … classifies MODIFIED/UNCHANGED over the projected row, whereas DIFF … RETURN GRAPH classifies over the whole element property map — so the same element can classify differently between the two output modes. Project the properties you care about in the scalar form.
