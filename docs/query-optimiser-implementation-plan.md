# Implementation plan: grammar-driven parser + query optimiser

**Companion to** [`query-optimiser-plan.md`](query-optimiser-plan.md) (the *design* — what & why). This document is the
*build plan* — ordered, self-contained tasks for a coding agent to execute. Where the design doc explains a decision,
this doc says which files to touch, what signatures to write, and how to prove the task is done.

Repo facts below were verified against the working tree on **2026-07-18**. Code drifts: **before editing any file,
re-read it and confirm the cited signature/line still holds** — line numbers are hints, names are contracts.

---

## 0. How to use this document

- **Reader**: an autonomous coding agent (e.g. Sonnet). Each task is written to be picked up cold.
- **Task shape**: every task has *Goal · Depends on · Files · Contract · Steps · Done-when · Verify*. Do them in
  order within a phase; phases are gated (don't start Phase N+1 until Phase N's "Done-when" all hold).
- **Depth**: Phases 0–5 are specified to the file/signature level. Phase 6 is task-structured with contracts but
  is deliberately lighter — **re-plan it in detail when you reach it**, because its shape depends on decisions
  taken in the phase before (this is flagged inline, not an omission).
- **Golden rule of this project — the legacy path must never change behaviour.** Everything is additive behind
  `stroom.query.optimiser.mode` (default **OFF** - a three-value `OFF`/`SHADOW`/`ON` enum since Task 5.4;
  `OFF`/`ON` were originally a plain boolean named `enabled`, see Task 0.3/D6). At every commit, with the mode
  `OFF`, the legacy engine produces byte-identical results to `master`. If a change forces a legacy-path edit,
  stop and reconsider.

### Prime directives (apply to every task)
1. **Flag off = zero behaviour change.** The new code path is unreachable until the flag flips.
2. **Green at every commit.** The module builds and its unit tests pass before you move on.
3. **Parity is the oracle.** For anything that turns StroomQL into a `SearchRequest`, the legacy output is the
   correct answer; a new-path difference is a bug in the new path until proven an intended improvement (and then it
   moves out of the parity corpus — see §11).
4. **Don't hand-edit generated files.** Two exist here: the ANTLR parser (regenerated by the build) and
   `ConfigProvidersModule.java` (regenerated by a test — see Task 0.3).
5. **Documented + checked contracts on every unit of code** — see Code standards below. A task is not "done" until
   its new code carries the required Javadoc *and* enforces it at runtime.

### Code standards (every file, every task — part of every "Done-when")
Applies to all new/edited production code in this project (generated ANTLR sources are exempt).

- **Javadoc on every type and every non-trivial method** (all public/protected members; non-obvious private ones
  too). Each method's Javadoc must state, explicitly:
  - **Preconditions** — required argument values/ranges and required object state on entry (`@param` constraints,
    "must be already bound", etc.).
  - **Postconditions** — what is guaranteed on normal return and the effect of any side effects (`@return`
    guarantees, mutations, emitted events).
  - **Null status** — carried by **JSpecify annotations** (`org.jspecify.annotations`, already in the version
    catalog as `libs.jspecify` and used across the codebase), *not* by prose. Apply `@NullMarked` at the **package**
    level (a `package-info.java` per new package) so everything is non-null by default, and annotate only the
    exceptions with `@Nullable`. Javadoc then explains null status only where a param/return is `@Nullable` (what
    null means) and must not contradict the annotations. (House style also permits class-level `@NullMarked` + inline
    `@NonNull`/`@Nullable`, as in `AnnotationDaoImpl`; prefer package-level `@NullMarked` for the new greenfield
    modules.) Prefer non-null designs; a `@Nullable` return should justify itself.
- **Enforce those contracts in code, don't just document them:**
  - **Preconditions**: JSpecify expresses the *static* non-null contract; still guard **trust boundaries** at
    runtime — public/entry-point methods and inputs crossing a boundary (parsed query text, JSON, ANTLR tokens, REST
    params) get `Objects.requireNonNull(x, "x")`. Value/range/state → throw `IllegalArgumentException` /
    `IllegalStateException` with a message naming the offending input. Use `stroom.util.shared.NullSafe` (house
    utility) for null-tolerant access rather than ad-hoc null checks. Internal `@NullMarked`-to-`@NullMarked` calls
    don't each need a redundant runtime null check.
  - **Postconditions / invariants**: assert before returning where the guarantee isn't trivially obvious (e.g. a
    "never null" return, a "size matches input" invariant, a plan-shape invariant after a rewrite). Cheap checks
    inline; use `assert`/explicit throws for should-never-happen invariants so a planner bug fails loud, not silent.
  - The optimiser is full of transformations with strong invariants (a rewrite preserves semantics; a bound plan has
    every field resolved; a physical plan has exactly one access path per scan). **Encode those invariants as
    checks**, not just prose — they are the cheapest bugs to catch.
- **Tests reflect the contracts**: every public method with a non-null precondition gets a test asserting it rejects
  null (and out-of-range/invalid-state where applicable). Contract tests count toward the task's unit tests.
- **Consistency**: match the surrounding module's existing style (it already uses `NullSafe`/`Objects.requireNonNull`
  and passes checkstyle); the build's checkstyle step must stay green.

## 1. Repo orientation (verified facts)

### Build / toolchain
- **Java toolchain: 25** (Adoptium), set centrally in root [`build.gradle`](../build.gradle) and pinned in
  `gradle/gradle-daemon-jvm.properties`. Modules set no `sourceCompatibility`.
- **`subprojects {}`** applies `java-library`, `checkstyle`, `idea` to every module — new modules get these free.
- **Version catalog**: `gradle/libs.versions.toml` (`[versions]`, `[libraries]`, `[plugins]`, `[bundles]`).
  Third-party deps use `libs.*` aliases; sibling modules use `project(':stroom-query:stroom-...')`.
- **No `buildSrc`, no convention plugins** — shared config is inline `allprojects{}`/`subprojects{}` + `apply from:`
  scripts in `gradle/`.
- **Module registration**: root [`settings.gradle`](../settings.gradle) only; `include 'stroom-query:stroom-query-X'`
  maps directly to `stroom-query/stroom-query-X/` (no `projectDir` remapping). Existing query includes at lines
  ~254–258. Each module sets `ext.moduleName = 'stroom.query.X'`.
- **ANTLR is not used anywhere today** (no plugin, no `.g4`, no catalog entry). You introduce it fresh.
- **GWT safety**: GWT compiles only packages listed under `<source>` in an inherited `.gwt.xml`. The new modules
  have no `.gwt.xml` and are on no GWT source path, so their code is **never transpiled** — you may use the ANTLR
  runtime, threads, regex, etc. freely. Keep generated code out of `stroom.query.client` / `.shared` / `.api`.

### The compilation seam (where StroomQL → SearchRequest happens)
- **`stroom.query.language.SearchRequestFactory`** (in `stroom-query-common`) — a plain class, **no interface**,
  **no Guice binding** (resolved by JIT `@Inject`). Two public methods, and these are the entire contract to
  preserve:
  ```java
  SearchRequest create(String string, SearchRequest in, ExpressionContext expressionContext);
  void extractDataSourceOnly(String string, Consumer<DocRef> consumer);
  ```
  Constructor deps: `VisualisationTokenConsumer`, `DataSourceResolver`, `Provider<QueryFieldProvider>`,
  `SecurityContext`.
- **Call sites** (all in `stroom-query-impl`):
  - `QueryServiceImpl.mapRequest(...)` → `create(...)` (~L605); reached by `search`, `validateQuery` (~L214),
    `downloadSearchResults`, `processRequest` (~L716).
  - `QueryServiceImpl.parseQuery(...)` → `create(...)` **directly** (~L1154).
  - `QueryServiceImpl` (~L826) and `QueryStoreImpl.getDependencyRemapFunction` (~L83) → `extractDataSourceOnly(...)`.
- **Guice module to edit**: `stroom.query.impl.QueryModule` (`stroom-query-impl`).

### Config pattern
- Leaf config `extends stroom.util.shared.AbstractConfig implements IsStroomConfig`; immutable fields; a no-arg
  default ctor + a `@JsonCreator` ctor with `@JsonProperty` per field (`Objects.requireNonNullElse(v, DEFAULT)`);
  getters annotated `@JsonProperty` + `@JsonPropertyDescription` (+ validation annotations on the getter).
- **Reachability = injectability.** A config is injectable only once it's nested into the `AppConfig` tree
  (`stroom-config-app`, `@JsonRootName("stroom")`). There is **no `stroom.query` node yet** (only `queryDataSource`,
  `queryHistory`).
- The Guice provider is **auto-generated** into
  `stroom-config-global-impl/.../ConfigProvidersModule.java` by the test `GenerateConfigProvidersModule`. Never hand
  edit it — re-run that test to regenerate.
- Dotted property path is derived from the JSON nesting → target is `stroom.query.optimiser.enabled`.

### APIs the planner reuses (Phases 2–3)
- `DataSourceProviderRegistry.getFieldInfo(FindFieldCriteria) : ResultPage<QueryField>` (`@Singleton`, common).
  Build `FindFieldCriteria(PageRequest, FindFieldCriteria.DEFAULT_SORT_LIST, dataSourceRef)`.
- `DataSourceProvider.getTimeField(DocRef) : Optional<QueryField>` (on the provider, not the registry).
- `SearchProviderRegistry.getSearchProvider(DocRef) : Optional<SearchProvider>` (keyed by
  `SearchProvider.getDataSourceType()`); `SearchProvider.createResultStore(SearchRequest) : ResultStore`.
  End-to-end usage pattern lives in `ResultStoreManager` (~L215–241).
- `FederatedSearchExecutor.start(FederatedSearchTask, ResultStore, NodeTaskCreator) : void` (async).
- Domain-type metadata (`QueryField.getDomainType()`, `DomainType.canAccept`) — see the design doc's
  [Domain types](query-optimiser-plan.md#domain-types-semantic-layer) section.
- **Expression engine stays as-is**: `stroom.query.language.functions.ExpressionParser.parse(ExpressionContext,
  FieldIndex, String) : Expression` — reuse for `eval`/`select`/`having`.

### Test corpus & parity mechanics
- **Golden harness**: `stroom.query.language.token.AbstractQueryTest` (testFixtures of `stroom-query-language`).
  Per test-dir it reads `in.txt` (queries split on `-----`) and `expected.txt`, emits one `DynamicTest` each, writes
  `out.txt`. Flip `CREATE_MODE=true` to regenerate `expected.txt`. Subclass implements `getTestDir()` + `convert()`.
- **Ready-made parity corpus**: `stroom-query-common/src/test/resources/TestSearchRequestFactory/in.txt` (~30 full
  queries: from/where/eval/select/sort/group/having/window/limit/show). `TestSearchRequestFactory` compares
  `JsonUtil.writeValueAsConsistentString(searchRequest)` and golden-tests error cases too (catches `RuntimeException`
  → `e.toString()`). More fragments in `TestStructureBuilder`/`TestTokeniser`/`TestBasicTokeniser` `in.txt`.
- **Structural equality is usable**: `SearchRequest`, `ExpressionOperator`, `ExpressionTerm` have deep `equals()`.
  **Caveat**: `SearchRequest.equals()` excludes `searchRequestSource`. Use `JsonUtil.writeValueAsConsistentString`
  when you want field-exact parity (incl. that field) + readable diffs — this matches the existing test style.
- **Full token inventory** to cover in the grammar (from `stroom.query.api.token.TokenType`): brackets; `TOKEN_GROUP`
  `FUNCTION_GROUP` `FUNCTION_NAME`; `SINGLE_QUOTED_STRING` `DOUBLE_QUOTED_STRING` `STRING` `PARAM`; `DATE_TIME`
  `DURATION` `NUMBER`; `COMMA`; `ORDER`(`^`) `DIVISION` `MULTIPLICATION` `MODULUS` `PLUS` `MINUS`; `EQUALS`
  `NOT_EQUALS` `GREATER_THAN` `GREATER_THAN_OR_EQUAL_TO` `LESS_THAN` `LESS_THAN_OR_EQUAL_TO` `IS_NULL` `IS_NOT_NULL`
  `IN` `DICTIONARY`; `AND` `OR` `NOT`; `FROM` `WHERE` `EVAL` `SELECT` `SORT` `GROUP` `FILTER` `WINDOW` `LIMIT`
  `HAVING` `SHOW`; `BY` `AS` `BETWEEN` `BETWEEN_AND`; `COMMENT` `BLOCK_COMMENT`. Adjacency/precedence rules are encoded
  in `TokenType` (`KEYWORDS_REQUIRED_BEFORE`, `KEYWORDS_VALID_BEFORE/AFTER`, `ALL_BODMAS`, …) — reproduce them in the
  grammar or the binder. A verified EBNF is in the design doc's
  [Appendix A](query-optimiser-plan.md#appendix-a-stroomql-grammar-reference-phase-1-seed).

> **Note on `IS_NULL`/`IS_NOT_NULL`**: these tokens *exist* (the tokeniser emits them) but the legacy factory rejects
> them at parse — an unfinished-feature bug (`createTerm`'s 3-token minimum was never special-cased for these two
> value-less conditions), not a deliberate rule. Per the project's policy of not reproducing legacy bugs, the new
> path implements them properly instead — see Open Decision D2 (resolved) and
> [query-optimiser-known-differences.md](query-optimiser-known-differences.md).

## 2. Target module layout

```
stroom-query/
  stroom-query-grammar/     (NEW)  ext.moduleName = 'stroom.query.grammar'
     src/main/antlr/stroom/query/grammar/antlr/StroomQL.g4
     src/main/java/stroom/query/grammar/ast/…            typed AST + AstBuilder visitor
     → generated parser lands in build/ under package stroom.query.grammar.antlr
  stroom-query-planner/     (NEW)  ext.moduleName = 'stroom.query.planner'
     src/main/java/stroom/query/planner/logical/…        logical IR (incl. Join from the start)
     .../bind/  .../rewrite/  .../cost/  .../physical/  .../explain/
     .../port/                                            ports the planner needs (see below)
  stroom-query-common/      (edit) QueryCompiler facade + Legacy/Optimising impls + QueryOptimiserConfig
  stroom-query-impl/        (edit) QueryModule binding + swap SearchRequestFactory → QueryCompiler
```

**Dependency direction (do not create a cycle):**
`impl → common → { planner, grammar, language, api }`, `planner → { grammar, api }`, `grammar → api`.
The planner must **not** depend on `common`. Where it needs server services (field info in Phase 2, cost signals in
Phase 3), it defines **port interfaces** in `stroom.query.planner.port` and `common` supplies adapters at wiring
time. This keeps the planner unit-testable with fakes and prevents `common ↔ planner` cycles.

### Task 1.4 — `OptimisingQueryCompiler` at parity (AST → same SearchRequest)
- **Goal**: implement `QueryCompiler` via grammar+AST, initially reproducing the legacy `SearchRequest` exactly.
- **Depends on**: 1.1–1.3.

  Reuse `ExpressionParser` for `eval`/`select`/`having` and the existing `DataSourceResolver` /
  `VisualisationTokenConsumer` (same deps as `SearchRequestFactory`).
- **Contract**: `create(query,in,ctx)` returns a `SearchRequest` equal (see §11 comparison) to the legacy output for
  every corpus query; **error cases must match too** (same rejection for limit-after-select etc.) — *except* where
  legacy's rejection is itself a confirmed bug rather than a deliberate rule (e.g. `is null`/`is not null`,
  bracket-adjacent `not`/`and`/`or` — see [query-optimiser-known-differences.md](query-optimiser-known-differences.md)
  and Open Decisions D2).
- **Done-when**: the parity test (1.6) is green.
- **Verify**: parity test.

> **Found while implementing**: three non-obvious things that made the difference between "parses" and "byte-exact
> JSON", each worth knowing before touching this class again.
> 1. **Legacy's term-value text is whitespace-*stripped* concatenation, not a source slice.**
>    `SearchRequestFactory.parseValueTokens` builds the `ExpressionTerm.value` string by concatenating each
>    underlying token's `getUnescapedText()` with **no separator** — so `now() - 2d` (with spaces) serialises as
>    `"now()-2d"`. A whitespace-preserving slice of the original source (which is what `TokenStream.getText(ctx)`
>    gives you) is the **wrong** value here — unlike for `eval`/`select` expressions, where it's exactly right (see
>    below). The fix: re-tokenise the value's own source text with the legacy `Tokeniser`/`StructureBuilder`
>    fresh (`AstToSearchRequestMapper.resolveValue`), then run the classification+concatenation logic over
>    *those* tokens. This also gets `DateExpressionParser` validation for free, called on real legacy
>    `AbstractToken`s, guaranteeing identical accept/reject decisions regardless of how this grammar's own lexer
>    happened to tokenise the same text (e.g. `2dx` lexes as one `BAREWORD` here vs. `DURATION`+`STRING` in
>    legacy — irrelevant once you re-tokenise independently).
> 2. **A `${param}` used as a plain field reference must reach `ExpressionParser` as raw text, not unescaped
>    text.** `select ${Stream Id}` failed with "Unexpected token without joining operator" until the fix: pass
>    `AstToken.rawText()` (`"${Stream Id}"`, wrapper included) to `ExpressionParser.parse(..., String)`, not
>    `unescapedText()` (`"Stream Id"` — two bare words with nothing joining them, once re-tokenised). Same fix
>    needed for a quoted field name in `select`, and for the `having`-only "additional fields" flush.
> 3. **`TokenType.isString` (which legacy uses for field-name positions almost everywhere) includes `PARAM`** —
>    so `group by ${Stream Id}`, `sort by ${x}`, a window's field, and an eval's variable name all accept a param
>    reference in legacy, not just `select`. The grammar's `termField` rule (renamed `fieldRef`) already covered
>    this for `where`/`filter`/`having` terms; it needed reuse in `groupClause`, `sortItem.field`, `windowClause
>    .field`, and `evalClause.name` too. Deliberately **not** reused in `select`'s plain-field alternative, which
>    already has a dedicated `selectParam` alternative — reusing it there would make `selectItem` ambiguous on a
>    `PARAM` token.
>
> Net result: **every valid query in the parity corpus is byte-identical JSON.** The only surviving differential-
> test deviations are on the corpus's ~7 deliberately malformed queries, where both compilers correctly reject but
> the exception text/embedded position differs (this grammar's errors are position-accurate for *syntax* errors —
> arguably better — but lose legacy's absolute source offset for errors raised from inside a re-tokenised
> substring, e.g. an unknown function name). Documented query-by-query with rationale in
> `TestQueryCompilerParity.KNOWN_ERROR_TEXT_DEVIATIONS` rather than a separate corpus file, since the corpus
> itself is shared with the golden test.

### Task 1.7 — Generative parity (property-based)
- **Goal**: fuzz beyond the hand corpus.
- **Files**: a small StroomQL generator over representative datasources; feed each query to both compilers; diff on
  the same normal form; persist failing seeds as permanent regression cases.
- **Done-when**: generator runs N queries with zero unexplained diffs; failing seeds captured.

> **Found while implementing**: two real bugs, both introduced by this grammar rather than pre-existing in legacy,
> caught by the 200-iteration generator before either shipped:
> - **`x or (y)` misparsed as a call to a function named "or"**: `valueToken`'s `functionCall` alternative allowed
>   `AND`/`OR`/`NOT` as a function name (to cover the genuine `eval bool = and(a, b)` corpus case) with no adjacency
>   check, so inside a `termValue` a bracketed OR sub-expression with a space (`... or (Feed != 'value36')`) greedily
>   swallowed into the term's value. The fix isn't a runtime adjacency predicate on the shared rule (a first attempt
>   at that made ANTLR's adaptive prediction commit to the doomed `functionCall` interpretation and hard-fail instead
>   of falling back to the outer `orExpr`) — it's removing the ambiguity by construction: legacy's own
>   `parseValueTokens` only ever accepts DatePoint/`param` functions in a term value, never `and`/`or`/`not`, so
>   `termValue` gets its own narrower `valueFunctionCall` (`FUNCTION_NAME` only, see `StroomQL.g4`), leaving the
>   broader `functionCall` (which does accept `AND`/`OR`/`NOT`) to `fexpr`/`operand` and `selectItem`, where there's
>   no competing and/or/not interpretation to be ambiguous with.
> - **`(not <term>)` — bracket immediately adjacent to `not`, no space — is accepted here but rejected by legacy**:
>   traced into `Tokeniser.tagKeyword`'s regex, whose "preceded by" alternation (`^\s*|[^=]\s+|\)`) has no `(`
>   alternative, so a per-chunk "and"/"or"/"not"-as-keyword retag never fires when the previous character is `(` with
>   no whitespace — confirmed empirically (`(not x = 1)` rejected, `( not x = 1)` accepted, in legacy directly). A
>   first attempt reproduced this exactly (a leading `{_input.LA(-1) != '('}?` predicate on `AND`/`OR`/`NOT`'s lexer
>   rules), reasoning that Phase 1's bar is parity, not bug-fixing — but this is a whitespace-sensitivity artifact of
>   legacy's regex-based tokeniser, not a deliberate rule, and per the project's policy a confirmed legacy *bug* is
>   not something the rewrite should carry forward. **Reverted**: the predicate was removed, so `AND`/`OR`/`NOT`
>   are recognised unconditionally (like any other keyword) regardless of what precedes them — see
>   [query-optimiser-known-differences.md](query-optimiser-known-differences.md) and
>   `TestLegacyBugFixes.bracketAdjacentNot_legacyRejectsButOptimisingAccepts` for the demonstrating test.
>
> The first bug (the `functionCall`/`valueFunctionCall` split) is a genuine parity fix — both sides must still
> agree once it's fixed, and they do byte-for-byte. The second is a one-directional, *intentional* divergence (the
> new path succeeds where legacy's bug makes it throw), which is a different shape of "known difference" than
> `TestQueryCompilerParity`'s `KNOWN_ERROR_TEXT_DEVIATIONS` (that map is for cases where **both** sides still throw,
> just with different text) — `TestQueryCompilerGenerativeParity` special-cases this one shape explicitly via
> `BRACKET_ADJACENT_LOGICAL_KEYWORD`, asserting legacy still throws and the optimising path does not, rather than
> silently skipping the comparison.

**Phase 1 exit gate**: with the flag **on**, the optimising compiler is at parity across the corpus + generator; with
the flag **off**, nothing changed. `SearchRequestFactory` is still the legacy engine (untouched).

## 5. Phase 2 — Logical IR + bind/validate + rewrite rules

Outcome: a logical plan tree shared by every future front-end (StroomQL now, Cypher later per the graph-DB design
doc) and every later phase; a `Binder` that turns a bound `AstQuery` into that tree or a fail-fast `BindException`;
and four rewrite rules (structural cleanup, auto where/filter split, push-below-joins) composed into a fixed
pipeline — two further rules (dictionary expansion, time-range extraction) explicitly deferred pending
infrastructure Phase 2 doesn't otherwise need — see T2.3.

**Not wired into `OptimisingQueryCompiler` yet.** Phase 1's compiler (AST → `SearchRequest` directly) is untouched
and still the byte-parity path; this phase adds a **second, standalone** module (`stroom-query-planner`'s
`logical`/`port`/`bind` packages) with its own unit tests. Wiring the two together — making the logical plan
actually produce a `SearchRequest` — is Phase 5's job, once there's a physical plan and an executor to justify it.

### Task 2.1 — Logical IR
- **Goal**: the node shapes every later phase (rewrite, cost, physical planning, and the graph DB's `expand`)
  builds on.
- **Files**: `stroom-query-planner/src/main/java/stroom/query/planner/logical/*.java` — a sealed
  `LogicalPlan` interface (`permits Scan, Filter, Project, Join, Aggregate, Having, Window, Sort, Limit`), one
  record per operator, plus `JoinType`, `QualifiedField`, `EquiKey`, `ProjectField`, `SortKey`.
- **Contract**:
  - Every node exposes `AstPosition position()` (reusing the grammar module's already-`@NullMarked` `AstPosition`)
    for later error/EXPLAIN reporting.
  - `Filter` carries **two** predicate slots — `@Nullable ExpressionOperator wherePredicate` and
    `@Nullable ExpressionOperator filterPredicate` — not one merged predicate. Rationale (re-derived from
    `SearchRequestFactory.addTableSettings`, not assumed): legacy's `where` → `Query.expression`, `filter` →
    `TableSettings.valueFilter`, and `having` → `TableSettings.aggregateFilter` are three distinct
    `SearchRequest` fields, but `where` and `filter` are the *same kind of thing* semantically — a row-level
    predicate evaluated pre-aggregation — just pushed to two different physical positions (the datasource vs.
    a post-extraction row filter). Modelling that as one `Filter` node with two slots is what makes the design
    doc's "auto where/filter split" rewrite (T2.3) expressible as "derive `filterPredicate` from `wherePredicate`
    only when the user left `filterPredicate` empty" — an invariant that's awkward to state over two separate
    node types. `having`, by contrast, genuinely applies post-aggregation, so it stays its own `Having` node,
    matching the design doc's 9-node list.
  - `Join` is **binary** (`left`, `right`, not a list) — an N-way `from`/`join` chain binds to a left-deep chain
    of nested `Join`s in source order. Reordering is a Phase 3 (cost-based) concern, not the binder's.
  - **Not modelled**: StroomQL's `show` clause (visualisation-token forwarding) has no relational-algebra
    equivalent — it's a side channel, not in the design doc's node list. The binder rejects it for now (see T2.2);
    revisit if/when Phase 5 needs to wire visualisations through the new path.
- **Done-when**: the module compiles; a table-driven test builds one hand-constructed tree per node kind (e.g.
  `Limit(Sort(Filter(Scan(...), where, null), keys), values)`) and asserts constructor/accessor/`equals` behaviour
  (records give this almost for free — the test is really about proving the *shape* is usable, not exercising
  edge cases that don't exist yet).
- **Verify**: `./gradlew :stroom-query:stroom-query-planner:test`.

### Task 2.2 — Binder + field-info port
- **Goal**: `(AstQuery, FieldInfoSource) → LogicalPlan`, throwing a typed `BindException` (message + position) on
  the first unresolvable field, unsupported condition, unknown join alias, or domain-incompatible join key —
  replacing legacy's scattered ad-hoc checks with one fail-fast pass.
- **Depends on**: T2.1; Phase 1's `AstQuery`/`AstClause` family (`stroom-query-planner` already depends on
  `stroom-query-grammar`, from Phase 0).
- **Files**:
  - `stroom-query-planner/src/main/java/stroom/query/planner/port/FieldInfoSource.java` — the port:
    `List<QueryField> getFields(String dataSourceName)`, `Optional<QueryField> getTimeField(String dataSourceName)`.
    Keyed by the raw datasource **name** (a `String` — exactly what `AstFrom.source()` already carries), not a
    `DocRef`: name/uuid resolution and permission checks are `DataSourceResolver`'s job
    (`stroom-query-common`), which the planner must not depend on (`common` will depend on `planner`, not the
    reverse — a dependency the adapter, not the port, is allowed to have).
  - `stroom-query-planner/src/main/java/stroom/query/planner/bind/Binder.java`.
  - `stroom-query-planner/src/main/java/stroom/query/planner/bind/BindException.java`.
  - `stroom-query-common/src/main/java/stroom/query/language/FieldInfoSourceAdapter.java` — the real adapter,
    wrapping `DataSourceResolver.resolveDataSourceRef` + `DataSourceProviderRegistry.getFieldInfo`/the resolved
    provider's `getTimeField`. Needs a new `stroom-query-common` → `stroom-query-planner` project dependency
    (safe: no cycle — `stroom-query-planner` depends on neither `stroom-query-common` nor anything that does).
  - New dependency: `stroom-query-planner` → `stroom-core-shared` (for `DomainType`; verified no cycle —
    `stroom-core-shared` depends on `stroom-query-api`, not the reverse, and `stroom-query-planner` already
    depends on `stroom-query-api` too).
- **Contract**:
  - Resolves `from`/`join` sources to `Scan` nodes keyed by alias.
  - Every field reference (`where`/`filter`/`having` terms, `group by`, `sort by`, `window`'s field, `eval`'s
    target name, `select` items) resolves against, in order: (a) an `eval`-defined name introduced earlier in the
    same query (tracked as the binder walks clauses in AST order — legacy allows a later clause to reference an
    earlier `eval` variable), then (b) the owning `Scan`'s `FieldInfoSource.getFields(...)`, else `BindException`
    ("Unknown field 'X'"). A bare `PARAM` field reference (`${...}`) is **never** validated against field
    metadata — like legacy, it's resolved at execution time.
  - Every `where`/`filter`/`having` term's condition must be in its field's `ConditionSet`
    (`BindException` "Condition X is not supported for field Y" otherwise). **This is new, stricter validation,
    not a parity requirement** — `SearchRequestFactory` today doesn't check this at all (unsupported conditions
    go straight to the provider); flag this explicitly in the PR as an intentional behaviour difference, not a bug
    (compare/contrast with `docs/query-optimiser-known-differences.md`, though this one is a deliberate
    improvement rather than a bug fix, so it doesn't belong in that document).
  - Builds `ExpressionOperator`/`ExpressionTerm` for `where`/`filter`/`having` by walking the same
    `AstOrExpr`/`AstAndExpr`/`AstNotExpr`/`AstPrimary`/`AstTerm` shape `AstToSearchRequestMapper` already folds
    (Task 1.4) — **a fresh, independent implementation, not a shared extraction**. Term values are taken as raw
    source text (`AstValue.sourceText()`), not legacy's byte-exact whitespace-stripped re-tokenised form (see
    Task 1.4's "Found while implementing" note #1) — byte-exact value serialisation is an execution-time concern
    for Phase 5, when the logical plan is actually turned back into a `SearchRequest`; forcing a shared
    abstraction now, before Phase 5 has a second real caller, would be premature.
  - `join ... on a.k = b.k` resolves `a`/`b` to the correct `Scan` by alias (`BindException` on an unknown alias),
    and checks domain-type compatibility via `DomainType.canAccept` only when **both** sides have a non-null
    `domainType` on their `QueryField` — skip (don't reject) when either side lacks one; domain types are
    advisory and must degrade gracefully, per the design doc.
  - `limit` values are parsed to `long` at bind time (`BindException` on a non-numeric value) — legacy defers
    this to execution (`Long.parseLong` inside `processLimit`); this is, again, a new fail-fast check, not a
    parity requirement.
  - `show` clauses: `BindException` ("show is not yet supported by the optimising binder") — see T2.1.
  - **Joins are bound and validated now, even though nothing executes them until Phase 6** — deliberately ahead
    of need, matching Phase 1's grammar reservation and the design doc's explicit instruction to make `Join`
    shape-complete from the start.
- **Done-when**: table-driven `(query, fake FieldInfoSource) → expected LogicalPlan | expected BindException`
  tests cover: unknown field, unsupported condition, unknown join alias, incompatible join-key domain types, a
  valid multi-join query, an `eval`-then-reference-later query, and a `${param}` field reference (must **not**
  throw "unknown field"). Plus one `FieldInfoSourceAdapter` test proving it correctly wraps the real
  `DataSourceProviderRegistry`/`DataSourceResolver` (mirroring Phase 0's `TestLegacyQueryCompiler` "test the real
  seam" style).
- **Verify**: `./gradlew :stroom-query:stroom-query-planner:test :stroom-query:stroom-query-common:test`.

### Task 2.3 — Rewrite rules
- **Goal**: pure `LogicalPlan → LogicalPlan` transformations, each unit-tested in isolation and in combination,
  that improve physical placement without changing results.
- **Depends on**: T2.1, T2.2.
- **Files**: `stroom-query-planner/src/main/java/stroom/query/planner/rewrite/*.java` — `RewriteRule` (functional
  interface), `PlanRewriteUtil` (shared tree-walk helpers: `mapPredicates`, `collectScans`, `aliasOf`), one class
  per rule, and `RewritePipeline` (the fixed-order runner, `RewritePipeline.standard(FieldInfoSource)`).
- **Implemented** (rationale in the design doc's
  [Domain types](query-optimiser-plan.md#domain-types-semantic-layer) section and its Phase 2 write-up):
  - **`ConstantFoldingRule`**: StroomQL terms have no boolean-literal equivalent, so this folds *structural*
    redundancy rather than literal constants — double negation (`NOT(NOT(x))` → `x`) and single-child
    `AND`/`OR` collapse (`AND(x)`/`OR(x)` → `x`). Purely mechanical, no field metadata needed.
  - **`RedundantTermPruningRule`**: drops a term subsumed by an identical one in the same AND-conjunction (e.g.
    `x=1 AND x=1`) — flattens through nested `Op.AND` only (matching the binder's own left-nested pairwise fold)
    and de-dupes the flat list; deliberately does **not** reach into an `OR`/`NOT` sub-tree for a duplicate
    against a sibling outside it (`(x=1 OR y=2) AND x=1` must not become `(x=1 OR y=2)` — that changes which
    rows match). Each sub-tree is still pruned independently within itself.
  - **`AutoWhereFilterSplitRule`**: for a `Filter` node whose `filterPredicate` is `null` pre-rewrite, splits
    `wherePredicate`'s top-level AND-conjuncts by index-eligibility (`QueryField.queryable()` + the term's
    condition in the field's `ConditionSet` — needs `FieldInfoSource`, so this rule takes one in its
    constructor) into an index-pushed remainder (stays `wherePredicate`) and a non-eligible remainder (becomes
    `filterPredicate`). **Invariant** (its own test): an already-present `filter` clause makes this a no-op. A
    top-level `OR`/`NOT` predicate is treated as one atomic, all-or-nothing unit (can't partially push without
    evaluating every branch at the datasource) and left entirely in `where`. Anything unresolvable (unknown
    field, missing `ConditionSet`) is treated conservatively as *not* eligible — a wrong "leave it in `where`"
    guess is still safe, a wrong "push it" guess could send an unsupported condition to a datasource that
    rejects it.
  - **`PushFiltersBelowJoinsRule`**: for a `Filter` directly above a `Join`, considers `wherePredicate` and
    `filterPredicate` independently and pushes either one below the `Join` onto whichever side **every** field
    reference in it belongs to (all `alias.field`-qualified, all the same alias) — merging into an existing
    `Filter` there via `AND` if one already exists. An unqualified reference, or references spanning both
    sides, leaves that predicate exactly where it was. If both slots end up pushed, the enclosing `Filter` node
    is removed entirely.
  - **`RewritePipeline.standard`** composes them in this order: `ConstantFoldingRule` →
    `RedundantTermPruningRule` (structural cleanup, so the predicate `AutoWhereFilterSplitRule` partitions is
    already in its simplest shape) → `AutoWhereFilterSplitRule` → `PushFiltersBelowJoinsRule` (relocates
    whichever predicates the split just placed in `where`/`filter`).
- **Deferred** (need new infrastructure this task didn't build, rather than a design gap):
  - **Dictionary expansion**: needs a dictionary-lookup port (resolving a dictionary name to its values/`DocRef`)
    that doesn't exist yet — `AstInDictionaryTerm` binding (T2.2) already defers `DocRef` resolution for the
    same reason. Building the port is its own port/adapter task, the same shape as T2.2's `FieldInfoSource`.
  - **Time-range extraction**: needs a new `Scan.timeRangePredicate`-shaped slot with no consumer yet (Phase 3's
    partition pruning, not built). Adding a field to the Logical IR that nothing reads would be exactly the
    kind of speculative abstraction this project's own coding standard says to avoid — defer until Phase 3
    actually needs it, then extend `Scan` and add this rule together.
- **Done-when**: each implemented rule has isolation tests (hand-built input plan → expected output plan) —
  `TestConstantFoldingRule` (5), `TestRedundantTermPruningRule` (7), `TestAutoWhereFilterSplitRule` (8),
  `TestPushFiltersBelowJoinsRule` (7) — plus a combination test (`TestRewritePipeline`) running all four rules
  in sequence, where each rule's output is what the next needs (structural cleanup → split → push-down),
  ending in a fully pushed-down `Join` with the enclosing `Filter` removed. The two invariants
  (`explicit where+filter → unchanged`, `auto-split → provably equivalent`) are each covered by a named test in
  `TestAutoWhereFilterSplitRule`.
- **Verify**: `./gradlew :stroom-query:stroom-query-planner:test`.

**Phase 2 exit gate**: T2.1 + T2.2 + T2.3 (four of six designed rules; two explicitly deferred, see above) are
green — unit tests, the `FieldInfoSourceAdapter` seam test, and the rewrite pipeline's isolation + combination
tests all pass, checkstyle clean — and the existing Phase 0/1 gates (grammar/common modules) are undisturbed.
`stroom-query-planner` still has no behavioural wiring into `OptimisingQueryCompiler` — that's Phase 5's job,
once there's a physical plan and executor to justify it.

### Task 3.2 — CostModel + access-path costing
- **Goal**: cost a single `Scan` (with whatever `Filter` predicate applies to it) against each port that
  answers for it, and emit a `CostEstimate` for the cheapest access path.
- **Depends on**: T3.1.
- **Files**: `stroom-query-planner/src/main/java/stroom/query/planner/cost/CostEstimate.java`, `AccessPath.java`
  (sealed: `FullScan`, `IndexScan`, `StateLookup`), `Selectivity.java` (the heuristic table), `CostModel.java`.
- **Contract**:
  - `record CostEstimate(long rows, long bytes, long durationMs, double confidence, List<String> notes)` —
    matches the design doc's shape exactly. `confidence` in `[0,1]` (1.0 = a port answered directly; lower when
    a heuristic multiplier was applied on top). `notes` carries human-readable provenance (e.g. `"index scan,
    equality selectivity applied to field X"`) for the Phase-4 EXPLAIN surface to reuse verbatim later.
  - `Selectivity`: a pure function `double forCondition(Condition condition)` — **equality < range <
    unindexed-scan**, encoded as calibration constants (`EQUALITY = 0.01`, `IN`/`BETWEEN`/comparison-range =
    `0.1`, everything else / no applicable term = `1.0`). Kept as `private static final double` fields on the
    class for now, not wired into `stroom.query.common.v2` config — nothing executes this cost model yet to
    make the constants tunable-in-production a real requirement; move them to config when Phase 4 gives someone
    a reason to tune them (avoids a config abstraction with no consumer).
  - `CostModel.estimate(Scan scan, @Nullable ExpressionOperator predicate) -> CostEstimate`: tries
    `metaStats.estimate(...)`, then `indexShardStats.estimate(...)`, then `stateStoreStats.estimate(...)` against
    `scan.dataSourceName()`; the first non-empty result decides the `AccessPath` (`FullScan` for Meta,
    `IndexScan` for a shard-backed source, `StateLookup` for Plan B/State). If none answer, falls back to
    `FullScan` with `confidence=0.0` and a note saying no cost signal was available (never throws — a missing
    stat is a low-confidence estimate, not an error).
  - For `IndexScan`, applies `Selectivity` to every top-level AND-conjunct term in `predicate` that references
    `scan.alias()` (reusing `PlanRewriteUtil`-style field/alias matching from Task 2.3 — a small local copy, not
    a cross-package dependency on the `rewrite` package, since `cost` and `rewrite` are siblings with no reason
    to depend on each other), multiplying the base row count down; converts to `durationMs` via
    `documentsPerSecond` when present (`rows / documentsPerSecond * 1000`), else via a fallback constant
    documenting that assumption explicitly in `notes` rather than silently guessing a number that looks precise.
  - **Node parallelism**: the design doc's "divide by node parallelism" is **not implemented in this pass** —
    there's no existing port for cluster size, and modelling it as a bare `nodeCount` parameter with no live
    signal behind it would be exactly the kind of number that looks calibrated but isn't. `durationMs` is
    computed as if `nodeCount=1`; a follow-up can introduce a `ClusterSizeProvider` port when something other
    than a unit test consumes the duration figure.
- **Done-when**: unit tests (all using fakes for the three ports — no real `MetaService`/`IndexShardService`
  needed) covering: monotonicity — a narrower time range yields a lower-or-equal row estimate; `equality <
  range < unindexed-scan` selectivity ordering for the same base row count; each of the three access-path kinds
  chosen correctly when only that port answers; the no-port-answers fallback.
- **Verify**: `./gradlew :stroom-query:stroom-query-planner:test`.

### Task 3.3 — Join costing interface
- **Goal**: cardinality estimation + algorithm selection for a `Join`, ready for Phase 6 to actually execute
  against (this task only costs and chooses — it doesn't run anything).
- **Depends on**: T3.2 (consumes `CostEstimate`s for the two join sides).
- **Files**: `stroom-query-planner/src/main/java/stroom/query/planner/cost/JoinCostModel.java`,
  `JoinAlgorithm.java` (enum: `BROADCAST_LOOKUP`, `HASH_JOIN`, `NESTED_LOOP`), `JoinPlan.java` (the chosen
  algorithm + which side is the build side).
- **Contract**:
  - `estimateCardinality(long leftRows, long rightRows, long leftDistinctKeys, long rightDistinctKeys) -> long`:
    `leftRows * rightRows / max(leftDistinctKeys, rightDistinctKeys, 1)` — the `max(..., 1)` guards the
    division when a distinct-key count is unknown/zero (falls back to the full cross-product rather than a
    divide-by-zero crash; a deliberately pessimistic default that only ever over-estimates, never silently
    produces a wrong-but-plausible small number).
  - `chooseAlgorithm(CostEstimate left, CostEstimate right, boolean leftSupportsPointLookup, boolean
    rightSupportsPointLookup) -> JoinPlan`: `BROADCAST_LOOKUP` (build side = whichever side
    `supportsPointLookup`, i.e. its `AccessPath` was `StateLookup` — see T3.2) whenever either side supports it,
    matching the design doc's framing of broadcast-lookup as specifically a State/PlanB-backed capability, not a
    size threshold; otherwise `HASH_JOIN` with the smaller-by-`rows` side as the build side; `NESTED_LOOP` only
    when neither side has a usable row estimate to compare (both `confidence == 0.0`) — the safe fallback, never
    the default choice.
  - Distinct-key counts are supplied by the caller (Phase 6), not estimated here — the design doc's "domain-
    type-sharpened `distinct()`" refinement is explicitly out of scope for v1 (gated on stats collection, itself
    a post-v1 non-goal per the design doc).
- **Done-when**: unit tests — cardinality formula (including the zero-distinct-keys guard); algorithm selection
  (a tiny lookup-capable side ⇒ `BROADCAST_LOOKUP`; two large non-lookup sides ⇒ `HASH_JOIN` with the smaller
  marked as build side; both unknown ⇒ `NESTED_LOOP`).
- **Verify**: `./gradlew :stroom-query:stroom-query-planner:test`.

**Phase 3 exit gate**: `MetaStats`/`IndexShardStats`/`StateStoreStats` port interfaces exist and `MetaStats` has
a real, tested adapter (the other two are interface-only, adapters deferred with documented rationale);

algorithm-selection tests all pass; checkstyle clean; Phase 0–2 gates undisturbed. Nothing in this phase is
wired into `OptimisingQueryCompiler` or any real execution path.

## 8. Phase 5 — Plan-driven execution (single source) + rollout

Outcome: `create()` — the seam used for real execution, not just `explain()` — starts benefiting from the
Phase 2/3 pipeline it has ignored until now, while never being allowed to make the flag-on path *worse* than
today, and a three-value flag (`off`/`shadow`/`on`) lets this roll out with zero risk to served results before
any environment flips to `on`.

> **Found while planning — `create()` does not need a `LogicalPlan → SearchRequest` lowering, and should not
> get one.** `AstToSearchRequestMapper` (the class `create()` already delegates to) does a lossless, 1:1 mapping
> of every AST clause (`where`/`filter`/`having`/`show`/params/visualisation/table settings) straight into
> `SearchRequest`/`TableSettings` — this is what gives it exact byte-parity with legacy (Task 1.4/1.6). The
> `LogicalPlan` IR (`Binder`'s output), by contrast, was built only far enough to support binding/rewrite/cost
> (Task 2.1) — e.g. `Scan(String alias, String dataSourceName, AstPosition position)` carries no `DocRef`, no
> visualisation/`show`-clause info, nothing about params. Rebuilding a `SearchRequest` generically *from* a
> `LogicalPlan` would mean either extending `LogicalPlan` to carry everything `AstToSearchRequestMapper` already
> has (large, risks reopening Task 1.4/1.6's parity work for no benefit), or accepting a lossy reconstruction
> (unacceptable — parity is the whole point of Task 1.4). The design doc's own wording settles this: Phase 5
> "**parameterises** the `SearchRequest`" — not replaces it. So the shape here is: run `AstToSearchRequestMapper`
> exactly as today (unchanged, still the source of truth for everything), separately run `Binder` +
> `RewritePipeline` (exactly what `explain()` already does) to get a rewritten `LogicalPlan`, and use *only* two
> narrow, specific insights from it — the where/filter split decision and any extracted time bounds — to
> **override** two fields on the already-built `SearchRequest`. Everything else about the request is untouched.

> **Found while planning — the enhancement step must be fail-open, always.** The "golden rule" (§0) protects the
> flag-*off* path, but says nothing about what happens when the flag is on and the *enhancement* itself errors —
> e.g. `Binder.bind(ast)` throws `BindException` for a condition/field combo that `AstToSearchRequestMapper`
> would have silently accepted (Task 2.2 made this validation deliberately *stricter* than legacy, precisely
> because until now nothing that ran for real ever called `Binder`). If `create()` let that exception propagate,
> turning the flag on would newly *break* queries that work today — the opposite of this project's risk posture.
> So: the entire "compute the enhancement" step (bind + rewrite + extract) must be wrapped so that **any**
> exception is caught, logged at `DEBUG`, and discarded — `create()` always falls back to
> `AstToSearchRequestMapper`'s unmodified output on any failure. This mirrors the pattern already used for
> `LogicalPlanExplainer`'s date-bound parsing (catches `RuntimeException`, treats it as "not a time term") and
> for the Task 4.2 UI estimate (a failed/slow estimate never blocks the real search).

> **Found while planning — wiring the where/filter split into real execution is a genuine, deliberate behaviour
> change for one specific case, not a pure optimisation.** Verified: neither `SearchRequestFactory` (legacy) nor
> `AstToSearchRequestMapper` checks `QueryField.queryable()`/`ConditionSet` today — an unsupported
> condition/field-type combo is sent straight to the datasource (Task 2.2's note, confirmed again here). Traced
> one specific consequence into `stroom-index-lucene/.../SearchExpressionQueryBuilder.getTermQuery`: a term
> referencing a field **unknown to the index** compiles today to `new MatchNoDocsQuery()`, which — ANDed into the
> top-level boolean query — silently makes the **entire query return zero rows**, not just that term. Once
> `AutoWhereFilterSplitRule`'s split is wired into `create()` (Task 5.3 below), that same term instead moves to
> `TableSettings.valueFilter` and is evaluated correctly at extraction time, so the query starts returning the
> rows it should have all along. This is a **behaviour improvement**, not a bug reproduction, and needs the same
> explicit callout this project already gives such cases (D2's bracket/`is null` precedent) — see Task 5.3's
> Done-when. It only affects bare `where` clauses mixing eligible and ineligible terms; a `where` clause that is
> entirely index-eligible is untouched (`AutoWhereFilterSplitRule` is a no-op there — confirmed by
> `TestAutoWhereFilterSplitRule.allTermsEligible_isANoOp`).

- **Contract**:

## 9. Phase 6 — Joins (multi-source execution)

Outcome: `create()` can compile and actually execute a query with `join`, producing correct INNER/LEFT-OUTER
results over two (or, by recursion, more) datasources; enrichment joins to a
State/PlanB store reuse the existing lookup functions rather than a new mechanism; EXPLAIN shows join
order/algorithm for real (not just the direct-`Scan`-sides case Phase 4 already covers).

> **Accuracy note (2026-07-19 code review):** the "driven by the cost-chosen algorithm" framing this outcome
> originally used is *not* met at execution time. `JoinSearchProvider` hard-codes `JoinAlgorithm.HASH_JOIN` and
> `JoinExecutor` always materialises the right side; `JoinCostModel.chooseAlgorithm` is consulted only by the
> advisory `LogicalPlanExplainer` (EXPLAIN), never by real execution. Wiring the cost-chosen algorithm/build-side
> into execution is a deferred Task 6.1 item (disclosed in the T6.1c status note as "a deferred optimisation, not
> a correctness gap"). The remaining deferred/absent Phase 6 items (cost-driven execution, per-side push-down,
> N-way joins, Task 6.2 enrichment joins, Task 6.3 real EXPLAIN cardinality, Task 6.4 domain relationships) are
> catalogued in `docs/query-optimiser-code-review.md`.

**This phase is materially bigger than Phases 0–5.** Every prior phase either built standalone, unwired machinery
(Phases 2–3) or *parameterised* an existing, unchanged execution path (Phase 5's `create()` enhancements only ever
added/overrode fields on a `SearchRequest` that `AstToSearchRequestMapper` already builds). A join has **no**
representation in that wire format at all — `Query.dataSource` is a single `DocRef`, and `ResultStoreManager`
routes purely by that one `DocRef`'s type. Making joins real means teaching the execution layer, not just the
compiler, about a genuinely new shape of query - see the findings below, gathered before writing any code.

> **Found while planning — where a join query would actually route.** `SearchProviderRegistry.getSearchProvider
> (DocRef)`'s only implementation (`SearchProviderRegistryImpl.java:74-78`) resolves purely by
> `docRef.getType()` against a flat `Map<String, SearchProvider>`, self-populated by each `SearchProvider`'s own
> `getDataSourceType()` (verified: this is exactly how `SearchableSearchProvider` registers itself once per
> `Searchable`, no special-casing anywhere in the registry). A join query has no single natural `DocRef` - the
> resolution: a **sentinel `DocRef` type** (e.g. `type="StroomQLJoin"`) that a new `JoinSearchProvider` registers
> itself under, exactly mirroring the existing `Searchable` registration pattern - no change to
> `SearchProviderRegistry`/`ResultStoreManager` routing logic itself, only a new provider added to the existing
> `Set<SearchProvider>` multibinding.

> **Found while planning — how a join's results reach the user without a parallel execution engine.**
> `Coprocessors`/`CoprocessorsImpl` extend `ValuesConsumer` (`accept(Val[] values)`) and are built purely from
> `TableSettings`/`FieldIndex` (`CoprocessorsFactory.create(...)`, verified: zero references to Lucene, an index
> shard, or any physical datasource in that class). This ingestion point is **already** fed by non-Lucene sources
> in production - `SearchableSearchProvider` passes a `CoprocessorsImpl` directly as the `ValuesConsumer` to
> `Searchable.search(...)` for SQL-stats/PlanB-shard-info sources - and directly by hand in
> `TestSearchResultCreation` (`stroom-search-impl` test), which builds a `CoprocessorsImpl` from a bare
> `TableSettings` and manually calls `consumer.accept(Val.of(vals))` per row, no search task involved at all. So a
> join executor's only genuinely new job is producing `Val[]` rows that represent joined tuples; **everything
> downstream** - the original query's post-join `where`/`select`/`group by`/`having`/`sort`/`limit` - reuses the
> existing `Coprocessors`/`DataStore`/`ResultStore` pipeline unchanged, fed via the same `accept(Val[])` call any
> other row producer already uses. This is the literal realisation of the design doc's "reuse `ResultStore`,
> coprocessors" instruction for Phase 6, not just a loose paraphrase of it.

> **Found while planning — realising each join side as a sub-query is already possible with public, synchronous
> APIs.** `ResultStore.awaitCompletion()` (`ResultStore.java:144-151`) blocks until a store's search finishes (not
> just a polling loop); `ResultStore.getData(componentId)` (line 219) returns the underlying `DataStore` directly,
> bypassing the UI-paginated `search()`/`ResultCreator` path entirely. `QueryServiceImpl.getColumnValues`
> (`QueryServiceImpl.java:390-440`) is existing, working precedent for reading **every** row of a completed store
> (`dataStore.fetch(columns, OffsetRange.UNBOUNDED, OpenGroups.ALL, timeFilter, IdentityItemMapper.INSTANCE, ...)`)
> rather than a UI-sized window. A join executor can therefore run each side as `searchProvider.createResultStore
> (sideRequest)` → `awaitCompletion()` → `getData(...).fetch(...)` and get back every row of that side, using
> nothing beyond what `QueryServiceImpl` itself already relies on elsewhere.

> **Found while planning — the logical-plan and cost-model groundwork already exists, unused.** `Join`
> (`stroom-query-planner/.../logical/Join.java`: `left`, `right`, `joinType`, `equiKeys`) is already produced by
> `Binder` for any join clause (verified: `Binder.bindFromAndJoins`, left-deep for N-way chains), with each
> `EquiKey`'s two `QualifiedField`s already domain-type-validated (`Binder.validateDomainTypeCompatibility`, Phase
> 2). `JoinCostModel.chooseAlgorithm`/`estimateCardinality` (Phase 3) already picks `BROADCAST_LOOKUP`/
> `HASH_JOIN`/`NESTED_LOOP` given each side's `CostedAccessPath` - it has just never been called by anything real
> (Phase 3's own documented scope). `LogicalPlanExplainer.explainJoin` (Phase 4) already annotates a `Join` node
> with the chosen algorithm/cardinality **when both sides are direct `Scan`s** - i.e. Task 6.3 below is mostly
> "stop passing `0, 0` for distinct-key counts and wire this into execution", not new machinery.

  - **Research finding, in order of discovery:**
    1. `Filter.wherePredicate()`/`filterPredicate()` and `Having.predicate()` are *already* real, wire-typed
       `ExpressionOperator`s - `Binder.bindTerm`/`qualifiedName` (`Binder.java` lines ~310-359) build

       an alias to an unqualified-but-unambiguous field once a query has ≥2 scans. So the where/filter/having side
       of a join's outer clauses needs **no new machinery at all** - Task 5.2/5.3's "it's already a wire type,
       just assign it" pattern applies unchanged.

## 11. Test strategy (quick reference)
The design doc's
[Test-driven development & dual-run parity](query-optimiser-plan.md#test-driven-development--dual-run-parity) section
is the method; the concrete harness is:
- **Golden differential** (Task 1.6): both compilers over `TestSearchRequestFactory/in.txt`, compared via
  `JsonUtil.writeValueAsConsistentString`. This is the hard merge gate for anything touching StroomQL→SearchRequest.
- **Property-based** (Task 1.7): generator → both compilers → same normal form; failing seeds become fixtures.
- **Shadow dual-run** (Task 5.2): compare-only on live traffic, zero user risk.
- **Two altitudes of "same"**: *same plan* (byte/JSON-identical `SearchRequest`) where the optimiser is told not to
  reorder (Phase 1, and rewrite-off); *same answer* (identical results, cost no worse) where it optimises (Phases
  2+). Joins have no legacy oracle → hand-computed expected result sets + the invariant that order/algorithm choice
  never changes the result.
- **Unit tests per component**: lexer/parser (token stream + error positions), AST builder (`text→AST`), binder
  (`(query,fields)→plan|error`), each rewrite rule (`plan→plan`, isolation + combination), cost model (monotonicity
  properties, not magic numbers), join planning (cardinality + algorithm selection).
