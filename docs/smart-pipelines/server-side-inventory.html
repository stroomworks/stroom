3. How it runs

The runtime path, as described by the class docs and wiring in element/, stage/ and fragment/. The key design choice is that a processing task never calls the model. A stream that nothing serves yet is deferred, and a scheduled job does the learning.

Fragment documents created on promotion go into the explorer through ExplorerContentCreator, running as the processing user. A pipeline deletion marks its learning deleted (PipelineDeletions), and AttemptRetention later removes it.

8. Model (LLM) call sites

WhereWhat it does
element/ModelAdvisorsBound as the default Advisors (an OptionalBinder, so tests can replace it). Resolves the document's model through AiService.getOpenAIModelDoc and getChatModel
element/ModelAdvisorThe only place the model is called: ChatModel.chat(messages). It builds the system message from the document's templates plus supervisor guidance, then replays the transcript. Counts tokens and writes an audit event per call
learning/Conversation, learning/RecordedAdvisor, stage/HeartbeatingAdvisorCallers of Advisor.ask. HeartbeatingAdvisor keeps the session lease alive during a long call (its own thread)
learning/QuestionText, learning/TemplatesPrompt text is held in code, not resources, and versioned with Templates.VERSION

Things to look at here:

  • Timeouts and retries come from the model document's HTTP client config in stroom-ai. There's no Shapeshifter-specific timeout, retry or back-off around chat().
  • Prompt injection. Event data reaches user messages, and guidance from people with EDIT permission reaches the system message. The model's reply drives generated Data Splitter and XSLT, so what that output is allowed to do (for example stroom:http-call) needs constraining. docs/reference/design/ai_translations D4 already discusses this.
  • Data leaving the system. Feed samples go to an external provider. We need to decide which data, and under whose authority.

12. Boundary findings

  1. No API module for Shapeshifter. -impl-db depends on the whole engine and imports stage.*, element.* and cache.*. The 17 ports in stage/ are the obvious content for a stroom-shapeshifter-ai-api.
  2. The engine depends on stroom-pipeline (an implementation module) through 168 imports from 15 stroom.pipeline.* packages, mostly in element and fragment. The pure learning engine (learning, scoring, stage) barely needs it. Most of the coupling is in the pipeline adapters.
  3. The LLM abstraction leaks twice. ModelAdvisor imports langchain4j directly, and stroom-ai-api's AiService returns langchain4j types (ChatModel, EmbeddingModel, ScoringModel). It also mixes model access with Ask Stroom chat persistence. Shapeshifter needs a narrow "send these messages, get a reply and usage" port.
  4. A 15k-line cycle joins stage, learning, scoring, extraction and fragment, plus a smaller doc ↔ element cycle (§10).
  5. Shared DTOs used as the domain model. The engine core imports stroom.shapeshifter.shared heavily, so the client contract and the engine model can't change independently. This matters for the client-side work.
  6. Resource → service → DAO layering isn't followed. SupervisorResourceImpl calls Stage and the ports directly and contains paging, sorting and business rules.
  7. Test doubles ship in production (state/, 19 classes).
  8. Packages are named by role, not by layer (doc holds REST plus the Guice root module, and element holds jobs, the model adapter and pipeline adapters). That makes the real boundaries hard to see.
  9. Release-bound artefacts that become expensive once shipped: migration V08_00_00_001, the 21 REST paths, the 6 config properties, 2 job names, 3 element types and the ShapeshifterAiDoc serialised form.

13. Suggested next steps

  1. Agree the contract with the client-side work: the REST paths and the 56 shapeshifter.shared types. Decide whether the engine keeps using them internally or gets its own model.
  2. Draw the target modules, for example:
    • -api: ports and the Advisor port
    • -engine: stage, learning, scoring, extraction, with no stroom-pipeline dependency if that's achievable
    • -impl: pipeline adapters, jobs, document, REST, services
    • -impl-db: DAOs
    Then add an ArchUnit-style test so the boundaries can't drift back.
  3. Break the engine cycle by finding the handful of types that cause the back-edges (for example scoring → stage 2, learning → stage 5, extraction → learning 11) and moving them down a layer.
  4. Run a focused risk review of the model path: data sent out, prompt injection, output constraints, timeouts, spend limits, and turn storage and retention.
  5. Agree the migration version and any schema changes before anything else depends on the tables.
  6. Assess the tests: which scenario tests are worth keeping as the regression net while restructuring.
