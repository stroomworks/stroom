Bringing Domain Types to the Floor Map

Today, an object on a floor map is just a shape on a picture. Domain Types can make it something you can follow, act on, and recognise anywhere in Stroom. Here is a catalogue of ways to connect the two — and where I'd start.

Why this matters

Two features that should talk to each other

The floor map is a live, time-scrubbable picture of a place — desks, cameras, gates, and the people or assets moving between them. Domain Types are Stroom's way of saying what a value means — that this column holds an IP address, that one a location, that one an asset ID — so the system can offer the right action for it.

Right now these two live in separate worlds. Connecting them pays off three ways: cross-navigation (get from a table row to the exact spot on a map and back), a consistent visual language (a camera looks like a camera everywhere), and richer, more robust data binding (live events attach to the right object by meaning, not by a brittle key match).

The two pieces today

What each one can — and can't — do right now

Floor Map

Every background and placed object is a "fact" with a type (gate, camera, desk…). That type decides its shape, colour, and stacking order. You can move, scale, rotate and multi-select objects, scrub through time, and watch live events animate across the plan.

But: an object's type is just a label for drawing. An object links to nothing — you can't get from it to the data behind it, and nothing elsewhere can point at it.

Domain Types

A domain type is a semantic tag like Host.ipaddress or Asset.location, with wildcards (*.ipaddress). Columns carry it; dashboards declare which types they handle. Right-click a typed cell and you get "Jump to …" the dashboards that understand it, carrying the value and time range across.

But: the only thing a domain type does today is offer a jump to a dashboard, from a grid cell. Maps neither produce these actions nor receive them.

The core idea

Give map objects a meaning, not just a look

The map already has a "type" on every object. If that type (and the columns of the query feeding the map) also carried a domain type, each object would gain a meaning the rest of Stroom already understands. That single change turns an object into three things at once:

The rest of this document is a catalogue of what that unlocks, grouped into seven themes, followed by a recommended order of attack.

Theme A

The map as a place you can jump to

A

Inbound — landing on the map from anywhere

Make a floor map a first-class jump destination, like dashboards already are.

A1Locate on map

From any domain-typed value anywhere in Stroom — a table cell, a query result — offer "Show on floor map". The map opens already focused on the matching object.

Value: close the loop from "there's an alert on Asset 42" to "here it is, in this room" in one click.

A2Maps declare what they handle

Let a floor map register which domain types it can show (e.g. this map handles *.location for the north campus). It then appears automatically in the "Jump to…" menu across Stroom — exactly the way dashboards opt in today.

Value: maps become discoverable destinations without anyone wiring links by hand.

A3Land at the right moment

Carry the source's time range along with the jump, so you arrive on the map already scrubbed to when the thing happened, not to "now".

Value: the map shows the world as it was at the moment you were investigating.

Theme B

The map's objects as things you can act from

B

Outbound — element-level linking that doesn't exist today

Turn each object into an actionable thing, not just a drawing.

B4Jump from an object

Right-click an object on the map → "Jump to…" the dashboards and queries that understand its type, carrying the object's own values across. This is the element-level linking the map has never had.

Value: the map becomes a launchpad — click the camera, land in its footage dashboard.

B5Actionable tooltips

The pop-up that appears over an object renders its meaningful attributes as live actions — jump, annotate, copy — instead of plain text.

Value: the detail you were already showing becomes the place you act.

B6Map tables get the grid superpowers

The map's own tables — the fact list and the events-query results — gain the exact "Jump to" behaviour that dashboard grids already have. Essentially free once their columns carry a type.

Value: consistency, at almost no cost — the same right-click works everywhere.

B7Live cross-highlight

Selecting a row in a linked view highlights the matching object on the map, and selecting an object highlights its row — a two-way "these are the same thing" link, beyond one-shot navigation.

Value: keep a table and a map open side by side and have them stay in sync.

Theme C

One consistent semantic look

C

Style by meaning, not by a hand-typed label

Make the same kind of thing look the same, everywhere.

C8Style by meaning

Drive an object's icon and colour from its domain type rather than a free-typed string — with class-level defaults and attribute-level overrides (everything under Camera.* looks like a camera; Camera.ptz can differ).

Value: no more the same real-world thing looking different because someone typed the label two ways.

C9A shared visual vocabulary

Define the icon and colour for a domain type once and reuse it across the map, dashboards, and grids.

Value: users learn one visual language and read it fluently across the whole product.

C10Smarter "Discover"

When new object types appear in the data, the map's discover step pre-assigns their icon, colour, and behaviour from the domain type instead of leaving them as anonymous blobs.

Value: new data shows up already looking right, with no manual styling.

C11Semantic legend & filter

A legend keyed by meaning lets you toggle or spotlight everything of a given type — "show only the doors", "dim everything that isn't a camera".

Value: cut a busy plan down to just what you care about, by meaning.

Relationship to Layers: this meaning-driven styling is exactly what the companion Layers UX proposal renders as each layer's swatch and legend. Today that swatch comes from the free-typed TypeStyle; Theme C moves the source of truth to the domain type, so the two docs must agree there is one place a thing's look is defined. That doc's "a layer is a type" (Option A) then evolves to "a layer is a domain type", and its smart-layer legend is the same surface as C11 above — one control, built once.

Theme D

Authoring becomes semantic

D

Make the map easier and safer to build

Reuse Stroom's existing type machinery in the editor.

D12Reuse the standard pickers

Configure object types and field mappings with the same class/attribute pickers used everywhere else in Stroom, drawing from the shared catalogue of known types.

Value: familiar UI, fewer typos, and every map speaks the same vocabulary.

D13Auto-detect identity & location columns

Infer which columns of the events query carry the entity's identity and its location from their domain types, instead of asking the author to pick them by hand.

Value: less setup, fewer misconfigurations — the map wires itself up.

D14Validate against the catalogue

Warn at authoring time when an object uses a domain type that isn't in the known catalogue, or that no handler understands.

Value: catch a dead-end link while building, not when a user clicks it.

Theme E

Smarter data binding

E

Attach live data to objects by meaning

Use semantics to make live binding robust — and to link maps together.

E15Bind by meaning

Match a live event to a placed object by a semantic value — this event's Host.ipaddress equals that object's — rather than by an exact, brittle key. Wildcard matching decides what's compatible.

Value: live tracking keeps working even when identifiers are formatted differently across sources.

E16Map-to-map drill-down

An object typed as a place — a site or a building — jumps to that place's own floor map, because the map registers itself as the handler for that type (Theme A). Campus → building → room becomes a natural navigation path.

Value: a whole estate becomes browsable by drilling from the big picture down to the room.

Theme F

Entity-centric actions

F

Act on the thing, not the pixel

Anchor actions to what an object represents.

F17Annotate the entity, not the spot

Attach annotations to an object's semantic identity rather than a coordinate, so a note about "Asset 42" follows it as it moves and shows up wherever that asset appears.

Value: investigative notes stay with the real-world thing, across maps and across time.

F18Where-used

From a domain-typed value, list every floor map, dashboard, and index that references it.

Value: answer "where does this thing show up in Stroom?" instantly.

Theme G

Make the mechanism first-class

G

Platform-level ideas that lift every feature at once

Turn "domain type behaviour" into shared infrastructure.

G19A shared action registry

Instead of each surface hard-coding "Jump to dashboard", keep one registry of actions per domain type — jump, locate-on-map, annotate, decorate. Maps, dashboards, and grids all draw from it.

Value: add a behaviour once and it lights up everywhere, including the map, for free.

G20Domain types in the dependency graph

Surface which maps and dashboards handle a given type in Stroom's dependency and impact tooling.

Value: see the blast radius before changing a type — who relies on Asset.location?

Where I'd start

A recommended roadmap

Start where the machinery already exists, then bring it down to individual objects, then unify it across the product. Each tier delivers something usable on its own.

Quick winsreuse what exists
  • B6 Map tables get the grid "Jump to" for free
  • D12 Standard type pickers in the editor
  • A1·A2 Maps register & become jump destinations
  • D14 Validate types against the catalogue
Mediumnew UI on the canvas
  • B4·B5 Jump & act from an object / tooltip
  • C8·C9 Style objects by meaning, shared look
  • D13 Auto-detect identity & location columns
  • C10·C11 Smarter discover · semantic legend
Ambitiousdeeper & cross-cutting
  • E15 Bind live data by meaning
  • E16 Map-to-map drill-down
  • F17·F18 Entity annotations · where-used
  • B7·G19·G20 Cross-highlight · registry · deps

Why this order: the quick wins lean entirely on mechanisms Stroom already ships — the grid "Jump to", the way dashboards register the types they handle, and the existing type pickers — so they carry low risk and prove the concept early. The medium tier is where the map's canvas gains genuinely new interaction. The ambitious tier is worth doing only once the ideas above have shown their value, because it changes shared infrastructure.

To resolve together

Open questions & risks

Add alongside, or replace?

Do map objects gain a domain type in addition to today's free-form type, or does the domain type replace it? The former keeps every existing map working; the latter is cleaner but needs a migration story. This is the same fork the companion Layers UX doc frames as "is a layer a type, or a richer grouping?" (its §6) — it should be decided once for both.

Cost of matching while animating

The map redraws continually during playback. Resolving semantic matches (styling, binding) needs to be cheap enough not to stutter the animation — likely pre-computed rather than done per frame.

Who curates the vocabulary?

Most of the value depends on domain types being used consistently. That needs an owner for the catalogue and some governance, or the shared visual language and cross-links fragment.

This is an ideas document to open a conversation, not a commitment to build any particular item. The themes and roadmap are a starting point for prioritisation — the numbering is for reference in discussion, not an implementation order beyond the tiers shown.
