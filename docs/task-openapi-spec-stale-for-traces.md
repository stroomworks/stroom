# The published OpenAPI spec advertises Traces endpoints that do not exist, and omits four that do

**Component:** `stroom-app` — the committed OpenAPI artefacts
`src/main/resources/ui/noauth/swagger/stroom.{json,yaml}`, generated from
`stroom-core-shared/.../pathways/shared/TracesResource.java` and `TracesDocResource.java`
**Severity:** medium. Nothing misbehaves, but the **published API contract is wrong** in both
directions — two advertised paths return 404, and four real ones are undocumented. The spec is
served **unauthenticated**, so it is the first thing an integrator reads.
**Status:** open. Not a code defect; the artefact is simply older than the code it describes.

---

## What the spec says, and what the code says

`TracesResource` declares `BASE_PATH = "/traces" + ResourcePaths.V2` with five sub-paths, and
`TracesDocResource` declares `/tracesDoc/v1/{uuid}`. The committed spec was generated before that
shape existed.

| Path | In the spec | In the code |
|---|---|---|
| `/traces/v1/getTrace` | **yes** | **no** — v1 is gone |
| `/traces/v1/getTraces` | **yes** | **no** — v1 is gone |
| `/traces/v2/findTrace` | yes | yes |
| `/traces/v2/findTraces` | yes | yes |
| `/traces/v2/getSpans` | **no** | **yes** |
| `/traces/v2/getTraceOverview` | **no** | **yes** |
| `/traces/v2/findTracesWithHistogram` | **no** | **yes** |
| `/tracesDoc/v1/{uuid}` | **no** | **yes** (fetch and update) |

The two `findTrace*` entries that appear in both **are** correct: their `operationId`s and request
schemas (`GetTraceRequest`, `FindTraceCriteria`) already match the source. So the defect is purely
one of coverage — two paths advertised that do not exist, four that exist but are not advertised —
rather than a wrong description of a real endpoint.

Regenerating rewrites roughly **800 lines** across the two files, and **every changed path is
`/traces/*`** — nothing else in the API is affected, which is what makes this cheap to fix and safe
to review.

## Why it went stale, which is the part that will recur

The spec is generated, not hand-written. `stroom-app/build.gradle`:

```gradle
resolve {
    outputFileName = 'stroom'
    outputFormat = 'JSONANDYAML'
    resourcePackages = ['stroom']
    outputDir = file('src/main/resources/ui/noauth/swagger')
}
...
tasks.build.dependsOn resolve
```

**`resolve` hangs off `tasks.build`, not `check`.** So a change to a resource interface or an
`@Operation` description is invisible to the ordinary pre-commit verification: the source is
correct, the tests pass, and the artefact that gets served still describes the previous API.

Two things make that easy to miss:

- The same `build.gradle` carries a large **commented-out block** configuring an older swagger
  plugin. Read on its own it looks as though generation is disabled and the spec is maintained by
  hand — it is not, and concluding so leads to editing the artefact directly.
- The command is documented, but in `SwaggerUiServlet`'s class javadoc —
  *"The swagger specs are generated by the gradle task `./gradlew :stroom-app:resolve`"* — which is
  not a file anyone changing an endpoint has reason to open.

## Why it matters more than a stale document usually would

`SwaggerUiServlet` is annotated `@Unauthenticated` and serves the spec under
`/stroom/noauth/swagger-ui/`. So this is not internal developer documentation that a reader can be
expected to sanity-check against the code: it is the machine-readable contract, reachable without
credentials, and the normal way to consume it is to generate a client from it. A generated client
gets two methods that 404 and is missing four endpoints entirely.

## Suggested fix

**Run the generator and commit the result.**

```bash
./gradlew :stroom-app:resolve
git add stroom-app/src/main/resources/ui/noauth/swagger/
```

The diff is large but mechanical, confined to `/traces/*`, and it is exactly what the build would
produce anyway.

### Worth doing at the same time

**Make staleness detectable.** The underlying problem is not this one lapse but that nothing fails
when the artefact drifts. Options, in increasing order of how well they prevent a recurrence:

1. **Document it where it will be seen** — a line in the resource-authoring guidance, or a comment
   on `TracesResource`, saying an API change needs `:stroom-app:resolve`. Cheapest; relies on
   someone reading it.
2. **Wire `resolve` into `check`** as well as `build`. Makes the artefact current whenever anyone
   verifies, at the cost of adding generation time to every `check`.
3. **Add a verification task that regenerates to a temporary directory and fails if it differs from
   the committed files.** This is the only option that makes the drift *impossible to commit*
   rather than merely likely to be noticed, and it costs nothing when nothing has changed. It also
   gives a clear failure message — "the OpenAPI spec is out of date, run `:stroom-app:resolve`" —
   which is more useful than a silent divergence.

**Also delete the commented-out swagger block** while in that file. It configures a plugin the build
no longer uses, and its presence actively misleads: it is the reason one might conclude the spec is
hand-maintained and edit it by hand, which produces a change that the next `build` silently reverts.

## Verification

- `./gradlew :stroom-app:resolve` leaves the working tree **clean** — that is the whole assertion,
  and it is the one a check task should automate.
- The five `/traces/v2/*` paths and `/tracesDoc/v1/{uuid}` are present in both `stroom.json` and
  `stroom.yaml`, and no `/traces/v1/*` path remains.
- Both files still parse as JSON and YAML respectively.
- If option 3 is taken: the new task fails on a deliberately edited spec, and passes immediately
  after `resolve`.
