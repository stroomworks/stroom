Stroom Query Engine — Developer Guide

How StroomQL and Cypher share one query core: the key classes, a query traced end-to-end through each language, how joins work, and where to extend it.
Audience: engineers reading, reviewing, or extending the query optimiser, joins, and the Graph DB.
Scope: the sw-query-optimiser query stack: stroom-query-grammar, stroom-query-planner, stroom-query-common, stroom-query-impl, stroom-graphdb-impl, stroom-searchable-impl.
The one idea to hold onto. There are two query languages (StroomQL and Cypher) but one core. Both parse to an AST, bind to a single shared LogicalPlan IR, and produce a SearchRequest that is dispatched to a SearchProvider chosen purely by the datasource's DocRef type. Every result row, from either language, is a Val[] fed into the same coprocessor / ResultStore pipeline. Learn that spine once and both languages read the same.

1. The big picture

A search enters through QueryServiceImpl as a SearchRequest carrying query text and a target datasource DocRef. Compilation turns that text into a mapped SearchRequest the execution layer understands; execution dispatches it to a SearchProvider and streams Val[] rows back through coprocessors into a ResultStore. The two languages diverge only in the compile step.

3. Shared foundations

Four things every path shares. Understand these and the rest is detail.

  • The compiler interfaces. QueryCompiler.create(query, request, ctx) turns text into a mapped SearchRequest. DispatchingQueryCompiler picks the implementation by the stroom.query.optimiser.mode flag (QueryOptimiserMode): OFF → LegacyQueryCompiler (default), ON → OptimisingQueryCompiler, SHADOW → runs the optimiser alongside legacy to compare, serving legacy's result. A different language is handled by an AlternativeQueryCompiler (Cypher's is GraphCypherQueryCompiler), chosen first by AlternativeQueryCompilerResolver on the datasource type.
  • The LogicalPlan IR. A single sealed interface (stroom.query.planner.logical.LogicalPlan) whose nodes cover both worlds: relational (Scan, Filter, Project, Join, Aggregate, Sort, Limit, …) and graph (NodeScan, Expand, VarLengthExpand). See §7.
  • Dispatch by type. SearchProviderRegistryImpl maps DocRef.getType() → SearchProvider. Everything routes here — an index, a Plan B/State store, the join sentinel ("StroomQLJoin"), and the graph ("GraphDb"). To add a datasource kind, register a provider under its type.
  • The row model. Results are stroom.query.language.functions.Val[], handed to Coprocessors.accept(...) and materialised in a ResultStore. Both engines emit the identical shape, which is what lets joins combine them positionally.

4. Trace: a StroomQL query

from "AuthEvents" where action = 'LOGIN' select time, user
  1. Entry. QueryServiceImpl.mapRequest(...) resolves the datasource DocRef (from ownerDocRef, or the leading from "X" via LeadingDataSourceExtractor), then asks AlternativeQueryCompilerResolver if a non-StroomQL compiler claims the type. For an index/searchable type, none does → falls through to queryCompiler (the DispatchingQueryCompiler).
  2. Dispatch. DispatchingQueryCompiler reads QueryOptimiserMode. OFF hands to LegacyQueryCompiler and you skip straight to step 6. ON uses OptimisingQueryCompiler.
  3. Parse. StroomQlParser.parse(text) runs the ANTLR StroomQL.g4 grammar; AstBuilder walks the parse tree into a typed AstQuery.
  4. Bind. Binder.bind(ast) resolves field names against the datasource (via the FieldInfoSource port), validates them, and produces a LogicalPlan — for this query, Project(Filter(Scan "AuthEvents")).
  5. Rewrite & cost. RewritePipeline.standard(...) applies result-preserving rules (e.g. AutoWhereFilterSplitRule splits the where into index-eligible terms pushed to the datasource vs value terms kept as a post-read filter; PushFiltersBelowJoinsRule for joins). The CostModel annotates scans for EXPLAIN. Key nuance: for a single relational source this IR is a planning artefact — it shapes the emitted SearchRequest (pushed predicates, pruned projection, time-range) but does not replace the datasource's own execution engine. Everything runs fail-open: any exception in OptimisingQueryCompiler.applyPlanEnhancements is caught and the plain legacy-mapped request is returned unchanged.
  6. Execute. The mapped SearchRequest goes to SearchProviderRegistryImpl.getSearchProvider(dataSource).createResultStore(request). The provider runs the search (async), producing Val[] rows into Coprocessors; the ResultStore collects them for the caller to page through.

5. Trace: a Cypher query

from "HostGraph" match (h:Host {ip:'10.0.0.1'})-[:CONNECTED_TO*1..3]->(t:Host) return t.ip
  1. Dispatch by type. QueryServiceImpl resolves "HostGraph" to a GraphDb-typed DocRef (via ownerDocRef, or the portable leading from "X"). AlternativeQueryCompilerResolver finds GraphCypherQueryCompiler claims GraphDbDoc.TYPE and routes there — the StroomQL compiler is never involved.
  2. Compile. GraphCypherQueryCompiler delegates to CypherCompiler.create(...), which parses with CypherQueryParser (the Cypher.g4 grammar) and lowers via CypherToLogicalPlan into the same LogicalPlan — here Project(VarLengthExpand(NodeScan(h))). Cypher-only concerns that the sealed IR has no node for (temporal window, DIFF, RETURN GRAPH, aggregation) ride alongside on CompiledCypherPlan.
  3. On the wire. The compiled request carries a GraphSpec holding the raw Cypher text (not the plan — that would create a module cycle), and its Query.dataSource points at the GraphDbDoc.
  4. Execute. Dispatch lands on GraphSearchProvider.createResultStore, which re-parses/re-compiles the Cypher, opens the graph's LMDB stores (GraphStores, permission-checked via GraphDbDocCache), and runs one of three executors over the plan: the ordinary GraphTraversalEngine; DiffExecutor for a scalar DIFF; or GraphElementExecutor for RETURN GRAPH. All three emit Val[] rows into the same coprocessors as StroomQL.
"A hop is a join." A MATCH (a)-[:T]->(b) lowers to graph operators (NodeScan → Expand) on the shared IR, conceptually an index-nested-loop join of an adjacency relation to a node relation. The graph reuses the IR and cost ports; it does not fork the planner. Where it differs from the relational side: GraphTraversalEngine executes the IR directly against LMDB, whereas a relational single-source plan is executed by that datasource's existing provider.

6. Joins, end to end

A join is the one place the compiler emits a composite request and a bespoke provider runs it. Two phases:

Compile (OptimisingQueryCompiler.createJoin)

  • The Binder binds from A join B on a.k = b.k to a left-deep Join node (each equi-key an EquiKey; join-key domain-type compatibility validated). Today: single join, two sides.
  • Each side is compiled to its own single-source SearchRequest (an index/state side via a synthesised from "…" select …; a graph side as a GraphSpec — the GraphJoinSource leaf, with its columns derived from the Cypher RETURN … AS via CypherJoinSchema).
  • JoinPredicateSplitter decides, join-type-aware, which parts of the outer where may pre-filter each side (never the null-supplying side of a LEFT join) vs. stay as a residual on the combined row.
  • The output is a SearchRequest whose datasource is the sentinel type JoinDataSourceType.TYPE = "StroomQLJoin", carrying a JoinSpec (both side requests + the equi-keys).

Execute (JoinSearchProvider)

  • openSide runs each side as its own sub-search, dispatched by DocRef.getType() — so a graph side "just" routes to GraphSearchProvider, an index side to its provider. Rows come back as Val[].
  • Build-side selection: for INNER, build the smaller side (by DataStore.getSize()) and stream the larger; a LEFT join never swaps (probe = left, so unmatched left rows emit null-padded inline).
  • The build side is realised into a BuildSideLookup that starts on-heap and spills to an LMDB store (SpillingBuildSideLookup → LmdbJoinBuildStore) once maxHeapBuildRows/maxHeapBuildBytes are exceeded. The probe side is streamed, never fully materialised.
  • JoinExecutor derives every key through the single keyOf(...) (so both sides agree on equality — numeric keys are canonicalised; SQL-null never matches), then runs HASH_JOIN, NESTED_LOOP, or the BROADCAST_LOOKUP enrichment fast path (a per-row point lookup against a keyed Plan B / State store via StateFetcher). Output is capped by maxOutputRows; caps throw JoinLimitExceededException.
  • The combined row is always [probe columns…, build/lookup columns…]; the residual where is evaluated on it before it reaches the coprocessors.

Cost & EXPLAIN: JoinCostModel.chooseAlgorithm picks the algorithm from each side's AccessPath (a StateLookup side → broadcast lookup; else hash join, smaller side built); LogicalPlanExplainer renders the plan + estimates for the EXPLAIN endpoint.

7. The shared LogicalPlan IR

stroom.query.planner.logical.LogicalPlan is one sealed interface. Relational and graph nodes coexist deliberately so both front-ends reuse the same rewrite rules, cost model, and planner ports:

sealed interface LogicalPlan permits
    Scan, Filter, Project, Join, Aggregate, Having, Window, Sort, Limit,   // relational
    NodeScan, Expand, VarLengthExpand;                                     // graph (Cypher)
  • Rewrite rules and tree-walkers (PlanRewriteUtil) switch over every node; a graph node in a relational walker is inert (returns no scans, is never a push-down target) and vice-versa — a relational Join never appears in a graph plan.
  • Anything the sealed IR can't represent for Cypher (temporal context, diff, RETURN GRAPH, aggregation/DISTINCT) is carried as side-channels on CompiledCypherPlan, kept out of the IR so the relational core stays untouched.
  • Three copies of the "unwrap the compiled plan shape" logic (GraphTraversalEngine.unwrap, GraphSearchProvider.terminalProject, CypherJoinSchema.terminalProjectFields) assume the emitted shape [Limit?][Sort?]Project[Filter?][Expand*|VarLengthExpand]NodeScan — keep them in lockstep if you change what CypherToLogicalPlan emits.

10. Invariants & gotchas

The rules a change must not break (a pre-production review confirmed these — see the review report and its findings):

  • Keys are single-sourced. Every equi-key (build and probe) is derived through JoinExecutor.keyOf; a SQL-null component never matches. Don't compute keys anywhere else.
  • A LEFT join never pre-filters its right side. JoinPredicateSplitter is the one place that decides push-down for execution — the rewrite rule's output is for EXPLAIN only.
  • The optimiser is fail-open. Any error in plan enhancement returns the legacy request unchanged — a query must never be made worse by the optimiser being on.
  • Row shape is positional. Combined rows are always [probe…, build…]; assembleRow/whereRowPredicate/buildFieldMapping depend on it regardless of which side is physically probe vs build.
  • Provider dispatch is by DocRef.getType() only. Registering a duplicate type now fails fast rather than silently overwriting.
  • Unsupported Cypher fails loud. Anything outside the compiled subset is a positioned compile error, never a silent wrong answer.
  • Graph properties are string-typed (v1) — type-sensitive ORDER BY/aggregates use string coercion; and edges are identified by (source, type, target) (no multigraph). See the review's F2/F9 and the temporal-features caveats.

11. Where the tests are

  • Grammar/AST: TestStroomQlParser-style + TestCypherQueryParser (query-grammar).
  • Planner: TestBinder, TestLogicalPlan, Test*Rule, TestJoinExecutor, TestCypherToLogicalPlan (query-planner).
  • Compiler parity: TestQueryCompilerParity (hand corpus) and TestQueryCompilerGenerativeParity (fuzz) assert the optimiser matches legacy; deliberate divergences are documented in known-differences.
  • Joins: TestJoinSearchProvider, TestSpillingBuildSideLookup, TestLmdbJoinBuildStore (common / searchable-impl).
  • Graph: TestGraphTraversalEngine, TestDiffOperator, TestGraphSearchProvider (graphdb-impl).
  • Turning the optimiser on for a test: the stroom.query.optimiser.mode flag (QueryOptimiserMode, default OFF). Run in SHADOW to diff against legacy without changing results; ON to execute the optimiser's plan.
