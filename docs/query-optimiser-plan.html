Internal design plan · Proposed

A grammar-driven parser & cost-based query optimiser for Stroom

Replace the hand-coded StroomQL engine with a formal ANTLR grammar, a rule-rewrite + cost-based optimiser that automatically chooses the cheapest way to answer a query — including joins across data sources — and a pre-run estimate of how long the query will take.

1Why we're doing this

StroomQL is compiled by a hand-coded pipeline: a regex Tokeniser, a StructureBuilder, and a ~1,490-line SearchRequestFactory. There is no formal grammar, so error messages are approximate and the language is hard to grow.

There is also no optimiser. A query is routed to exactly one backend by document type, and the user must manually decide which predicates are index-eligible (where) versus applied in memory afterwards (filter). The engine never chooses an access path, never prunes by an index's time partitions, and cannot tell you how long a query will take before you run it.

Formal grammar

Precise, evolvable syntax with real error positions.

Automatic planning

The engine, not the user, decides how to fetch data.

Pre-run estimate

Know the likely cost & duration before hitting Run.

Joins

Combine an index with a state store or another index.

2The engine today

Current path: text → regex tokeniser → structure builder → SearchRequestFactory → one backend. Red = the parts we are changing.

Good news — the foundation is already there Every field already advertises a ConditionSet declaring which predicates its backend supports, and Stroom already tracks per-shard document counts, file sizes, throughput, and index time partitions. The optimiser is built on metadata we already have — not a new statistics subsystem.

3Design decisions

Four forks were agreed up front. They shape everything below.

Parser technology

ANTLR4 grammar

A formal .g4 grammar generating a Java parser (server-side only — the GWT client parses nothing, it calls REST). Strong error messages, easy to evolve.

How plans are chosen

Rule rewrites → cost-based choice

Heuristic rewrites first (pushdown, prune, reorder), then pick the cheapest plan by estimated cost. Standard RDBMS design; the same cost model powers the time estimate.

Where estimates come from

Existing metadata

Shard doc counts, index time-partition overlap, meta counts by feed/type/time, and condition selectivity heuristics. No new storage; ships fastest. Telemetry calibration can come later.

Delivery

Incremental, behind a flag

New parser + optimiser coexist with the current engine behind a config flag. One switch point, instant revert, existing StroomQL keeps working throughout.

We reuse the execution engine The optimiser emits into the existing machinery — SearchProviders, ResultStore, coprocessors, extraction pipelines, and the federated cluster executor. We are not rewriting execution; we are making smarter decisions about what to ask it to do.

5How the optimiser decides

Two stages. First, rule rewrites transform the plan into an equivalent but cheaper shape. Then, cost-based choice picks between physical alternatives.

Rule rewrites (always-safe transformations)

  • Predicate pushdown — automatically derive the where/filter split the user does by hand today: index-eligible terms (per each field's ConditionSet) go to the backend; the rest become post-filters.
  • Push filters below joins — apply each single-source condition before joining, so every side scans as little as possible.
  • Time-range extraction — isolate the time predicate so the planner can prune index shards whose partition window doesn't overlap the query.
  • Constant folding, prune redundant terms, expand dictionaries.

Cost-based choice (pick the cheapest equivalent plan)

For each data source the planner enumerates access paths — an index scan with partition pruning, a full scan, or a state lookup — estimates each, and keeps the cheapest. For joins it also chooses the algorithm (next section).

Backwards compatible Queries that already spell out where / filter keep compiling to the same thing. The optimiser only improves placement when it can prove the result is unchanged.

6Estimating cost & time before you run

The cost model turns metadata Stroom already keeps into an estimate of rows, bytes, and wall-clock duration.

Example: a tight time range overlaps fewer shards → fewer docs → lower cost; an equality predicate is cheaper than a range, which is cheaper than an unindexed scan.

The estimate is surfaced in the query editor before Run, with a warning when it exceeds a configurable threshold. Calibration constants live in config; later we can fit them to real measured durations without changing the interface.

7Joins across data sources

New capability: a single query can combine sources — e.g. enrich an event index with a PlanB/State store, or join two indexes on a shared key. v1 supports equi-joins, INNER and LEFT OUTER.

Example query

from Events as e
left join UserState as u on e.userId = u.userId
where e.time between 2026-07-01T00:00:00.000Z and 2026-07-17T00:00:00.000Z
select e.time, e.userId, u.department

Filters are pushed to each side first; then the planner costs broadcast-lookup vs hash vs nested-loop and picks the cheapest, using the smaller side to build.

Each side runs as its own sub-query through the existing SearchProviders and federated executor; a join operator combines the streams using ResultStore/coprocessors — no new storage layer. Enrichment lookups reuse the existing state-fetch functions rather than a new mechanism.

Out of scope for v1 Non-equi joins, temporal stream-to-stream correlation joins, and RIGHT/FULL OUTER joins. These build on the same operator later (the windowing infrastructure already exists for temporal joins).

8Domain types — querying by meaning

Stroom already tags fields with a domain type: a semantic label such as Host.ipaddress or Asset.location, with wildcards like *.ipaddress. Today it only powers the grid's "Jump to …" navigation. The new engine becomes its first execution-side consumer — using it as an advisory signal that sharpens exactly the features this project adds (joins, cross-source enrichment, costing). It is never required: a query whose fields carry no domain type plans exactly as it does today.

Two sources name the same real-world thing differently; their domain types make them join-compatible, so the planner can validate — or infer — the equi-key by meaning.

Smarter, safer joins

Validate an equi-join's keys by domain type (reject Asset.id = Host.ipaddress at plan time) and infer the key when compatible types line up under different names. Where a type owns a canonical form, normalise both sides so 192.168.0.1 matches 3232235521.

Find the source that answers a type

The execution-side twin of the dashboard "Jump to" registry: stores declare which domain types they answer for, so an enrichment join can discover the right State / PlanB / reference source for a typed key instead of being wired by hand.

Advisory, always Domain types add nothing to single-source planning and are never required. Later they can also sharpen cost estimation (better distinct-value counts for join sizing) once a statistics source exists — a post-v1 upgrade.

9Where it plugs in

The whole thing hangs off one method. Both validation and execution funnel through searchRequestFactory.create(...) in QueryServiceImpl (and QueryStoreImpl). We introduce a QueryCompiler facade with two implementations and let a config flag choose.

Flag stroom.query.optimiser.enabled (default off). One switch point means instant revert to the legacy compiler.

11Scope & non-goals

In scope

  • ANTLR grammar + typed AST replacing the regex tokeniser.
  • Logical plan, rule rewrites, cost-based physical choice.
  • Pre-run cost & duration estimate + EXPLAIN.
  • Equi-joins (INNER, LEFT OUTER) across data sources.

Not in v1

  • Non-equi & temporal stream-stream correlation joins; RIGHT/FULL OUTER.
  • Replacing the expression/function engine (kept as-is).
  • Changing result storage, coprocessors, or cluster protocol.
  • A statistics-collection job or query-telemetry store (later accuracy upgrade).

12Proving it works — dual-run parity

Because both compilers sit behind the one facade and both emit a SearchRequest, the legacy engine is a live oracle for the new one: any query can be compiled by both and the outputs compared — in a test, a fuzzer, or production. The work is done test-first, and no phase merges until its parity gate is green.

The same query, both engines, one comparison — run as a unit test, a generator, and a production shadow.

Three layers, tightening

  • Golden differential (hard merge gate) — both engines over the existing corpus, compared on a canonical normal form; negative tests assert precise error positions.
  • Generative fuzz — random valid queries diffed the same way; failing seeds become permanent fixtures.
  • Shadow mode — in production the legacy result is served while the optimiser compiles in parallel; divergences are logged, never served. Flip to "on" only after a clean soak.

Two altitudes of "same"

Same plan — a byte-identical SearchRequest where the optimiser is told not to reorder (parity mode). Same answer — identical results, cost no worse, where it does optimise. Joins have no legacy twin, so they're checked against hand-computed results and the invariant that join order / algorithm never changes the answer.

Alongside parity, each component has focused unit tests — rewrite rules (input plan → expected plan), cost-model monotonicity, join cardinality & algorithm selection — plus an end-to-end pass via the Stroom MCP tools (validateQuery, the estimate endpoint, csvQuery) including a cross-source join, with estimates held to a target error band.

Risk posture Grammar drift is caught by the parity gate; estimate inaccuracy is bounded by confidence bands + config calibration; rollout risk is neutralised by the flag + shadow mode; joins ship last, after single-source is proven.

13Downstream consumer — the temporal Cypher graph

A second project, the temporal Cypher graph, is designed to build directly on this query core rather than ship its own parser/planner. This is not a requirement on this plan's scope — just a flag that a second consumer exists, and a further reason to keep the Join IR shape-complete early (Phase 2). In it, graph "traversal" is a join: a hop MATCH (a)-[r]->(b) lowers to a join of an edge/adjacency relation to a node relation.

Consumes from this core

  • The grammar module — a Cypher.g4 alongside StroomQL.g4 → the same logical IR.
  • The Join operator (Phase 2) + join algorithms (Phase 6): a hop runs as the broadcast-lookup / index-nested-loop join over an adjacency prefix-scan access path.
  • The rewrite rules + cost model and the existing execution machinery (providers, ResultStore, coprocessors).
  • The semantic (domain-type) layer (§8) — domainType + canAccept + the enrichment-source-routing index for entity resolution (same domain type ⇒ same node across sources) and catalogue-driven node mapping; see the graph's domain-type integration.

Adds on top (out of scope here)

  • A variable-length-path / fixpoint operator (bounded transitive closure) — beyond the equi-join set.
  • An as-of temporal join — reuses the enrichment-lookup path (GetState/StateProvider); distinct from the windowed stream-stream correlation joins deferred in §11.
  • A Plan B graph datasource (node/edge/adjacency relations with cost signals).
