1. What Shapeshifter AI does

Shapeshifter AI turns a feed's raw data into events without anyone writing a translation by hand. A pipeline has an AI Translator element where the parser and XSLT would normally be. While it has nothing to run, it learns: it asks a model, step by step, for a parser and a stylesheet, judges every answer against the feed's own data, and keeps the result once it passes. Later streams are served by what it learned, and every record it serves is still checked.

Figure 1. The two loops. Serving runs on every stream; learning starts when nothing is bound, or when a served record fails a gate.

Learning Flow
The Shapeshifter AI document. It says how feeds are learned: the model, the instructions, the learning steps, the checks, the approval mode and, now, the target schema.
Smart Pipeline
A pipeline with an AI Translator. It is where a feed's learning happens, so the work on one feed is done on its pipeline, under the pipeline's permissions.
Learner
One AI Translator in one pipeline, identified by the pipeline's UUID and the element's id. What is learned belongs to the learner.
Learning run
One session of questions to the model. Each answer is a candidate.
Check
A test of a candidate on the feed's own data, such as Schema-valid, Completeness or Preservation. Each is Off, Advice or Gate.
Draft
A candidate that passed every gate and is waiting for a person to approve it.

3. Checks: Off, Advice or Gate

Each check is Off, Advice or Gate. A candidate goes live when every gate passes, and a served record that fails a gate holds its stream back.

  • One list of checks, on the Learning Flow, under the Setup tab's Quality checks. This includes the checks that used to live only on learning steps (wholeness, preservation, fidelity) and the new ones (completeness, no data-like literals, time plausibility, the regression corpus).
  • Off isn't run. Advice is run, shown beside a draft and fed back to the model, but never decides. Gate refuses a candidate that falls below its threshold. Compile is always a gate.
  • No weights and no pass mark. Several near misses no longer add up to a failure, and a check that isn't a gate can't change the result.
  • Serving uses the same gates. Each record is judged by every gate that judges records.
  • Steps don't name checks. A check applies to any step where it has something to measure, and step rules still route on it.
  • The score people see is the average of the checks that ran.
DefaultChecks
GateCompile (always), Schema-valid, Completeness, Preservation, the regression corpus, Input coverage, Wholeness (90%), Fidelity
AdviceNo data-like literals (a gate once it has run on the demo feeds without false failures), Time plausibility (its window set per Learning Flow)
OffThe heuristic ones: Yield, Extraction quality, Business rules

Example: NETFILTER

Today it has 30 lines in, 29 events out, and a stylesheet containing select="2023", and it was promoted at 1.0. With the decided defaults:

✓ Compiles
✓ Schema-valid (29 / 29)
✕ Completeness: 30 in, 29 out, 0 skips declared
✓ Preservation
✓ Regression corpus: no earlier records for this feed
⚠ Literals (advice): 2023, Production

It can't be approved, because Completeness is a gate and fails. The literals advice goes back to the model and shows beside the draft, but wouldn't refuse it on its own.

Where it is built: Track 1 task 10 on the server; the Quality checks change on the Setup tab in Track 2 step 4. Tasks 1 to 3 build their new checks into it.

4. Review by default

  • A new Learning Flow waits for someone to approve each new translation. There is one promotion path for both modes, and automatic mode approves the same draft at once through the same code.
  • Approving a draft needs EDIT on its pipeline, so the pipeline's owner decides.
  • Switching a Learning Flow to automatic needs a new application permission, provisionally Approve AI Translations Automatically. It is checked whenever a Learning Flow is saved, including on import. Switching back to review needs only EDIT. By default only administrators have it.
  • No provisional bindings. On trial and Accept now go. A first result learned from fewer than 10 records is always a draft, and later streams wait for a person. The minimum applies to first learning only, not to relearns.

5. What a learned stylesheet may use

A learned stylesheet runs in the real XSLTFilter. Nothing limits what Saxon can reach from there. On the dev instance, a pipeline XSLT listed /etc and wrote a file under /tmp using standard XSLT alone, and several stroom: functions call out, read other feeds' data, drop records or give different answers each run.

A learned stylesheet may use only what is on an allow-list, covering standard XSLT and XPath as well as stroom: functions (N1, option C).

Figure 4. The static check refuses anything not on the list, including indirect calls and computed URIs. A refusal goes back to the model like any other failed check.

  • First, a list in code (Track 2 step 2), applied by the static check and the scenario test harness alike. It must exist before any Content Template makes an AI pipeline, and Track 1 task 3 needs format-date and meta on it.
  • Later, the Egress Policy screen (Track 2 step 6). The ai_translations_egress branch is pulled in, an administrator maintains the list, and it is enforced at run time too.

6. What is judged

The design says a candidate is judged over the whole held stream. In fact, the stream-level checks only see its first 64 KiB.

Figure 5. The model sees a sample; the checks see the whole stream.

  • Coverage is judged on the whole held stream, in the full pass (N2 option B).
  • One sample-size setting, in bytes, that the prompt honours (option F). The 6,000-character prompt cap goes. The default stays cautious, because there is no calibration yet.
  • Large single documents aren't learned (option E). The stop report says why, and what to change.

7. Target schema and time zone

The options for both are on the group 7 options page, with mockups.

Target schema: one version, on the Learning Flow

The target schema is a Target schema field under AI model and instructions on the Setup tab (D1, option A). Everything that depends on the schema already lives in the Learning Flow: the business rules, the required fields, the prompts, and the Target and Admit steps. So each target schema gets its own Learning Flow.

Figure 6. The field names one schema version, not a group: EVENTS holds seven event-logging versions, from 3.0.0 to 4.1.0.

  • The prompt's description of the schema is generated from the XSD (D2 option G), so every target schema is usable, not only event-logging.
  • The hand-written event-logging guidance, written today for 3.0.0, is checked against the latest version and updated. The namespace, location and version are filled in from the chosen schema.
  • With no event-logging schema installed, the field starts empty, and the readiness banner says so.

Time zone: header, then pipeline, then UTC

Today the prompt tells the model to write times "with a trailing Z", so local times are written as UTC. Now each stream's zone is resolved before the stylesheet runs.

Figure 7. The resolved zone is written under its own key, so the sender's TimeZone attribute is left alone.

  • The header is TimeZone, a Stroom header like Feed or System, with an IANA zone ID. HTTP has no standard header for this, and the header describes the data's zone, not that of whatever posted it.
  • The pipeline property is timeZone on the AI Translator, which in practice means one per feed. It is checked as a zone ID when the pipeline is saved.
  • The Learning Status tab shows the zone in use, and whether it came from the header, the pipeline, or UTC because neither was set.
  • Known and accepted: pipelines made by a Content Template inherit the template's timeZone. Most installations take data from systems in one zone, so that will usually be right.

8. How feeds get an AI pipeline

Figure 8. New feeds through Content Templates; existing feeds by hand.

  • The Pipeline Factory goes (SIM-7 option B), with about 6,000 lines, two tables and three security problems. Content Templates, which already ship, make each new feed's AI pipeline.
  • Setting up the template is the decision that the feeds it matches may send data to the model. No one inspects each feed first, so its pipelines learn at once.
  • Existing feeds are moved by hand (SIM-8 option D). A minimum creation time keeps the feed's history away from the model.
  • The claimTasksOnWorker requirement goes (SIM-9 option H) after a test-cluster trial with the master queue (Track 1 task 5). Without that, a Content Template can't make an AI pipeline on a default install. If the trial fails, SIM-7 reopens.

12. Rules for working across both tracks

  • The client stops using a feature before the server removes it. This covers provisional bindings, the weights and pass mark, and the QA assessments.
  • Change the step model once. Track 1 task 10 (checks) and Track 2 step 1c (flows in JSON) go together.
  • Change the Setup tab once for the target schema. The field lands with Track 1 task 7.
  • Re-find each audit finding in the merged code before starting a task. The UI merge moved much of what the audit cites.
  • Build parser drift's coverage measure as the filter that structural refactor i needs, so the refactor keeps it.
  • Merge the egress branch while it is still cheap. It confines XsltStep and OutputRecords, which both tracks change. Re-check the confinement after the merge.
  • Every changed screen gets its workbench stories: default, read-only, and dialog OK and Cancel, run with the leak check.

14. Waiting on, and later

Runs and checks still to do

  • The test-cluster trial for the master queue (Track 1 task 5). If it fails, SIM-9 and SIM-7 reopen.
  • A TestLiveScenarios run to confirm Quick, then careful as the default. It uses a real model, so it costs money.
  • Assumptions nobody has checked yet:
    • clusters are real for the first customers (AS8; N8 rests on it);
    • format-date is pure (AS6);
    • learned stylesheets can be confined on their own (AS20);
    • the demo evaluation needs re-running before it is used as a baseline (AS3).

Later: calibration and larger step sizes

Calibrating each model against the scenario suite, and coarser steps (parser and XSLT in one reply, then a whole-pipeline loop), both rely on Track 1's gates, so they come after it. When calibration comes:

  • reconsider sizing the sample from the model (N2 option G);
  • reconsider allowing automatic mode only for calibrated models (UM-6 option C);
  • if quiet automatic feeds wait too long behind a small draft, reconsider letting a later stream replace it (N4 option G).

Release and rollout are outside this project for now.
